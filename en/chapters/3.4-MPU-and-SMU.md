# 3.4 MPU and SMU: Physical Isolation and the Alarm Center

Your colleague is debugging a ghost bug. After 23 hours of continuous operation, the EPS (electric power steering) torque sensor reading occasionally jumps to 0, lasts for one communication cycle, then returns to normal. The bug won't reproduce reliably; sometimes 48 hours pass without a single occurrence. He captured a full week of logic-analyzer data with Lauterbach Trace32 and finally pinned down a chilling root cause:

A `memset()` call in the diagnostic logging task (QM level, not safety-related) wrote through the stack. The stack bottom of the logging task is at 0x7000FFF0, and right next to it is the first address of the EPS torque sensor filter buffer, exactly 0x70010000. The `size` argument in `memset(buffer, 0, size)` was turned into 0x00010014 by a stray pointer—65,556 bytes. Those 65,556 bytes flooded the torque buffer, the CAN transmit mailbox, and half the DMA descriptor table.

Why didn't the MPU stop it? Because the MPU's address regions were partitioned by "task role"—the logging task and the EPS torque task were assigned to the same MPU data region (both marked "application data"). The MPU could stop the logging task from touching the OS kernel region or peripheral registers, but not from crossing its own stack boundary into adjacent application data. The partitioning granularity was too coarse: inside one MPU region, every address is equal for a task that holds the region's permissions.

Even scarier: the values that overwrote the torque buffer were all 0x00. The logging task's `memset` was meant to fill with zeros. The normal torque signal range happens to include 0 (zero torque). So the whole EPS algorithm ran on the wrong input for a full cycle, believing the driver applied no steering force at all; then normal sensor sampling overwrote the data again. The whole process was silent, except that the driver might have felt the steering wheel suddenly go light for an instant.

Your colleague wrote one line in his debug notes: "The granularity of MPU region partitioning determines the effectiveness of the safety boundary."

## How the MPU Works: Defining Territorial Borders in Hardware

The MPU (Memory Protection Unit) is a hardware module in ARM Cortex-R processors. It lets software define up to 12 or 16 memory regions (depending on the implementation) and set independent access permissions for each.

Unlike the MMU (Memory Management Unit), the MPU does no address translation and provides no virtual memory. A physical address is a physical address. The MPU does one thing: when the CPU issues a memory access, it checks whether the target address lies inside a defined region, and whether the current access mode (read/write/execute) and privilege level (privileged/user) are allowed by that region.

```
  MPU access-control decision flow:

  CPU issues a memory access
  (address + read/write + privileged/user)
       │
       ▼
  ┌─────────────────────────────────┐
  │ MPU checks each configured      │
  │ region in turn                  │
  │                                 │
  │ for each region (0..11):        │
  │   if (addr >= base &&           │
  │       addr < base + size)       │
  │   {                             │
  │       check the region's        │
  │       permission attributes:    │
  │       - AP[2:0] (access rights) │
  │       - XN (execute never)      │
  │                                 │
  │       if (access is allowed)    │
  │          continue normally      │
  │       else                      │
  │          raise Data Abort       │
  │   }                             │
  │                                 │
  │ if no region matches:           │
  │   background region rules apply │
  │   (if enabled); otherwise       │
  │   → raise Data Abort            │
  └─────────────────────────────────┘
```

The Cortex-R5 MPU is configured through **CP15 coprocessor registers**. Unlike Cortex-M, it does not use memory-mapped addresses; it operates on the c6 register group through `MCR`/`MRC` coprocessor instructions:

```c
/* Cortex-R5 MPU region configuration — through CP15 c6 registers */
static inline void Mpu_WriteRegion(uint8 region, uint32_t base, uint32_t size_and_attr) {
    asm volatile("MCR p15, 0, %0, c6, c2, 0" :: "r"(region));    /* select the region number */
    asm volatile("MCR p15, 0, %0, c6, c1, 0" :: "r"(base));       /* write the base address */
    asm volatile("MCR p15, 0, %0, c6, c1, 2" :: "r"(size_and_attr)); /* write size + attributes */
}

/* Below is the Cortex-M form: base address and attributes use the memory-mapped MPU_RBAR / MPU_RASR */
void Mpu_ConfigureRegion(uint8 region,
                         uint32 base_addr,
                         uint32 size,
                         uint8 access_permissions,
                         uint8 attributes)
{
    /* RBAR: bits[31:5] = base address (must be aligned to the region size)
     *       bits[3:0]  = region number (used for hardware validation)
     */
    MPU_RBAR(region) = (base_addr & 0xFFFFFFE0U) | (region & 0xFU);

    /* RASR: bits[31:29] = reserved
     *       bit[28]    = XN (execute never)
     *       bits[26:24] = AP[2:0] (access rights)
     *       bits[21:19,18,17,16] = TEX, S, C, B (cache attributes)
     *       bits[15:8]  = sub-region disable bits
     *       bits[5:1]   = SIZE (region size encoding)
     *       bit[0]      = ENABLE
     */
    uint32 rasr_val = ((uint32)access_permissions & 0x7U) << 24U;  /* move AP[2:0] to bits[26:24] */
    rasr_val |= ((uint32)attributes & 0x3FU) << 16U;               /* TEX, S, C, B, etc. */
    rasr_val |= (size << 1U);                                      /* SIZE encoding */
    rasr_val |= 1U;                                                /* ENABLE */

    MPU_RASR(region) = rasr_val;
}
```

The constraint between MPU region size and base-address alignment is often ignored: a region's base address must be naturally aligned to the region size. A 64 KB region must have zeros in the low 16 bits of its base. A 4 KB region must have zeros in the low 12 bits. If you try to configure a region with base 0x70010010 and size 4 KB, hardware behavior is undefined: some implementations ignore the low address bits, others raise a fault.

## MPU Integration in AUTOSAR OS: Making Protection Part of the Runtime Context

In bare-metal code, MPU configuration is static: configured once at startup and never changed. But in AUTOSAR OS, different tasks and ISRs may belong to different safety integrity levels (ASIL D, ASIL B, QM), and their memory access needs are completely different. If all tasks share one MPU configuration, then either the configuration is too loose (QM tasks can access ASIL D data) or too strict (ASIL D tasks are blocked from shared memory they need).

The AUTOSAR OS solution is to **bind MPU configuration to the task context switch**. When the scheduler switches from one task to another, it switches the active MPU region configuration at the same time.

```
  MPU context switch on task switch:

  Task_A (ASIL D, steering)        Task_B (QM, diagnostic log)
  ┌───────────────────┐           ┌───────────────────┐
  │ MPU regions:      │           │ MPU regions:      │
  │ Region 0: Flash   │           │ Region 0: Flash   │
  │ Region 1: RAM_D0  │  ◄─switch─► │ Region 1: RAM_Q0  │
  │ Region 2: RAM_D1  │           │ Region 2: RAM_Q1  │
  │ Region 3: Stack_D │           │ Region 3: Stack_Q │
  │ Region 4: CAN_Buf │           │ Region 4: none    │
  │ Region 5: PWM_Reg │           │ Region 5: none    │
  └───────────────────┘           └───────────────────┘

  Task_A accesses RAM_Q0 → MPU Fault   Task_B accesses PWM_Reg → MPU Fault
```

The AUTOSAR OS `Os_Hal_Arch_ContextSave` and `Os_Hal_Arch_ContextRestore` hooks contain the MPU context save and restore logic. The latency of this process directly affects context-switch time. On a Cortex-R5 at 400 MHz, writing 12 MPU region register pairs (24 32-bit registers) takes about 300 ns. That looks negligible, but in an ultra-fast control loop with a 10 µs period, spending 3% of CPU time on each MPU switch is a design trade-off that deserves serious thought.

One useful MPU feature is **stack overflow detection**. The trick uses the MPU region mechanism to place an inaccessible "guard page" at the bottom of a task stack.

```
  Task stack layout (with an MPU guard page):

  high addr ┌──────────────┐
            │ normal stack │ ← initial SP
            │              │
            │ (read/write) │
            │              │
  low addr  ├──────────────┤
            │ guard page   │ ← MPU configured as no access
            │ (4 KB)       │
  lower     └──────────────┘
            │ other tasks' │
            │ RAM          │
```

As the stack grows downward, SP decreases. Normally SP never enters the guard page. If a task uses too much stack (recursion too deep, local variables too large), SP enters the guard page's address range. The next stack operation (push, function call, and so on) raises an MPU Fault. The OS catches this exception, can identify it as a stack overflow, and takes the appropriate recovery action.

But this mechanism has a race-condition-like blind spot: if the stack grows by more than 4 KB in one step (the guard-page size), SP skips straight over the guard page into the adjacent memory region without raising an MPU Fault. That's why proper stack usage analysis is not optional in safety-critical systems: the MPU guard page is the last line of defense, but it isn't always fast enough.

## SMU: The Alarm-Aggregation Logic of the Safety Management Unit

MPU access violations, lockstep core-to-core mismatches, uncorrectable ECC errors, watchdog timeouts. These fault signals from different sources usually all point to the same destination: the SMU (Safety Management Unit), or an equivalent alarm unit (TI calls it the ESM).

The SMU is the chip's "safety alarm center." It gathers fault signals from every part of the chip and decides what to do according to a preconfigured fault signaling protocol (FSP, Fault Signaling Protocol). Take the Infineon AURIX TC3xx SMU: its architecture has three layers (the register and response details below come from the chip manual; this repository has no corresponding driver):

```
  AURIX TC3xx SMU architecture:

  ┌─────────────────────────────────────────────────────────┐
  │                      alarm sources                      │
  │                                                         │
  │ lockstep  ECC   MPU  watchdog  power   temp             │
  │ mismatch  error viol.         monitor  alarm            │
  │     │      │      │      │      │      │                │
  │     ▼      ▼      ▼      ▼      ▼      ▼                │
  │   ┌──────────────────────────────────────────────────┐  │
  │   │            SMU alarm aggregation layer           │  │
  │   │                                                  │  │
  │   │   ┌─────────┐ ┌─────────┐ ┌─────────┐ ...        │  │
  │   │   │ Alarm 0 │ │ Alarm 1 │ │ Alarm N │            │  │
  │   │   │  group  │ │  group  │ │  group  │            │  │
  │   │   └─────────┘ └─────────┘ └─────────┘            │  │
  │   │        │           │           │                 │  │
  │   │        └───────────┼───────────┘                 │  │
  │   │                    ▼                             │  │
  │   │          ┌──────────────────┐                    │  │
  │   │          │ internal state   │                    │  │
  │   │          │ machine (ISM)    │                    │  │
  │   │          │                  │                    │  │
  │   │          │ current state:   │                    │  │
  │   │          │  RUN → ALARM     │                    │  │
  │   │          │     → FAULT      │                    │  │
  │   │          └─────────┬────────┘                    │  │
  │   │                    │                             │  │
  │   │                    ▼                             │  │
  │   └────────────────────┼─────────────────────────────┘  │
  │                        │                                │
  │                        ▼                                │
  │           ┌───────────────────────────┐                 │
  │           │ fault signaling           │                 │
  │           │ protocol (FSP)            │                 │
  │           │                           │                 │
  │           │ Alarm Level  → IRQ        │                 │
  │           │ Fault Level  → NMI        │                 │
  │           │ Fatal Level  → Reset      │                 │
  │           └─────────────┬─────────────┘                 │
  └─────────────────────────┼───────────────────────────────┘
                            │
                            ▼
              ┌───────────────────────────┐
              │ SCU reset control         │
              │ → trigger system reset    │
              │ → drive PORST pin         │
              └───────────────────────────┘
```

SMU alarm inputs can be configured as "pass-through" or "filtered." In filtered mode you can specify that "an alarm signal is valid only after it persists for N samples," which is very effective against transient interference (false alarms from a single pulse during EMC testing, for example). Typical sampling periods range from microseconds to milliseconds, depending on the physical properties of the alarm source. Lockstep mismatch alarms usually operate at nanosecond scale (no filtering needed; a lockstep mismatch cannot be noise), while external voltage-monitor alarms may need millisecond filtering (noise on the power line is common).

The core SMU internal state machine (ISM) is a multi-state finite state machine implemented in hardware:

```
  SMU internal state machine (simplified):

                ┌──────────┐
      power-on/ │   INIT   │
      reset     └────┬─────┘
                     │ initialization done
                     ▼
                ┌──────────┐      any alarm arrives
                │   RUN    │ ──────────────────┐
                └──────────┘                   │
                     ▲                         ▼
                     │                  ┌──────────────┐
                     │ alarm cleared    │    ALARM     │
                     │                  │ (recoverable)│
                     │                  └──────┬───────┘
                     │                         │
                     │                         │ alarm escalates to fault
                     │                         ▼
                     │                  ┌──────────────┐
                     │                  │    FAULT     │
                     │                  │ (severe)     │
                     │                  └──────┬───────┘
                     │                         │
                     └─────────────────────────┘
                     return via reset or fault recovery
```

The FSP triggers different levels of CPU response according to the current ISM state:
- **Alarm** → maskable interrupt (IRQ) → software can log and try to recover
- **Fault** → non-maskable interrupt (NMI) → software must handle it immediately; it cannot be masked
- **Fatal** → system reset → hardware resets the MCU directly

The beauty of this graded response is that not every error needs an immediate system reset. Some alarms (like a single-bit ECC error) can be logged and handled in a maintenance cycle while the system keeps running. Some faults (like a lockstep mismatch) prove that core computation can no longer be trusted, so the system must enter a safe state immediately. Some catastrophic events (like core voltage dropping below threshold) make any software handling unreliable, leaving hardware reset as the only option.

## FSP: From Alarm to Action

The FSP (Fault Signaling Protocol) is the configuration layer in the SMU that maps alarms to responses. Each alarm source can map to one or more "actions." In the AURIX TC3xx, an FSP action can be:

- trigger a CPU interrupt (IRQ or NMI)
- set a fault status flag
- pull the SMU error output pin low (the ERROR/ESR signal on AURIX)
- trigger a system reset
- reset a specific peripheral module

In an AUTOSAR environment, SMU alarm handling usually involves the `Mcu`, `Gpt`, and `Port` drivers in the MCAL (Microcontroller Abstraction Layer), plus the EcuM fault-handling callback:

```
  Alarm → response, the full path:

  hardware alarm source (e.g. lockstep comparator)
       │
       ▼
  SMU alarm input 0x0B
       │
       ├──► SMU ISM: RUN → ALARM → FAULT
       │         │
       │         ▼
       ├──► FSP action: trigger NMI
       │         │
       │         ▼
       ├──► CPU NMI exception vector
       │         │
       │         ▼
       ├──► Mcu driver: Mcu_PerformReset()
       │         │
       │         ▼
       └──► EcuM: EcuM_AL_DriverInitZero()
            EcuM_AL_DriverInitOne()
            ...
            system resets and restarts
```

One easily overlooked consideration when designing an FSP configuration is the **timing budget for fault response**. The standard requires a fault handling time interval (FHTI, Fault Handling Time Interval) for every safety mechanism that can bring the item to or keep it in a safe state, consistent with the timing requirements allocated from the higher-level architecture. FHTI is the sum of FDTI and FRTI. The total delay from fault occurrence to the system reaching a safe state must not exceed that value.

For an ASIL D steering system, a typical FHTI is 10 ms to 50 ms (this magnitude is engineering experience; the standard only requires the higher-level architecture to allocate a specific value). You need to allocate that time budget precisely:

```
  FHTI timing budget example (ASIL D steering, 50 ms FHTI):

  fault occurs (α particle hits a lockstep core)
       ↓  ≤ 5 ns    lockstep comparator detects the mismatch
       ↓  ≤ 50 ns   SMU alarm input latches
       ↓  ≤ 1 µs    SMU ISM state transition (RUN→ALARM→FAULT)
       ↓  ≤ 2 µs    NMI vector jump
       ↓  ≤ 100 µs  NMI handler: log the fault context
       ↓  ≤ 5 ms    shut down the motor drive bridge (hardware PWM emergency stop)
       ↓  ≤ 10 ms   tell the external watchdog to stop kicking
       ↓  ≤ 20 ms   vehicle degradation mode activates (CAN report)
       ↓  ≤ 50 ms   driver perceives the warning lamp / heavier steering
```

This is only an idealized analysis. In a real system, the WCET of the software NMI handler may far exceed 100 µs, especially if the handler tries to log the full fault context (call stack, task state, register snapshot) to NVM. In safety concept reviews, you often have to trade off "logging enough information for post-mortem analysis" against "reaching the safe state as fast as possible."

## The Fault-to-Error Pin: The Last Sinew

The SMU has another physical mechanism worth special attention: the **Fault-to-Error pin** (the ERROR/ESR signal on AURIX; /PORST is a different kind of reset line, pulled low when the reset control unit initiates a system reset).

This is an open-drain hardware pin. When the SMU internal state machine enters FAULT, the pin is pulled low. In a typical system design, this pin connects directly to the enable input of an external power management chip (PMIC/SBC). When it is pulled low, the PMIC cuts the MCU's VDD supply and forces a physical power-off. After a configured delay (long enough for all capacitors to discharge), the PMIC powers up again and the MCU runs the full POR sequence.

```
  External safety monitor connection:

  MCU                                PMIC/SBC
  ┌──────────────────────┐          ┌──────────────────┐
  │                      │          │                  │
  │  SMU ──► /FaultOut ──┼──────────┼──► /ENABLE_MCU   │
  │                      │          │         │        │
  │                      │          │         ▼        │
  │                      │          │   VDD_CORE = 0 V │
  │                      │          │                  │
  │                      │          │  after a 10 ms   │
  │                      │          │  delay, VDD_CORE │
  │                      │          │  recovers        │
  │                      │          │                  │
  └──────────────────────┘          └──────────────────┘
```

This design solves a fatal chicken-and-egg problem: if the SMU detects that core voltage has fallen to a level where reliable CPU operation cannot be guaranteed, how do you make the CPU run fault-response code? The answer is that you can't. The Fault-to-Error pin is a pure hardware path. It goes through no CPU code, depends on no clock, and needs no running software. It is just an NMOS pull-down transistor on the silicon driven by the SMU state machine's output. Even if the CPU is completely deadlocked, the /FaultOut pin can still be pulled low.

This is the lowest-level safeguard in functional safety hardware design. If this pin also fails, it is like a person whose hypothalamic heat-regulation center has shut down: all you can do is wait for an external observer to notice and intervene. In automotive systems, that "external observer" is usually a cluster warning lamp driven by another independent MCU, or a second domain controller.

The MPU and the SMU represent two different philosophies in functional safety architecture. The MPU is preventive: it uses spatial isolation to stop faults from propagating across safety integrity levels. The SMU is reactive: it gathers alarm signals from every source and makes unified decisions with graded responses.

One intriguing design fact: the stricter the MPU configuration, the more often the SMU is triggered. Conversely, if SMU alarms are rare, the MPU configuration may be too loose: faults are propagating silently across domains without triggering access violations. A good safety architect uses SMU alarm statistics to continuously refine the MPU region partitioning strategy.

MPU and SMU configuration is not a one-time activity. With domain fusion and central computing platforms, it is increasingly common for ASIL D, ASIL B, and QM software to share one SoC. Completeness reviews of the MPU configuration and fault-injection tests of SMU alarm paths must become mandatory checks for every software release.

## Summary

1. The MPU implements spatial isolation through hardware access-control regions and does not rely on software cooperation. AUTOSAR OS binds MPU configuration to the task context switch, so tasks at different ASIL levels have independent region permissions.
2. MPU region base addresses must be naturally aligned to the size (the low 16 bits of a 64 KB region must be zero). A misconfiguration leads to undefined behavior.
3. The SMU gathers all hardware alarms—lockstep mismatch, ECC error, MPU violation, watchdog timeout—and uses the FSP (Fault Signaling Protocol) to grade the response as IRQ/NMI/hardware reset.
4. FHTI is the sum of FDTI and FRTI, and the timing budget must be allocated precisely (every nanosecond from fault occurrence to safe state). The standard's criterion for "covered in time" is that FDTI plus FRTI is below the relevant FTTI; the 10–50 ms budget magnitude for an ASIL D steering system is engineering experience, and once it exceeds its corresponding FTTI, the fault is not considered covered in time.
5. The Fault-to-Error pin is a pure hardware safety path. It depends on no software or clock and can pull the PMIC enable pin low to force power-off even when the CPU is completely deadlocked.
