# 4.1 The Safety Stack at a Glance: A Map of Arctic Core's Safety Modules

## Scenario: The Moment You Open the Repository

You open the Arctic Core source tree, set on finding out where the functional safety code actually lives. You search the whole directory tree and find safety modules scattered across three completely different top-level directories:

```
classic-platform/
├── safety_security/    ← safety/crypto core
│   ├── WdgM/           ← watchdog manager (1450 lines)
│   ├── WdgIf/          ← watchdog abstraction interface
│   └── SafeLib/
│       ├── Crc/        ← CRC engine (32/16/8-bit)
│       └── E2E/        ← end-to-end communication protection library
├── memory/
│   ├── RamTst/         ← SRAM hardware self-test
│   ├── NvM/            ← non-volatile memory management
│   └── ...
└── datastructures/
    └── Safety_Queue/   ← CRC-protected safety queue
```

Those file locations are not arbitrary. Every module is a layer of defense, a **safety immune system**. Arctic Core is the open-source AUTOSAR platform from ArcCore AB, dual-licensed under GPLv2 (GPLv2 + commercial license). It follows the AUTOSAR 4.3.0 specification closely and carries detailed `@req SWS_xxx` requirement traceability tags.

This chapter covers about **6560 lines of C safety code**, spread across 16 core source files. Today we draw a map and take in the whole picture.

## 1. Why Does It Look Like the Immune System?

Arctic Core's safety stack works in layers, like the human immune system. RamTst walks every SRAM block after the ECU powers up and looks for stuck-at faults in the silicon; that is a physical inspection at the hardware level. WdgM refreshes the deadline and logical substates on every checkpoint report, evaluates alive supervision once per MainFunction cycle, and aggregates the state of each entity — runtime patrol. E2E + CRC + Safety_Queue use mathematical signatures to verify that every message is genuine. And WdgM gathers all the local states, decides which global state the system enters among OK/FAILED/EXPIRED/STOPPED (the enum also has DEACTIVATED, meaning not activated), and triggers a reset or degradation.

You will see this logic again and again in the sections that follow. For now, look at the architecture.

## 2. Mapping onto AUTOSAR Layers

Where Arctic Core's safety modules sit in the AUTOSAR layered architecture:

```
┌──────────────────────────────────────────────┐
│  Application layer (SW-Cs, CDDs)             │
│  Calls WdgM_CheckpointReached()              │
│  Calls E2E_P01Check()/E2E_P01Protect()       │
│  Uses Safety_Queue for communication         │
├──────────────────────────────────────────────┤
│  RTE (Run-Time Environment)                  │
│  Rte_Switch_globalMode_currentMode()         │
│  modeFunctionSwitchPointer[]                 │
├────────────────┬─────────────────────────────┤
│  Service layer │  ECU abstraction layer      │
│  WdgM          │  WdgIf                      │
│  RamTst        │  Mcu (reset)                │
│  Crc           │  Os (counter)               │
├────────────────┴─────────────────────────────┤
│  MCAL (Microcontroller Abstraction)          │
│  Hardware watchdog driver                    │
└──────────────────────────────────────────────┘
```

Key point: WdgM sits in the service layer, and it never touches the hardware watchdog directly. It goes through the WdgIf abstraction layer. That indirection is core AUTOSAR philosophy: **the upper layer cares only about policy (when to trigger the watchdog), the lower layer about mechanism (how to touch the registers)**.

## 4. Module-by-Module Overview

### WdgM (Watchdog Manager): The Core Dispatcher

File: `safety_security/WdgM/src/WdgM.c` (1450 lines)

WdgM is the "brain" of the safety stack. It implements the triple supervision defined by the AUTOSAR specification:

- **Alive Supervision**: application software calls `WdgM_CheckpointReached()` to report that it is still alive. Inside that call WdgM increments the counter for the matching checkpoint; at `WdgM_MainFunction()` it evaluates against the supervision reference cycle and uses the tolerance (MinMargin/MaxMargin) to decide whether things are normal.
- **Deadline Supervision**: uses the OS counter to record the interval between two checkpoints and checks whether it falls between DeadlineMin and DeadlineMax.
- **Logical Supervision**: maintains a **transition table** (Transitions) and verifies that checkpoints execute in a legal order. Only the directed edges defined in the graph are valid program execution paths.

On every `WdgM_MainFunction()` pass, WdgM aggregates the results of the three substates, updates each SupervisedEntity's LocalState (OK→FAILED→EXPIRED), then derives the GlobalState (OK/FAILED/EXPIRED/STOPPED, plus DEACTIVATED in the enum), and finally decides whether to trigger a hardware watchdog reset.

### WdgIf (Watchdog Abstraction Interface)

It lives in `safety_security/WdgIf/` and gives WdgM a uniform hardware watchdog interface: `WdgIf_SetMode()` and `WdgIf_SetTriggerCondition()`. WdgM uses WdgIf to switch watchdog modes (FAST/SLOW/OFF) without caring which chip is underneath.

### E2E Library (End-to-End Communication Protection)

Files: `E2E.c`, `E2E_P01.c`, `E2E_P02.c`, `E2E_P04.c`, `E2E_P05.c`, `E2E_P06.c`, `E2E_SM.c` under `SafeLib/E2E/src/`, plus `inc/E2E.h`

The E2E library provides data protection for end-to-end communication. Arctic Core implements 5 profiles (P01 P02 P04 P05 P06). The core mechanisms:

- **Protect (sender)**: embeds a CRC checksum + counter + DataID in the data frame.
- **Check (receiver)**: extracts the counter, computes the CRC, compares the DataID, detects duplicates/loss/reordering/timeout.
- **State Machine**: keeps OK/ERROR counts over a sliding window and moves through INIT→VALID→INVALID.

Worth noting: the E2E library **may not call RTE or BSW modules**. It has to be a pure mathematical function library, reporting errors only through return values.

### The CRC Engine

File: `SafeLib/Crc/src/Crc_32.c` (232 lines)

It implements IEEE-802.3 CRC32 (polynomial 0x04C11DB7), with a compile switch choosing one of two:
- `CRC_32_RUNTIME`: bit-by-bit calculation (used to cross-check the table result)
- `CRC_32_TABLE`: 256-entry precomputed table (the default setting in the configuration)

It also implements CRC8 (SAE J1850 polynomial 0x1D) and CRC16, called by E2E and Safety_Queue.

### Safety_Queue

File: `datastructures/Safety_Queue/src/Safety_Queue.c` (284 lines)

A **dual-CRC protected** ring buffer. Before every Add/Next/Peek/Contains operation it computes the CRC8 of all data and compares it with the stored value. If hardware silently flips any bit in memory, the queue immediately returns `QUEUE_E_CRC_ERR`. This is a data structure built specifically for ASIL levels.

### RamTst (SRAM Self-Test)

File: `memory/RamTst/src/RamTst.c` (561 lines)

It runs the March X algorithm at ECU startup:
1. Write all 0 in ascending order
2. Read 0, write 1 in ascending order
3. Read 1, write 0 in descending order
4. Read 0 in descending order

Each step catches a particular fault model: stuck-at, coupling, address decode errors. Configured per block, reported per block. `RamTst_Suspend()` and `RamTst_Resume()` are currently empty functions; pausing is up to the upper-layer schedule.

## 5. The Compile-Time Configuration Tree

Look at `WdgM_ConfigTypes.h` and you find a key design decision: **all configuration is const structs**, with no runtime allocation:

```c
WdgM_ConfigType  ← top-level configuration
├── WdgM_General
│   ├── SupervisedEntities[]  → WdgM_SupervisedEntity (transition graph, start/end points)
│   └── Watchdogs[]           → WdgM_Watchdog (device mapping)
└── WdgM_ConfigSet
    ├── DemEventIdRefs        → DEM event IDs
    ├── initialModeId         → initial mode
    └── Modes[]               → WdgM_Mode
        ├── SEConfigurations[] → WdgM_SupervisedEntityConfiguration
        │   ├── AliveSupervisions[]    → expected/tolerance per checkpoint
        │   ├── DeadlineSupervisions[] → start/end checkpoint + time bounds
        │   └── FailedAliveSupervisionReferenceCycleTol → tolerated cycle count
        ├── Triggers[]         → WdgM_Trigger (watchdog mode + trigger value)
        └── ExpiredSupervisionCycleTol → Expired→STOPPED tolerance
```

All of this is fixed before linking. A version mismatch fails the build (via `#error`); errors in the configuration content itself are caught by runtime parameter checks that return an error code. That is a core principle of functional safety coding.

Arctic Core's safety stack is not "a pile of feature modules". It uses **const compile-time configuration** to weave all the modules into one complete defense chain: SRAM self-test at startup → triple runtime supervision → data integrity checks → hardware watchdog reset. Every layer's failure has an explicit state machine to handle it, and there is no "silent failure" path. That is the real difference between production-grade code and prototype code.

## Summary

1. Arctic Core's safety stack is spread across three top-level directories — `safety_security/`, `memory/`, and `datastructures/` — about 6560 lines of C code in total, forming a layered defense chain from hardware self-test to runtime supervision to data integrity.
2. WdgM (the watchdog manager) is the "brain" of the stack. It implements Alive/Deadline/Logical triple supervision and, in each MainFunction cycle, aggregates the local states into a global state (OK→FAILED→EXPIRED→STOPPED, plus DEACTIVATED in the enum), which decides whether to trigger a hardware watchdog reset.
3. The E2E library and the CRC engine are pure function libraries that depend on neither RTE nor BSW modules. They protect end-to-end communication with CRC checks, counters, and DataID, and can be certified independently as a Safety Element out of Context (SEooC).
4. Safety_Queue uses dual-CRC protection (bufferCrc + queueCrc) and verifies data integrity before every Add/Next/Peek operation, returning `QUEUE_E_CRC_ERR` when it detects silent RAM corruption.
5. RamTst runs the March X algorithm at ECU startup, walking up and down through four passes to detect stuck-at, coupling, and address decode faults. All configuration is const compile-time structs; version errors surface before linking, and configuration content errors are caught by runtime checks.
