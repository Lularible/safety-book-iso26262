# 3.3 ECC and Memory Protection: DNA Error Correction in Silicon

In the failure-analysis lab, you have a domain controller that just "died" after a 48-hour high-temperature aging test. The QA engineer says it produces one bit error for every million CAN frames it processes. Not an error on the CAN bus—CRC already catches those. The data inside the MCU's SRAM is being silently corrupted somewhere along the way. You've scoped it for four days and found nothing. Finally, you find the answer in an SEM (scanning electron microscope) image: in the SRAM array, cell number 4,783,291 has a 0.3 µm pinhole in the gate oxide of its NMOS pull-down transistor. At 85 °C, that tiny leakage path cuts the cell's charge-retention time from a theoretical infinity down to 3.2 seconds.

In the memory world, 3.2 seconds is not an error, or even an anomaly. A 3.2-second retention time means that if your SRAM is read and written only once every 10 ms, the cell never fails. But under one specific corner case (the one where you found the problem), a 200 ms blocking interrupt left the SRAM untouched for 207 ms. Bit 4,783,291 flipped slowly and invisibly. The data was wrong. The wrong data computed the steering angle command. The steering motor pushed in a direction it should never have pushed. And at the physical level, all of this came from an oxide defect 300 times thinner than a human hair.

You take a deep breath and archive the SEM image. Then you turn to page 23 of the datasheet: "On-Chip SRAM: 1.4 MB, with ECC." You know that if this chip's ECC is not correctly initialized and configured, that pinhole will cause a dangerous wrong steering command in the first week of real-road testing after production. But you already stepped in this hole on a previous project: in the current startup code, SRAM ECC is fully initialized before the first line of C code runs.

## 6T SRAM: Every Bit Dances on a Knife's Edge

Before discussing ECC, you must understand what it protects. The on-chip SRAM of a modern MCU consists of millions of 6T cells (6-Transistor Cells). Each cell stores one bit and is built from two cross-coupled inverters and two access transistors.

```
  6T SRAM cell circuit:

       WL (word line)
        │
        ▼
       ┌┴┐          ┌┴┐
  ─────┤M5├──────────┤M6├─────
       └┬┘          └┬┘
        │            │
        ▼            ▼
      ┌─┴──────┬─────┴─┐
      │        │       │
  ┌───┴─┐   ┌──┴───┐   │
  │ M1  │   │  M2  │   │
  │     ├─┐ ┌┤      │   │
  └──┬──┘ │ │ └──┬───┘   │
     │    │ │    │       │
     ├────┘ └────┤       │
  ┌──┴─┐      ┌──┴─┐     │
  │ M3  │      │ M4 │     │
  │     │      │    │     │
  └──┬──┘      └──┬─┘     │
     │            │       │
     └────────────┘       │
          │               │
         VDD             GND

  BL (bit line)     BLB (bit line bar)
```

The cross-coupled inverters (M1/M3 and M2/M4) form a bistable circuit: when Q is high, Q-bar is necessarily low, and vice versa. Once that state is established, it can in theory be held forever (as long as VDD stays up). But several physical mechanisms can break the balance:

**α-particle interference**: an α particle crosses the silicon substrate, ionizing silicon atoms along its path and generating a large number of electron-hole pairs. If those charges are collected at a storage node, the node voltage can flip from high to low. At 40 nm, the critical charge of a 6T cell (Qcrit, the minimum deposited charge needed to flip it) is roughly 1.5 fC to 3 fC. A 5 MeV α particle deposits about 160 fC in silicon, 50 to 100 times Qcrit. SRAM has no defense against this.

**NBTI aging (Negative Bias Temperature Instability)**: under high temperature and negative bias, a PMOS transistor's threshold voltage drifts slowly. Over time, the drive strength of M3 or M4 drops, and the loop gain of the cross-coupled pair falls. When the gain drops below 1, the bistable state degrades, and any small disturbance can flip the cell.

**Electromigration and TDDB (Time-Dependent Dielectric Breakdown)**: just like the gate-oxide pinhole in the opening scenario, long-term electric-field stress gradually forms a conductive path in the oxide. Once formed, leakage current persists, and the node voltage slowly decays.

All these failure mechanisms share one feature: in the early stage of fault development, they affect only a single storage cell. ECC protection is built on exactly that assumption: it corrects single-bit errors, detects double-bit errors, and for three or more bits it can detect only some of them.

## Hamming Codes: The Mathematical Magic of Protecting 32 Bits with 7

The core of ECC is the SECDED code (Single Error Correction, Double Error Detection), most commonly an extended version of the Hamming code. A standard Hamming(7,4) code encodes 4 data bits in 7 bits and can correct one bit error. In a real MCU, we deal with much wider data. A typical SRAM ECC uses a (39,32) code: 32 data bits plus 7 check bits, forming a 39-bit "codeword."

The 7 check bits are generated by XOR operations over specific subsets of the data bits. Each check bit covers a subset of data bits defined by the Hamming matrix:

```
  Typical (39,32) SECDED Hamming matrix:

  data bits: D[31:0] = d₃₁ d₃₀ ... d₁ d₀
  check bits: P[6:0]  = p₆ p₅ p₄ p₃ p₂ p₁ p₀

  check-bit generation (on write):
  p₀ = XOR{d₀, d₁, d₃, d₄, d₆, d₈, d₁₀, d₁₁, d₁₃, d₁₅, d₁₇, d₁₉, d₂₁, d₂₃, d₂₅, d₂₆, d₂₈, d₃₀}
  p₁ = XOR{d₀, d₂, d₃, d₅, d₆, d₉, d₁₀, d₁₂, d₁₃, d₁₆, d₁₇, d₂₀, d₂₁, d₂₄, d₂₅, d₂₇, d₂₈, d₃₁}
  p₂ = XOR{d₁, d₂, d₃, d₇, d₈, d₉, d₁₀, d₁₄, d₁₅, d₁₆, d₁₇, d₂₂, d₂₃, d₂₄, d₂₅, d₂₉, d₃₀, d₃₁}
  p₃ = XOR{d₄, d₅, d₆, d₇, d₈, d₉, d₁₀, d₁₈, d₁₉, d₂₀, d₂₁, d₂₂, d₂₃, d₂₄, d₂₅}
  p₄ = XOR{d₁₁, d₁₂, d₁₃, d₁₄, d₁₅, d₁₆, d₁₇, d₁₈, d₁₉, d₂₀, d₂₁, d₂₂, d₂₃, d₂₄, d₂₅}
  p₅ = XOR{d₂₆, d₂₇, d₂₈, d₂₉, d₃₀, d₃₁}
  p₆ = XOR(all 39 bits of the codeword)  ← this extra check bit enables double-bit error detection
```

When data is read back, the ECC controller recomputes the check bits and XORs the new ones with the stored ones. The XOR result is called the **syndrome**.

**Syndrome = 0**: no error, or an undetectable multi-bit error (extremely unlikely).

**Syndrome ≠ 0, and parity bit p₆ indicates an odd error**: single-bit error. The syndrome value points directly at the position of the bad bit. The ECC controller flips that bit and returns the corrected data.

**Syndrome ≠ 0, and parity bit p₆ indicates an even error**: double-bit error. The ECC controller cannot correct it and raises an uncorrectable-error interrupt.

```
  Single-bit error correction example:

  write data:     0x5A3C_F721 = 01011010 00111100 11110111 00100001
  write check bits: 0x3E     = 011_1110

  α particle hits bit[13] (flips from 1 to 0)

  read data:      0x5A3C_D721 = 01011010 00111100 11010111 00100001
                                                      ↑
                                                  bit[13] flipped

  recompute check bits: 0x6D = 110_1101

  Syndrome = 0x3E XOR 0x6D = 0x53 = 101_0011

  Lookup: the low 6 bits of the syndrome, 0x13 = 19, and codeword position 19 maps to bit[13]
  → flip bit[13]
  → corrected data = 0x5A3C_F721 (matches the original data)
```

This process is handled entirely by the hardware ECC controller and is transparent to the CPU. When the CPU reads a 32-bit word from SRAM, what it sees on the bus is always corrected data, unless a double-bit error occurred (in which case the ECC controller raises a data abort exception).

## Flash ECC: A Different Medium, Different Challenges

On-chip Flash (eFlash) has fundamentally different failure modes from SRAM. SRAM faults are mainly transient flips; the bit cell itself is not damaged, only its state was changed by an external force. Flash faults are more often **cumulative degradation**.

Flash stores each bit by injecting or removing charge from a floating-gate transistor. The floating gate is completely surrounded by SiO₂ insulation, so in theory charge can be retained for decades. But each program/erase (P/E) operation introduces tiny damage into the oxide, and hot-carrier injection creates trap states in the oxide. When trap density reaches a certain level, charge on the floating gate leaks slowly through trap-assisted tunneling (TAT).

That is why Flash has two core specs: **endurance** and **data retention**. A typical 40 nm eFlash macro specifies 100,000 P/E cycles of endurance and 20 years of data retention at 85 °C. If you write Flash frequently (say, adaptive parameters stored in NVM), you may exhaust data retention before you exhaust endurance.

Flash ECC usually uses stronger correction. Many MCU Flash controllers integrate **multi-bit correction** (for example, 4-bit ECC per 256-bit page), because Flash faults tend to be "regional": one oxide defect can affect several adjacent bits. According to public device data, take the Renesas RH850 family: its Code Flash uses a 256 data bits + 45 ECC bits scheme and can correct up to 4 bit errors.

```c
/* Flash ECC error-handling callback example (Renesas RH850 style) */
void Flash_ECC_ErrorHandler(uint32 fault_address, uint8 ecc_status)
{
    if ((ecc_status & FLASH_ECC_1BIT_CORRECTED) != 0U)
    {
        /* Single-bit and correctable: log it but do not interfere with operation */
        Dem_ReportErrorStatus(DemConf_DemEventParameter_FlashEcc1Bit, DEM_EVENT_STATUS_PASSED);
        /* Optional: trigger preventive refresh—copy the affected page to a new location */
        Flash_RefreshPage(fault_address);
    }
    else if ((ecc_status & FLASH_ECC_UNCORRECTABLE) != 0U)
    {
        /* Uncorrectable ECC error: this is a safety event */
        Dem_ReportErrorStatus(DemConf_DemEventParameter_FlashEccUncorr, DEM_EVENT_STATUS_FAILED);
        /* Decide the response strategy according to the safety concept */
        if (ASIL_LEVEL >= ASIL_C)
        {
            /* Trigger the safe state */
            EcuM_RequestReset(EcuM_RESET_SAFE);
        }
    }
}
```

Another peculiarity of Flash ECC: Flash is usually read in "pages" or "blocks" (say, 256 or 512 bits), while SRAM is read in 32-bit or 64-bit words. So Flash ECC has coarser coding granularity. A longer codeword means higher coding efficiency (less redundancy), but also longer encode/decode latency.

## MBIST: Letting Hardware Check Its Own Memory

ECC protects the integrity of runtime data. But who guarantees that the ECC logic itself has no fault? Who checks whether the "cold" SRAM cells that the CPU never touches (say, the storage for static variables written once at startup and then read-only forever) can still store data correctly?

The answer is a hardware mechanism called MBIST (Memory Built-In Self Test). MBIST is a hardware test engine implanted next to the SRAM controller at chip design time. It can automatically write specific test patterns into SRAM, read them back, and compare—without CPU involvement.

Typical MBIST test algorithms include:

**March C- algorithm** (the most common SRAM test algorithm):
```
  1. ↑ Write 0x00000000 to all addresses (initialize everything to 0)
  2. ↑ Read 0x00000000, write 0xFFFFFFFF, then increment the address (read 0, write 1)
  3. ↑ Read 0xFFFFFFFF, write 0x00000000, then increment the address (read 1, write 0)
  4. ↓ Read 0x00000000, write 0xFFFFFFFF, then decrement the address (reverse read 0, write 1)
  5. ↓ Read 0xFFFFFFFF, write 0x00000000, then decrement the address (reverse read 1, write 0)
  6. ↑ Read 0x00000000 from all addresses (final check)
```

This seemingly simple sequence detects almost every common SRAM manufacturing defect: stuck-at faults, transition faults, coupling faults, and address decoder faults.

```c
/* Simplified MBIST startup code example (executed at startup) */
void Bsp_Mbist_Run(void)
{
    /* Configure the MBIST controller */
    MBIST->START_ADDR = (uint32)&__SRAM_START;
    MBIST->END_ADDR   = (uint32)&__SRAM_END;
    MBIST->ALGORITHM  = MBIST_ALG_MARCH_C_MINUS;  /* March C- */
    MBIST->BACKGROUND = 0x00000000U;               /* initial background pattern */

    /* Start the test */
    MBIST->CTRL |= MBIST_CTRL_START;

    /* Poll until done (real code may use an interrupt) */
    while ((MBIST->STATUS & MBIST_STATUS_DONE) == 0U)
    {
        /* wait */
    }

    /* Check the result */
    if ((MBIST->STATUS & MBIST_STATUS_FAIL) != 0U)
    {
        uint32 failing_addr = MBIST->FAIL_ADDR;
        uint32 expected     = MBIST->EXPECTED_DATA;
        uint32 actual       = MBIST->ACTUAL_DATA;

        /* Log to DEM / NVM */
        Dem_ReportErrorStatus(DemConf_DemEventParameter_SramMbistFail,
                              DEM_EVENT_STATUS_FAILED);

        /* ASIL D systems usually do not allow operation to continue after MBIST failure */
        while (1) { /* enter a safe stopped state */ }
    }

    /* MBIST has cleared all of SRAM — all RAM variables must be re-initialized */
}
```

A key challenge with MBIST is that during the test it **destroys everything in SRAM**, because the March algorithm writes test patterns. That means a full MBIST cannot run during normal operation. It usually runs at two points:
1. **At power-on**: before the C runtime environment is initialized (in the startup code)
2. **In the shutdown sequence**: before system power-off

For systems that need continuous SRAM health monitoring at runtime, there is also a lightweight "online MBIST" that performs destructive testing only on SRAM regions not currently in use, avoiding live task data. This requires cooperation from the operating system and the memory management unit (MPU).

## LBIST: Extending the Test from Memory to Logic

If MBIST is a medical checkup for SRAM, then LBIST (Logic Built-In Self Test) is a medical checkup for combinational and sequential logic. LBIST uses scan chains already built into the chip design—part of the DFT (Design for Testability) infrastructure—to self-test random logic.

The basic principle of LBIST: a hardware PRPG (Pseudo-Random Pattern Generator) shifts a set of test vectors into the scan chains. After one clock cycle of combinational logic, the outputs are captured into the scan chains and shifted out to a MISR (Multiple Input Signature Register). The MISR compresses the whole response sequence into a fixed-length "signature." If the signature does not match the expected value, the logic contains a manufacturing defect.

The main use of LBIST in automotive functional safety is **power-on self-test**: a full logic-gate health check at power-on. One LBIST run can cover millions of logic gates in tens of milliseconds, far faster than any software self-test.

But LBIST has a fundamental limit: it can detect only static manufacturing defects (stuck-at faults, bridging faults). It cannot detect timing-related faults (like path-delay degradation), because LBIST usually runs at reduced frequency to ensure the test vectors propagate correctly. For aging-induced timing degradation, software test libraries (STL) are needed as a supplement.

## Bus ECC: When Data Is Attacked in Transit

ECC protects not only data at rest (in SRAM) but also data in motion (on buses). The data path from SRAM to CPU, the instruction-fetch path from Flash to cache. These physical wires are equally exposed to electromagnetic interference and α particles.

The AXI interconnect of a modern MCU usually includes end-to-end ECC protection. Take the ARM CoreLink NIC-400 interconnect: it can add optional ECC logic to every bus channel:

```
  AXI read data path with ECC protection:

  SRAM ──► [39-bit data + ECC] ──► NIC-400 interconnect ──► CPU
               │                                          │
               │   ┌──────────────────────┐               │
               └──►│ recompute ECC at     │◄──────────────┘
                   │ every node along the │
                   │ path, compare with   │
                   │ the stored value     │
                   │ error → correct or   │
                   │ report               │
                   └──────────────────────┘
```

The key design consideration for bus ECC: checking and correction happen independently at **every bus node**. Data from SRAM to CPU may pass through three intermediate nodes (SRAM controller → NIC-400 switch → CPU subsystem AXI bridge), and each node recomputes and checks ECC. This ensures that interference anywhere along the transfer path is detected. It also pinpoints which segment the fault occurred in.

This design—end-to-end plus per-node double protection—is a best practice in functional safety: the failure of any single protection mechanism is caught by another layer.

The essence of ECC is not "make memory never fail" but accepting that "memory will always fail" and trading information redundancy for reliability. Analog circuit designers pursue higher inherent circuit reliability: bigger transistors, thicker oxide. Digital designers use ECC to accept a fact: at nanometer process nodes, a single transistor is no longer reliable, but coding theory can protect 32 information bits with 7 extra bits.

This idea comes from life science. DNA polymerase makes one error for every 10⁵ base pairs it inserts during replication, but its 3'→5' exonuclease activity can "proofread": when it detects a mismatch, it steps back, excises the wrong nucleotide, and inserts the right one. This proofreading cuts the error rate from 10⁻⁵ to 10⁻⁷. ECC is the DNA proofreading mechanism inside a chip: Hamming codes correspond to DNA polymerase proofreading (real-time correction), MBIST corresponds to the DNA-damage checkpoints in the cell cycle (periodic full scans), and preventive Flash page refresh corresponds to nucleotide excision repair.

For engineers, the biggest ECC trap is "thinking it's safe once it's enabled." Whether ECC actually works depends on three preconditions: SRAM initialization covers the ECC domain, ECC error interrupts are correctly configured and connected to the SMU, and the single-bit error rate is monitored. Neglect any one, and ECC turns from a protection mechanism into a false sense of safety.

## Summary

1. ECC uses SECDED Hamming codes, adding 7 check bits to every 32 data bits to form a 39-bit codeword. It corrects single-bit errors, detects double-bit errors, and is fully transparent to the CPU.
2. The real precondition for ECC is that SRAM must be fully initialized before the first line of C code runs; otherwise uninitialized ECC check bits produce false corrections or missed detection.
3. Flash ECC needs stronger multi-bit correction (for example, correcting 4 bits per 256 bits), because Flash faults tend to be regional degradation rather than single-bit transient flips.
4. MBIST uses the March C- algorithm at startup to thoroughly detect SRAM manufacturing defects (stuck-at, transition, coupling faults), but it destroys all stored contents.
5. Bus ECC checks independently at every intermediate node of the data path (SRAM controller, NIC-400 switch, AXI bridge), ensuring data in motion is equally protected.
