# 2.13 Software Testing and MC/DC: Every Line Must Testify for Safety

## The immune metaphor: testing is the software's immune system

The human immune system works like an engineering miracle: it does not wait until a pathogen has already done widespread damage. It patrols actively, recognizes anomalies, and strikes specific targets. T cells undergo "negative selection" in the thymus: any T cell that would attack the body's own tissue is eliminated. What remains attacks only foreign invaders. This process is the biological version of "testing." Every T cell must prove it will not harm friendly tissue before it is allowed on duty.

Software testing plays the same role in functional safety as the immune system. Every line of code you write must prove its "loyalty" through layer after layer of testing before the car ships. It will not flip a sign bit under some boundary condition, will not deadlock under some interrupt nesting, will not skip a safety check under some rare timing combination. Part 6 of ISO 26262 lays down extremely detailed rules for this "immune screening" process: from software unit testing to integration testing to vehicle-level testing, every layer has explicit coverage requirements, and how strict those requirements are is tied precisely to the ASIL.

Next, put yourself into a real test scenario.

## Scenario: the safety decision on steering angle

You're in the test lab staring at a screen that shows a piece of apparently unremarkable C code:

```c
if ((steering_angle > MAX_ANGLE) && (!calibration_active) && (!emergency_override))
{
    Trigger_Safety_Shutdown();
}
```

The meaning is straightforward: when the steering angle exceeds the maximum allowed value, calibration is not active, and emergency override has not been triggered, execute a safety shutdown. Three conditions, one decision. The question is: how do you prove you have tested enough?

A test engineer's instinct is: give it an over-limit angle, make the other two conditions true, run it once, see Trigger_Safety_Shutdown() called, tick the box, done. That's "statement coverage": the code was executed. Satisfied?

You're not satisfied. Because you know that a single input set (angle=MAX_ANGLE+1, calibration_active=0, emergency_override=0) covers the if line and the function call inside it: 100% statement coverage. But have you verified that safety shutdown is not triggered wrongly when any one condition fails? That calibration being active prevents a false shutdown even when the angle is over the limit? That the driver can deliberately exceed the limit in emergency override mode?

No. 100% statement coverage may cover only 12.5% of the logic's behavior. That's why ISO 26262 requires coverage criteria of different depth at different ASILs.

## From statement coverage to MC/DC: four levels of progression

You decide to test this decision systematically. You sit down and draw the truth table. Three boolean conditions: A = (steering_angle > MAX_ANGLE), B = (!calibration_active), C = (!emergency_override). Decision D = A && B && C.

**Statement coverage** only requires proving that every executable line ran at least once. For this if statement, one input set is enough: A=T, B=T, C=T. D=T, the branch is taken. Statement coverage: 100%. You have proven exactly one thing: this code "can run." It's like checking a car's brake pedal. You pressed it and it moved. But you don't know whether it will snap at highway speed, whether ABS will false-trigger on a wet road, or whether it still works after heat fade on a long descent.

**Branch coverage** requires every possible outcome of every decision to occur at least once. For this if, you need D=T (branch taken) and D=F (branch skipped), each once. You add an input set: A=F, B=T, C=T, so D=F. Now you have proven two things: safety shutdown triggers when it should, and does not trigger when it shouldn't. But you still don't know which condition prevented the trigger: was the angle within limits? Was calibration active? Was emergency override on? You don't know, because a single false condition makes D false. The independent effect of A, B, and C is hidden by the logical AND.

**Condition coverage** requires each atomic condition to take both true and false at least once. For three conditions, you need A=T and A=F, B=T and B=F, C=T and C=F, each once. But you can satisfy condition coverage with two input sets while branch coverage remains incomplete. That leads to MC/DC.

**MC/DC (Modified Condition/Decision Coverage)** is the answer you're looking for. MC/DC requires:
1. Every possible outcome of every decision occurs at least once;
2. Every condition independently affects the decision's result at least once;
3. Every entry point and exit point is invoked at least once.

"Independent effect" is the soul of MC/DC. It requires you to prove that, with all other conditions held fixed, changing this one condition flips the result of the whole decision. That means you must find the test vectors where "this condition is the deciding vote."

You design test cases. Fix B=T, C=T, and let A go from F to T: D goes from F to T. This proves A independently affects D. Fix A=T, C=T, and let B go from T to F: D goes from T to F. This proves B independently affects D. Fix A=T, B=T, and let C go from T to F: D goes from T to F. This proves C independently affects D. Add A=F, B=T, C=T (D=F) to cover the false branch of the decision.

Four test cases:

| Case | A | B | C | D | What it proves |
|------|---|---|---|---|------|
| 1 | T | T | T | T | Baseline where the decision is true |
| 2 | F | T | T | F | A independently affects D (flip A → flip D) |
| 3 | T | F | T | F | B independently affects D (flip B → flip D) |
| 4 | T | T | F | F | C independently affects D (flip C → flip D) |

N+1 cases (N = number of conditions). That is the theoretical minimum test set for MC/DC. You don't need to enumerate all 2³=8 combinations, but you have proven that each condition can cast a "veto." That is the screening precision a software immune system should have.

You look once more at the structural coverage table in ISO 26262-6 (structural coverage metrics at the software unit level):

| Coverage method | ASIL A | ASIL B | ASIL C | ASIL D |
|----------|--------|--------|--------|--------|
| Statement coverage | ++ | ++ | + | + |
| Branch coverage | + | ++ | ++ | ++ |
| MC/DC | + | + | + | ++ |

Notice the subtlety of this table: ASIL D requires MC/DC as "++" (highly recommended), while statement coverage actually drops to "+" (recommended). Why? Because once you do MC/DC, statement coverage is satisfied automatically: the former is a strict superset of the latter. ASIL A is the opposite: statement coverage is "++" and MC/DC is only "+" — for lower safety levels, the extra cost of MC/DC may not be worth it. This is the pragmatic side of ISO 26262: safety investment should match the risk level, not be as strict as possible everywhere.

## Test derivation methods: the path from requirements to test cases

With coverage criteria in hand, how do you generate test cases? ISO 26262-6 gives recommended levels for the methods used to derive software unit test cases:

| Method | ASIL A | ASIL B | ASIL C | ASIL D |
|------|--------|--------|--------|--------|
| Requirements analysis | ++ | ++ | ++ | ++ |
| Equivalence class generation | + | ++ | ++ | ++ |
| Boundary value analysis | + | ++ | ++ | ++ |
| Error guessing | + | + | + | + |

Requirements analysis is a clean sweep of "++": at every ASIL, you must derive tests from requirements. This is the foundation of safety testing. Testing is not to prove the code "runs"; it is to prove the code "satisfies the safety requirements." If a safety requirement has no corresponding test case, that requirement has never been verified, and the safety argument has a logical break.

Equivalence class generation and boundary value analysis are "++" at ASIL B/C/D. Picture testing a steering angle sensor: the input range is [-540°, +540°]. Equivalence partitioning tells you to test one valid class (a representative value inside the normal range) and the invalid classes (below -540°, above +540°). Boundary value analysis then requires testing -540°, +540°, -541°, and +541°: behavior at the boundaries is where errors concentrate. Every veteran engineer has been tortured by an off-by-one bug. Boundary value analysis is built to hunt exactly those bugs.

Error guessing is the only method that is "+" at every ASIL. It relies on the tester's experience and intuition: "I think this could overflow here," "if an interrupt arrives here, could it deadlock?" It cannot be systematized, so it cannot be the main basis, but its value is undeniable: the best test engineers often find defects that requirements analysis and equivalence partitioning both missed.

## Test levels: unit → integration → architecture → vehicle — four layers of immune defense

Picture the above as four lines of defense in the immune system:

**First line of defense: software unit testing (ISO 26262-6)**

This is the most microscopic level. Skin and mucous membranes: the first physical barrier against pathogens. You take each function and each module on its own, feed it carefully constructed inputs, and check whether the output matches the detailed design exactly. This is where you verify MC/DC. It is also where you find pointer overruns, division by zero, integer overflow, dead code, and other low-level but lethal bugs.

For ASIL D unit testing you must:
- Achieve MC/DC for every safety-related software unit (++)
- Achieve branch coverage for every safety-related unit (++)
- Derive test cases from requirements analysis (++)
- Derive test cases with equivalence classes and boundary value analysis (++)

**Second line of defense: software integration testing (ISO 26262-6)**

This is the innate immunity level. Macrophages and neutrophils. They don't target a specific pathogen, but they can recognize "this is not normal." You assemble tested units into subsystems and verify their interfaces, data flow, and timing. The goal here is not to verify logic inside functions but to verify that "the data module A passes to module B is correct under every scheduling scenario," that "synchronization between tasks does not deadlock," and that "access to shared memory is mutually exclusive."

ISO 26262 gives recommended methods for integration verification:

| Method | ASIL A | ASIL B | ASIL C | ASIL D |
|------|--------|--------|--------|--------|
| Requirements-based testing | ++ | ++ | ++ | ++ |
| Fault injection | + | + | ++ | ++ |
| Resource usage assessment | ++ | ++ | ++ | ++ |

Fault injection is the signature method of integration testing. You deliberately make one module return an error code and watch how another module reacts: graceful degradation? A crash? Or silent failure (the most dangerous kind)? For ASIL C/D, fault injection is "++." You must systematically verify how every safety mechanism behaves when faced with faulty inputs.

Resource usage assessment is also a clean sweep of "++." In embedded systems, stack overflow, heap exhaustion, and excessive CPU load are the most insidious killers. You must measure worst-case resource consumption in integration testing and make sure a safety margin remains.

**Third line of defense: architectural coverage (ISO 26262-6)**

This is the adaptive immunity level. T cells and B cells. They target specific antigens and deliver precision strikes. Architectural coverage doesn't look at code inside functions; it looks at whether the software architecture's "skeleton" is complete:

| Method | ASIL A | ASIL B | ASIL C | ASIL D |
|------|--------|--------|--------|--------|
| Function coverage | + | + | ++ | ++ |
| Call coverage | + | + | ++ | ++ |

Function coverage: has every function in the architecture been called? Call coverage: has every function-call relationship defined in the architecture been exercised in testing? You might wonder: unit testing and integration testing were both done, so how could a function never be called? The answer: interrupt service routines (ISRs), error handlers, and fallback paths in degraded modes. These "rare paths" are often missed in normal testing. Architectural coverage requires you to verify them specifically.

**Fourth line of defense: vehicle integration testing (ISO 26262-4)**

This is immune memory. After vaccination, the body remembers the antigen: the next encounter produces a faster, stronger response. Vehicle-level testing verifies safety mechanisms in the most realistic setting: not a simulator, not an HIL bench, but a real vehicle driving on a real road.

The vehicle-level verification table in ISO 26262-4 (methods for verifying functional safety requirements at the vehicle level) is terse and firm:

| Method | ASIL A | ASIL B | ASIL C | ASIL D |
|------|--------|--------|--------|--------|
| Requirements-based testing | ++ | ++ | ++ | ++ |
| Fault injection | ++ | ++ | ++ | ++ |
| Long-term testing | ++ | ++ | ++ | ++ |
| User testing | ++ | ++ | ++ | ++ |

Four clean sweeps of "++". Every ASIL gets "++". Vehicle-level testing accepts no "recommended": every item is "highly recommended." Why? Because no matter how thorough your lab simulations are, the real world's complexity and randomness always have a surprise for you: noise patterns on the CAN bus, condensation from temperature cycling, users operating switches in ways you never imagined. These scenarios cannot be enumerated in design and must be exposed by vehicle testing.

Long-term testing (durability testing) deserves a separate discussion. It does not verify "whether the function is correct." It verifies "how long correctness holds under continuous stress." A car is driven for 15 years. Fifteen years of vibration, temperature change, electromagnetic interference, and accumulated software state. You cannot simulate that in unit tests. You have to run the mileage.

## Summary

1. Test depth progresses: statement coverage → branch coverage → MC/DC, each layer covering the blind spots of the one before.
2. Tests are derived by four methods: requirements analysis, equivalence partitioning, boundary value analysis, and error guessing.
3. From unit testing to vehicle testing, four lines of defense each have their own coverage criteria and test methods.
4. The four "++" items of vehicle testing remind us: verification on real roads cannot be skipped.
