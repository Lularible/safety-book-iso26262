# 2.12 Software Unit Design and MISRA C: Taming the C Language


## Scenario

There are two windows open on the screen in front of you. On the left is a piece of C code you wrote last month. It's full of a young engineer's "cleverness": dynamic allocation, function pointers jumping around, two gotos used to break out of nested loops fast. It passed unit testing, and the unit tests covered every branch.

On the right is the same functionality, rewritten to MISRA C:2012. No dynamic memory, no recursion, no goto, one return per function. It looks more verbose, more "clumsy."

The product manager walks past, glances at it, and says: "The code on the right is slower, isn't it?"

You say: "Yes. About 3% slower."

The product manager asks: "Then why change it?"

You're silent for three seconds. This isn't a performance problem. This is: the code on the left **cannot be analyzed**. It "runs," but you cannot prove to anyone that it is safe. The code on the right can be examined by static analysis tools, measured by structural coverage tools, and laid open in front of an auditor, line by line.

The software unit design principles table in ISO 26262-6 is about exactly this.


## Lay out both versions

### Version A: "normal C"

```c
/* Steering angle calculation — "normal C" style */
#include <stdlib.h>
#include <string.h>

typedef struct {
    float *raw_samples;
    int count;
    float offset;
} AngleCalc_t;

static AngleCalc_t *g_calc = NULL;

float calc_steering_angle(void) {
    if (g_calc == NULL) {
        g_calc = (AngleCalc_t *)malloc(sizeof(AngleCalc_t));
        g_calc->raw_samples = (float *)malloc(100 * sizeof(float));
        g_calc->count = 0;
        g_calc->offset = 0.0f;
    }
    
    float raw = read_sensor();
    
    if (g_calc->count >= 100) {
        goto filter_done;
    }
    g_calc->raw_samples[g_calc->count++] = raw;
    
filter_done:
    float sum = 0.0f;
    int valid = 0;
    for (int i = 0; i < g_calc->count; i++) {
        /* Simulation: sometimes we need to skip outliers */
        if (g_calc->raw_samples[i] > 900.0f || 
            g_calc->raw_samples[i] < -900.0f) continue;
        sum += g_calc->raw_samples[i];
        valid++;
    }
    
    return (valid > 0) ? (sum / valid - g_calc->offset) : 0.0f;
}
```

This code compiles, runs, and spent an afternoon on the test bench without a single problem. But let's count which red lines from the software unit design principles table it crosses:

1. **One entry, many exits (violates the one-entry-one-exit principle)**: the function has two implicit return paths (the 0.0f in the if condition and the return at the end) plus goto jump logic. In structural coverage analysis this creates path combinations that are nearly impossible to trace.

2. **Dynamic objects (violates the no-dynamic-objects principle)**: memory is allocated on the heap with malloc. In a real-time embedded system, malloc's behavior is non-deterministic. It can return NULL (allocation failure caused by fragmentation). Your code does call malloc in the if (g_calc == NULL) branch, but what if malloc fails mid-run because of fragmentation? You don't handle it.

3. **No initialization (violates the variable-initialization principle)**: the local variables sum and valid are declared without initialization. Compilers usually don't zero stack variables; their initial value is whatever stack data the previous call left behind — an "invisible" but real non-deterministic input.

4. **Global variables (violates the avoid-global-variables principle)**: g_calc is a global pointer. Any other function (including those QM partition functions, if someone linked them by mistake) can read or even overwrite it.

5. **Function-pointer-equivalent behavior (violates the restricted-use-of-pointers principle)**: the dynamically allocated array is accessed indirectly through a pointer with no bounds check, and the increment of count has no upper limit.

6. **Hidden data flow (violates the no-hidden-data-flow principle)**: count carries state from the previous call. It's a state machine implemented through a global variable, but its state transitions are not modeled explicitly, so tests and verification struggle to enumerate all states.

7. **Unconditional jumps (violates the no-unconditional-jumps principle)**: goto filter_done breaks the linear control flow.

8. **Implicit type conversions (violates the no-implicit-type-conversions principle)**: the return type of read_sensor() is unclear, and assigning it to float may involve an implicit conversion.

**A C file of fewer than 50 lines, and it violates eight of the ten principles.** It isn't malicious. It's written in "normal" C style. The problem is that in an ASIL D world, **"normal C" is malicious code.**


### Version B: MISRA C:2012

Now look at the right side: the same functionality, rewritten to MISRA C:2012 (the software unit design principles table in ISO 26262-6 explicitly states that MISRA C covers many of those principles):

```c
/* PRQA S 0492, 3450 EOF */
/* Steering angle calculation — MISRA C:2012 style */

#define ANGLE_SAMPLE_SIZE   16U
#define ANGLE_MAX_VALID     900.0f
#define ANGLE_MIN_VALID     -900.0f
#define ANGLE_INVALID       0.0f

typedef enum {
    FILTER_INIT,
    FILTER_FILLING,
    FILTER_READY
} FilterState_en;

typedef struct {
    float32 sample_buffer[ANGLE_SAMPLE_SIZE];
    uint8   write_index;
    uint8   sample_count;
    float32 offset;
    FilterState_en state;
} AngleFilter_st;

static AngleFilter_st s_filter;

FUNC(void, ANGLECALC_CODE) AngleFilter_Init(void)
{
    uint8 i;
    
    s_filter.write_index   = 0U;
    s_filter.sample_count  = 0U;
    s_filter.offset        = 0.0f;
    s_filter.state         = FILTER_INIT;
    
    for (i = 0U; i < ANGLE_SAMPLE_SIZE; i++)
    {
        s_filter.sample_buffer[i] = 0.0f;
    }
}

FUNC(float32, ANGLECALC_CODE) AngleFilter_Update(float32 raw_angle)
{
    float32 sum           = 0.0f;
    float32 average       = 0.0f;
    uint8   valid_count   = 0U;
    uint8   i;

    if (s_filter.state == FILTER_INIT)
    {
        s_filter.state = FILTER_FILLING;
    }

    if (s_filter.write_index < ANGLE_SAMPLE_SIZE)
    {
        s_filter.sample_buffer[s_filter.write_index] = raw_angle;
        s_filter.write_index++;
    }
    else
    {
        s_filter.write_index = 0U;
    }

    if (s_filter.sample_count < ANGLE_SAMPLE_SIZE)
    {
        s_filter.sample_count++;
        s_filter.state = FILTER_FILLING;
    }
    else
    {
        s_filter.state = FILTER_READY;
    }

    if (s_filter.state == FILTER_FILLING)
    {
        average = raw_angle;
    }
    else
    {
        sum = 0.0f;
        valid_count = 0U;

        for (i = 0U; i < ANGLE_SAMPLE_SIZE; i++)
        {
            if ((s_filter.sample_buffer[i] >= ANGLE_MIN_VALID) &&
                (s_filter.sample_buffer[i] <= ANGLE_MAX_VALID))
            {
                sum += s_filter.sample_buffer[i];
                valid_count++;
            }
        }

        if (valid_count > 0U)
        {
            average = (sum / (float32)valid_count) - s_filter.offset;
        }
        else
        {
            average = ANGLE_INVALID;
        }
    }

    return average;
}
```

Compare compliance principle by principle:

- **One entry, one exit**: each function has exactly one return statement. Control flow does not jump or goto. The state machine is modeled with an explicit enum type, and every state transition is clear and traceable.

- **No dynamic objects**: all memory is allocated statically at compile time. sample_buffer is a static array of 16 floats. There is no malloc and no non-determinism from run-time memory allocation. And because there is no dynamic memory, the "allocation failure" failure mode does not exist.

- **Variable initialization**: every local variable is explicitly initialized at declaration. sum, average, valid_count, i: each starts from a known value.

- **Restricted use of pointers**: no pointers at all. Data is reached only through array indices and static struct members. Cortex-R5 addressing has no performance difference between writing *(ptr++) and array[index]. But the address range of the latter can be fully verified at compile time by static analysis tools.

- **Avoid global variables**: although s_filter is at file scope, it is declared static, so its linker-level scope is limited to the current translation unit and external code cannot reach it. In an AUTOSAR context this is usually restricted further by the RTE encapsulation mechanism: every SWC has its own RTE ports, and data flow is normalized at the architecture level.

- **No implicit type conversions**: the explicit cast (float32)valid_count. MISRA requires every conversion to be either an assignment of the same type or an explicitly written conversion.

- **No hidden data flow**: all state is represented explicitly in the AngleFilter_st struct. Every state transition has a clear entry condition and exit condition. There is no pattern of "quietly change a global counter and later read it through a conditional expression."

- **No unconditional jumps**: no goto. No setjmp/longjmp. Control flow is only if/else and for, and the number of paths is finite and provable.

- **No recursion**: every function is implemented iteratively, with no recursive calls, so the call stack depth is fully determined at compile time.

**This isn't "written more conservatively." This is "written so it can be analyzed."**


## MISRA C and the software unit design principles

The software unit design principles table in the software part of ISO 26262 lists the principles for software unit design and implementation: ten in total. In the notes after the table, the standard **explicitly cites MISRA C** as a coding guideline that can satisfy many of those principles (in the standard's own words, for the C language "MISRA C covers many of the principles listed" in that table). This is no coincidence: MISRA C:2012 has 143 rules and 16 directives, graded by how strictly they apply, and it covers almost every area the table cares about.

The core idea of MISRA is not mysterious at all. One sentence covers it: **eliminate every behavior in C that is undefined, implementation-dependent, or impossible to analyze statically.** It doesn't care whether "this code runs." It cares whether "this code can be **proven** to always run as intended."

One example to help you see the link between "undefined behavior" and the principles:

```c
/* Dangerous: function argument evaluation order is undefined */
result = calc_a(x++) + calc_b(x);
```

The C standard does not specify the evaluation order of function arguments: the compiler may evaluate calc_a first or calc_b first. That means x++ may run before or after calc_b(x). The compiler's choice changes the result, and nothing in your code says which one you meant. MISRA C Rule 13.2 explicitly forbids this pattern.

Another example:

```c
/* Dangerous: signed integer overflow is undefined behavior */
int32_t angle = 2147483640;
angle = angle + sensor_offset;
```

If sensor_offset is greater than 7, angle overflows. The C standard says signed integer overflow is undefined behavior: the compiler may delete all code that depends on the overflow value. It isn't "you get a wrong result." It's "the behavior of the whole program is no longer constrained by the standard."

**These are not bugs from "writing it carelessly." They are language features that the C standard allows in normal situations but that must not appear in safety-critical code.** MISRA switches all of them off. What MISRA gives you is a smaller C language subset whose behavior is fully determined.


## Software unit verification: verification methods and structural coverage

After the code is written, you need to verify it. Not by "ran a few test cases and nothing crashed." The software unit verification table in ISO 26262-6 lists, by ASIL, the methods you must perform:

| Method | ASIL A | ASIL B | ASIL C | ASIL D |
|------|--------|--------|--------|--------|
| Static code analysis | ++ | ++ | ++ | ++ |
| Fault injection testing | + | + | + | ++ |
| Resource usage testing | + | + | + | ++ |

**"++" means "highly recommended"; "+" means "recommended."**

A few notes:

**Static code analysis (++ for every ASIL)**: this is not the "unused variable" check in your IDE. It's automated compliance checking against MISRA C rules: the tool checks all 143 mandatory rules one by one and tells you which line violates Rule X.X. PRQA (QA-C) is a representative tool of this kind. It generates a report item for every violation, and you must supply a deviation for each report item explaining why this violation is allowed.

**Fault injection testing (++ at ASIL D)**: you inject errors into the code, for example by setting sensor_offset to an abnormal value or forcing sample_count to an unreasonable number. Then you observe whether the system responds safely (enters the safe state or degrades). This isn't "see whether the code has bugs." It's "see how well the code takes a beating."

**Resource usage testing (++ at ASIL D)**: stack depth analysis and execution time analysis (WCET). You need to prove that running this function will not overflow the stack and will not exceed the CPU time budget. For ASIL D you need measured worst-case execution time: not the average, but the theoretical maximum that can occur.


## Structural coverage: ASIL D = branch + MC/DC

Once the unit tests are written, you still have to measure structural coverage, using the structural coverage table in ISO 26262-6:

| Coverage metric | ASIL A | ASIL B | ASIL C | ASIL D |
|---------|--------|--------|--------|--------|
| Statement coverage | ++ | ++ | + | + |
| Branch coverage | + | ++ | ++ | ++ |
| MC/DC | + | + | + | ++ |

ASIL D requires MC/DC (Modified Condition/Decision Coverage).

Many people think MC/DC is hard. The concept is actually simple:

For if (A && B), to satisfy MC/DC you need to show:
- Changing A independently affects the whole decision (with B held true, changing A changes the result)
- Changing B independently affects the whole decision (with A held true, changing B changes the result)

That means you need at least three test cases: (true, true), (false, true), (true, false). Three, not four. MC/DC cares not about all combinations (that would be the full truth-table requirement) but about the **independent effect** of each condition on the decision.

Why does ASIL D require MC/DC? Because statement coverage and branch coverage **can miss logic defects**. Look at this example:

```c
if ((speed > 5) && (gear == GEAR_DRIVE)) {
    enable_steering_assist();
}
```

- Statement coverage: one test case (speed=10, gear=GEAR_DRIVE) is enough to cover enable_steering_assist()
- Branch coverage: two cases are needed: (speed=10, gear=GEAR_DRIVE) and (speed=0, gear=GEAR_PARK)
- MC/DC: three cases are needed, and speed>5 must independently determine the result. So you need (speed=10, gear=GEAR_DRIVE) and (speed=0, gear=GEAR_DRIVE), where gear stays at GEAR_DRIVE and speed changes to prove speed's independent effect.

**But what a single MC/DC analysis can reveal: what if the short-circuit evaluation of `gear == GEAR_DRIVE` hides a bug when speed<=5?** Only by analyzing each condition's influence independently can you be sure that "this logic has no dead conditions, and every condition really matters."


## Summary

1. The software unit design principles table in ISO 26262-6 defines ten basic principles for ASIL software unit design: design principles (modularity/encapsulation/simplicity), one entry and one exit, no dynamic objects, variable initialization, restricted pointers, avoid global variables, no implicit type conversions, no hidden data flow, no unconditional jumps, no recursion.
2. The standard explicitly cites MISRA C:2012 as a coding guideline covering these principles.
3. At ASIL D, branch coverage and MC/DC are both marked "++" (highly recommended), and statement coverage is "+" (recommended).
