# 5.4 The Safety Queue: A Ring Buffer with Structural Integrity Checks

## Scenario: The Silent Data Break

Your colleague was reviewing the black-box data from a test vehicle and found something odd: the CAN log showed that among the ABS controller's four wheel-speed signals, the left rear wheel's data suddenly went to all zeros at a certain moment, stayed that way for a full 17 seconds, then returned to normal. During those 17 seconds the car went over a speed bump, and the jolt briefly broke the left rear wheel-speed sensor's wiring harness.

The physical fault isn't scary; the ABS software has dedicated diagnostic logic for an open sensor circuit. What really chilled your colleague was this: **the ring buffer that caches the wheel-speed signals handed out, after the sensor recovered, not the correct post-recovery value but the stale data left over from before the fault.**

The root cause was a software defect: when the sensor returned an error code because of the open circuit, the task skipped the enqueue operation entirely. But the buffer's head pointer had already moved forward in the previous operation, so a "free slot" in the buffer was wrongly marked as "contains valid data." When the sensor recovered and new data came in, the 17-second gap left consumer and producer pointers completely out of sync.

**The memory buffer is one of the weakest links in safety**, not because the algorithm is complex but because it's a "state holder." When the memory holding the state is damaged, nothing checks it.

Today you'll build a safety ring queue that can check its own structural integrity: `safe_queue`.

## Design Philosophy: Every Entry Carries a "Passport"

An ordinary ring buffer looks like this:

```c
struct ring_buffer {
    uint8_t data[CAPACITY][ELEMENT_SIZE];
    int head, tail, count;  // three integers that are very easy to corrupt
};
```

If a wild pointer overwrites any of head, tail, or count — extremely common in bare-metal systems without an MPU — the whole queue's logic is ruined: head>tail but count=0, tail>CAPACITY but count=CAPACITY-1... Impossible metadata combinations trigger no checks at all, and the data is delivered "legally" to the wrong place.

safe_queue's defense strategy: **attach a magic number and a CRC check to every data entry, so each cell of the queue can verify its own identity.**

```c
typedef struct {
    uint32_t magic;       /* 0xDEADBEEF — "I am a valid queue entry" */
    uint16_t length;      /* valid data length */
    uint8_t  data[32];     /* payload */
    uint8_t  entry_crc;   /* CRC8(magic || length || data) */
} safe_queue_entry_t;
```

This is like issuing a "passport" to every data entry: magic is the watermark (proof that this is a real queue entry, not random RAM garbage), and entry_crc is the tamper seal. When the consumer takes data, it checks the passport before memcpy.

Note the CRC's coverage: `magic || length || data`. Putting magic first mainly affects each field's positional weight in the CRC; it adds no extra error-detection power. What matters is that it's inside the CRC input range. The code still compares magic explicitly before the CRC comparison, so the two failure classes are reported separately: a magic mismatch means the slot isn't a valid entry at all (returns `SAFE_MAGIC_ERROR`); magic matches but the CRC doesn't means the entry structure is intact but its contents were changed (returns `SAFE_CRC_MISMATCH`).

## All the Members of the Data Structure

```c
#define SAFE_QUEUE_MAX_ENTRIES  8
#define SAFE_QUEUE_DATA_SIZE    32

typedef struct {
    safe_queue_entry_t entries[SAFE_QUEUE_MAX_ENTRIES];
    uint32_t           head;      /* producer write position */
    uint32_t           tail;      /* consumer read position */
    uint32_t           count;     /* current entry count */
} safe_queue_t;
```

**Why uint32_t instead of the more suitable size_t?** Because this is a teaching framework, and I deliberately use fixed-width integers (uint32_t) to mimic the choice you'd make in an embedded environment. The ring capacity is the compile-time constant 8 (`SAFE_QUEUE_MAX_ENTRIES`); an 8-bit index would do. Choosing uint32_t wastes a few bytes, but it buys head, tail, and count the same width on every platform, so the layout doesn't shift when the queue is placed in cross-core shared memory.

**Why is there no CRC field for the queue metadata?** It's a deliberate simplification: the teaching version puts verification at entry granularity. The module also exports a function that computes a CRC8 over head, tail, and count on demand, splitting the three 32-bit integers little-endian into 12 bytes and feeding them through the same CRC8 table. But the struct has no field to store the result, and validate never calls it. The function's output is only a diagnostic snapshot; there's no reference value to compare against. When head is corrupted, validate catches it by walking count entries from head and hitting the magic of an empty slot.

## Enqueue: Wrap the Entry and Write the CRC

```c
safe_status_t safe_queue_add(safe_queue_t *q, const uint8_t *data, size_t len)
{
    /* Preconditions */
    if (q->count >= SAFE_QUEUE_MAX_ENTRIES) return SAFE_QUEUE_FULL;
    if (len > SAFE_QUEUE_DATA_SIZE) return SAFE_ERROR;

    /* Locate the tail slot */
    safe_queue_entry_t *entry = &q->entries[q->tail];

    /* Write the data */
    entry->magic  = SAFE_QUEUE_MAGIC;   /* 0xDEADBEEF */
    entry->length = (uint16_t)len;
    if (len > 0) memcpy(entry->data, data, len);

    /* Compute the enqueue CRC */
    uint8_t crc_buf[sizeof(uint32_t) + sizeof(uint16_t) + SAFE_QUEUE_DATA_SIZE];
    memcpy(&crc_buf[0], &entry->magic,  sizeof(uint32_t));
    memcpy(&crc_buf[4], &entry->length, sizeof(uint16_t));
    if (len > 0) memcpy(&crc_buf[6], entry->data, len);
    entry->entry_crc = safe_crc8_compute(crc_buf, 6 + len);

    /* Update the queue metadata */
    q->tail = (q->tail + 1) % SAFE_QUEUE_MAX_ENTRIES;
    q->count++;

    return SAFE_OK;
}
```

Note the temporary buffer `crc_buf` used in the CRC computation. Why not compute the CRC directly over `entry`? Because the `entry_crc` field is itself inside `safe_queue_entry_t`. If you compute the CRC starting at `entry`'s address, the computation includes the not-yet-determined `entry_crc` field, creating a circular dependency. The temporary buffer rearranges the fields that need CRC coverage (magic, length, data) and excludes entry_crc itself.

**PRODUCTION note:** In real embedded code, this memcpy into a temporary buffer can be handed to a scatter-gather CRC computation: many hardware CRC engines, paired with a DMA that supports scatter-gather, can splice the (magic, 4), (length, 2), and (data, len) segments into one computation without an intermediate copy. Whether a particular chip has that acceleration path is a matter for its datasheet; the only thing the repository can verify is this software implementation, which assembles first and computes once.

## Dequeue: The Passport Checkpoint

```c
safe_status_t safe_queue_get(safe_queue_t *q, uint8_t *data_out, size_t *len)
{
    if (q->count == 0) return SAFE_QUEUE_EMPTY;

    safe_queue_entry_t *entry = &q->entries[q->head];

    /* Check the passport: magic */
    if (entry->magic != SAFE_QUEUE_MAGIC) {
        return SAFE_MAGIC_ERROR;
    }

    /* Check the passport: recompute the CRC and compare */
    uint8_t crc_buf[sizeof(uint32_t) + sizeof(uint16_t) + SAFE_QUEUE_DATA_SIZE];
    memcpy(&crc_buf[0], &entry->magic,  sizeof(uint32_t));
    memcpy(&crc_buf[4], &entry->length, sizeof(uint16_t));
    if (entry->length > 0) memcpy(&crc_buf[6], entry->data, entry->length);
    uint8_t computed = safe_crc8_compute(crc_buf, 6 + entry->length);
    if (computed != entry->entry_crc) {
        return SAFE_CRC_MISMATCH;
    }

    /* Passed: copy the data, clear the entry, update the pointers */
    if (entry->length > 0) memcpy(data_out, entry->data, entry->length);
    *len = entry->length;
    memset(entry, 0, sizeof(*entry));  /* zero it to prevent stale-data leakage */
    q->head = (q->head + 1) % SAFE_QUEUE_MAX_ENTRIES;
    q->count--;
    return SAFE_OK;
}
```

`memset(entry, 0, sizeof(*entry))` isn't just good programming practice. In a safety-critical system, **each piece of data should exist only in a context where it can be used correctly.** If the slot isn't cleared after dequeue, stale data stays behind:
1. Task A writes sensitive data (say, a cryptographic key) into the queue, with a length close to the slot's 32-byte limit
2. Task B takes it; `get()` zeroes the whole entry before returning. Skip that step, and the key stays in the slot
3. A shorter message is enqueued next; `add()` overwrites only the first length bytes, the tail keeps the old contents, and the new entry's CRC also covers only length bytes
4. Any read that bypasses the length field (a diagnostic dump, memory-image forensics, an out-of-bounds copy) can scoop up the tail of the previous message

This structure sits in the static global area and doesn't overlap task stacks; the dequeue API also copies only length bytes. But zeroing is still necessary: it closes the residual channel that bypasses the length field. The teaching code is tiny, but this is a habit you should build in production.

## Batch Validation: safe_queue_validate()

When the system suspects memory corruption (for example, the ECC controller reported a correctable error), you need to sweep the whole queue:

```c
safe_status_t safe_queue_validate(const safe_queue_t *q)
{
    uint32_t cnt = q->count;
    uint32_t idx = q->head;
    for (uint32_t i = 0; i < cnt; i++) {
        const safe_queue_entry_t *entry = &q->entries[idx];
        if (entry->magic != SAFE_QUEUE_MAGIC) return SAFE_MAGIC_ERROR;
        uint8_t crc_buf[6 + SAFE_QUEUE_DATA_SIZE];
        memcpy(&crc_buf[0], &entry->magic,  sizeof(uint32_t));
        memcpy(&crc_buf[4], &entry->length, sizeof(uint16_t));
        if (entry->length > 0) memcpy(&crc_buf[6], entry->data, entry->length);
        uint8_t computed = safe_crc8_compute(crc_buf, 6 + entry->length);
        if (computed != entry->entry_crc) return SAFE_CRC_MISMATCH;
        idx = (idx + 1) % SAFE_QUEUE_MAX_ENTRIES;
    }
    return SAFE_OK;
}
```

Core logic: **from head, walk count slots** (not the whole entries array). This ensures only entries "the queue thinks are in use" get checked. If head is corrupted to point at garbage, validate immediately detects a magic mismatch at the first slot. If count is corrupted to an unreasonable value (say count=255 when there are really 3 entries), validate walks into empty slots, where magic was zeroed at init and is likewise not 0xDEADBEEF, so the check fails all the same.

## Fault Models and Detection

Let's use the test code to verify each fault scenario:

**Normal operation test**:
```c
safe_queue_add(&q, "alpha", 6);
safe_queue_add(&q, "beta", 5);
safe_queue_add(&q, "gamma", 6);
// dequeue in FIFO order
safe_queue_get(&q, buf, &len);  // buf = "alpha" ✓
safe_queue_get(&q, buf, &len);  // buf = "beta"  ✓
safe_queue_get(&q, buf, &len);  // buf = "gamma" ✓
```

**Magic corruption test**:
```c
safe_queue_add(&q, "sensitive_data", 15);
fault_queue_magic_corrupt(&q, 0);   // → entry[0].magic = 0xBAADF00D
safe_queue_get(&q, buf, &len);      // → SAFE_MAGIC_ERROR ✓
```

**CRC corruption test**:
```c
safe_queue_add(&q, "Q_FAULT", 8);
fault_queue_crc_corrupt(&q, last_entry_index);  // → entry_crc ^= 0x01
safe_queue_get(&q, buf, &len);                   // → SAFE_CRC_MISMATCH ✓
```

**Metadata corruption test**:
```c
safe_queue_add(&q, "AAAA", 5);
safe_queue_add(&q, "BBBB", 5);   // head=0, tail=2, count=2
fault_queue_metadata_corrupt(&q);  // → head+=3 (head=3)
safe_queue_validate(&q);           // → SAFE_MAGIC_ERROR ✓
// head=3 points at an empty slot, zeroed as a whole at init, magic != 0xDEADBEEF
```

**Full-queue rejection test**:
```c
for (int i = 0; i < SAFE_QUEUE_MAX_ENTRIES + 2; i++) {
    st = safe_queue_add(&q, &i, sizeof(i));
}
// the first SAFE_QUEUE_MAX_ENTRIES succeed; the last 2 return SAFE_QUEUE_FULL ✓
```

## Working with E2E Protection

Here's an easily overlooked design point: **E2E protects message content; the safety queue protects the storage structure.** The two aren't redundant.

Consider this data flow:
```
Sensor → E2E Protect() → [CRC|Ctr|DID|payload] → safety queue Add() → [magic|len|data|entry_crc]
```

The data passes through two layers of protection:
1. The E2E layer verifies "is this message from the right sensor, and is its content intact?"
2. The queue layer verifies "has this storage slot itself been affected by RAM damage?"

If you rely only on E2E protection and don't protect the queue structure, two kinds of faults lead to different outcomes:
- The queue's head pointer is corrupted and points at an empty slot or garbage memory → the bytes retrieved have neither a valid magic nor a computable CRC, the queue layer reports MAGIC_ERROR on the spot, and the E2E layer never gets a chance to see the data
- The head pointer is corrupted and points at a structurally intact but stale message → both queue-layer checks pass (magic present, CRC correct). The only thing left that can stop it is E2E's counter freshness, and that check works only when the staleness falls within 1 to 7 values. At a staleness of 8, the modulo-16 difference is exactly 8, so it's accepted as 8 steps forward; a few more and it wraps back to 1–7, again mistaken for a new message. That's also why production implementations hang an extra layer of message-age and timeout monitoring off the counter

**The deep principle behind the check order:** `get()` checks magic before CRC. That order differs from E2E's CRC→DataID→Counter. The magic check here is a "type check." If the data isn't even a queue entry (magic mismatch), there's no point computing a CRC. That's an optimization, but more importantly it's semantically correct: **verify identity first, then content**.

## Summary

1. Every safety-queue entry carries a magic number (0xDEADBEEF) and its own entry_crc (covering magic + length + data), giving self-checking at the single-entry level.
2. `safe_queue_get()` checks magic (identity) before CRC (content). The order is the reverse of E2E's because the entry-level magic check is a lighter-weight pre-check.
3. Zeroing with `memset` after dequeue prevents stale-data leakage. It embodies the safety-critical principle that "each piece of data exists only in a context where it is used correctly."
4. `safe_queue_validate()` walks count entries starting from head, which indirectly covers head and count (tail isn't on the walk path, and the struct has no field holding a metadata checksum). A pointer corrupted to an empty slot triggers a magic error immediately.
5. E2E protects message content; the safety queue protects the storage structure. They complement each other and neither is replaceable. The missing checksum field for queue metadata is a deliberate simplification: the module only exports an on-demand CRC8 function over head, tail, and count, with no reference value to compare against. A production system should, like industrial implementations, store a checksum covering the data buffer and the metadata in the struct, then recompute and compare it before every enqueue.
