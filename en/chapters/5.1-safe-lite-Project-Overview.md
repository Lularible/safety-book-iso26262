# 5.1 safe-lite Project Overview: A Teaching-Grade Safety Framework

## Scenario: A Machine Without an Immune System

At six in the evening, you're getting ready to leave when the phone rings. The production line supervisor's voice is anxious and hoarse: "The robot's third axis suddenly slammed into the safety fence at full speed. The operator nearly got hurt. There's nothing in the log — the controller ran wild for three seconds, then rebooted itself."

You hang up and stare at the ceiling. The control chain appears in your mind: sensor sampling → microcontroller computes PID → PWM drives the motor → encoder feedback. A three-stage closed loop, textbook design. But here's the question: **who supervises the supervisor itself?** If the microcontroller's program counter jumps to the wrong address because of a single SEU flip, your elegant PID algorithm doesn't help. If electromagnetic interference flips two bits in a sensor message on the CAN bus, your feedback loop is making correct decisions from wrong data.

This is where functional safety begins. It isn't about making the system "never fail." It's about pulling the system into a safe state before harm happens, at the moment it **has already failed**.

In this chapter you'll build a teaching-grade safety monitoring framework called **safe-lite**. It isn't a real industrial product. It runs on an x86 PC with Linux, uses timerfd to simulate a hardware watchdog, and uses CRC8 in place of a hardware CRC engine. Everything is "fake." But just as medical students practice surgical skills on simulators again and again, safe-lite's value lies here: **it builds the right neural pathways in your brain**, so that before you do real production work you understand "why these things are needed."

## The Immune-System Metaphor

If you compare an embedded system to the human body, then:

| Human body | Embedded system | Counterpart in safe-lite |
|------|-----------|---------------------|
| Heartbeat/pulse | Periodic task scheduling | **Watchdog** — a safety timer supervises every task's alive signal |
| Immune cells recognize "self/non-self" | Message source authentication | **E2E protection** — CRC + counter + DataID verify message integrity |
| Lymph nodes filter pathogens | Data-flow integrity | **Safety queue** — a ring buffer with structural checks |
| Deliberately injecting an inactivated virus (a vaccine) | Fault-injection testing | **Fault injector** — verifies the coverage of the safety mechanisms |

The human immune system has an elegant design: it doesn't try to repair every damaged cell. It recognizes what's abnormal and **isolates/eliminates** it. Your safety monitoring framework should do the same. You don't have to detect every possible fault, but you must **detect the faults that lead to danger**, and then bring the system to a safe state.

safe-lite is a four-layer immune structure designed around exactly this metaphor.

## Inside the Modules

### 4.1 Watchdog (safe_wdg): Multi-Slot Alive Supervision

A real hardware watchdog — on an automotive MCU, usually a down-counter peripheral in its own clock domain — resets the chip when it times out. On Linux we can't reset hardware directly, so we simulate the watchdog's timing with `timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK)` and build **multi-slot checkpoint supervision** on top of it.

```c
/* Each supervised task registers a "slot" */
safe_wdg_register_slot(&wdg, 0, "sensor_task",
    100,   /* deadline_ms: the sensor must signal every 100 ms */
    20,    /* tolerance_ms: 20 ms of extra delay allowed */
    3);    /* max_misses: 3 consecutive misses before a timeout */
```

Design points:
- **deadline + tolerance only set an upper bound.** This implementation has no check on the min-deadline side. Feeding the dog too fast won't be judged a failure; only the upper bound is strictly enforced (window mode is on this chapter's list of omissions).
- **max_misses avoids false positives.** A single jitter shouldn't trigger a timeout. This is similar to debouncing.
- **Each slot keeps its own time.** A stuck sensor shouldn't affect supervision of the communication task or any other module.

### 4.2 E2E Protection (safe_e2e): An ID Card and Tamper Seal for Messages

The AUTOSAR E2E Profile 1 specification uses CRC-8 plus a 4-bit counter. DataID is a 16-bit configuration value, and only one mode writes one of its nibbles onto the wire (industrial implementations also reserve 0xF as an error value, and the counter cycles from 0 to 14). safe-lite implements a simplified version:

```
+------+------+------------...------------+
| CRC8 | Ctr|DID |        payload         |
+------+------+------------...------------+
  byte0  byte1    byte2 ... byteN+1

CRC8 = safe_crc8_compute([DataID | Counter | payload])
```

**Each side keeps its own context (`safe_e2e_ctx_t`):**
- `data_id`: the message identity (0–15). Think of it as a TCP port number. The sender says "this is sensor data." If the receiver gets a packet labeled "diagnostic command," you can drop it immediately.
- `counter`: a 4-bit sequence number (0–15) that increments with every message sent. The receiver works out how many steps forward the received counter is from the last recorded value on the modulo-16 ring. It accepts only 1 to 8. A difference of 0 or more than 8 is a counter error. This blocks replay attacks.

**Why does the CRC cover DataID + Counter + payload?**
Because safe communication has to protect three things at once: the content is right (CRC), the sender is right (DataID), and the order is right (Counter). If the CRC covered only the payload, an attacker — or a fault — could change the DataID undetected. That's exactly the hole in many home-grown communication protocols.

### 4.3 Safety Queue (safe_queue): A Buffer That Checks Itself

An ordinary queue has no defense against memory corruption. Every entry in safe_queue carries:

```c
typedef struct {
    uint32_t magic;      // 0xDEADBEEF — memory integrity sentinel
    uint16_t length;     // valid data length
    uint8_t  data[32];    // payload
    uint8_t  entry_crc;  // CRC8(magic || length || data)
} safe_queue_entry_t;
```

**The magic number works like a filesystem superblock signature.** If a wild pointer damages the RAM region holding a queue entry, the magic won't happen to be 0xDEADBEEF, and `safe_queue_get()` catches the problem before handing out the data and returns SAFE_MAGIC_ERROR.

**entry_crc** then protects the payload's integrity. Even if the magic happens to survive, a bit flip in the payload still gets caught.

In addition, `safe_queue_validate()` walks from head through count occupied slots, checking each one's magic and entry_crc. It doesn't validate the queue metadata itself; the metadata CRC can only be computed on demand by a separate helper, because the struct holds no reference value to compare against. This is still useful when you suspect large-scale RAM damage, such as a DRAM retention failure caused by high temperature.

### 4.4 Fault Injection (fault_inject): The Vaccine Mechanism

The value of a safety mechanism isn't what it "can do." It's **how many kinds of faults it can detect**. Fault injection is the tool that quantifies that coverage. safe-lite declares seven injection functions in `fault_inject.h`. The table below picks the four most representative:

| Function | Physical phenomenon simulated | Module that detects it |
|------|---------------|-----------|
| `fault_bit_flip()` | SEU / α particle / neutron flip | E2E (CRC mismatch) |
| `fault_counter_reset()` | Unexpected ECU restart | E2E (counter error) |
| `fault_queue_magic_corrupt()` | Wild pointer / RAM damage | Safe Queue (magic error) |
| `fault_queue_metadata_corrupt()` | Race condition / ISR preemption | Safe Queue (magic error, reported by the validate walk) |

In section 5.5 we'll walk through each injection and its detection result.

## What We Deliberately Left Out

safe-lite is a **teaching tool**, not production code. It deliberately leaves out many mechanisms that a real system can't do without:

| Omitted | Why it's omitted | How a real functional safety project handles it |
|---------|---------|-------------------------------|
| **Hardware watchdog** | Linux user space can't reset the CPU | A WDOG peripheral on an independent clock source, configured with window mode and an error response (interrupt → reset) |
| **MPU/MMU memory protection** | Simplified memory model | The ARM Cortex-R MPU divides memory into OS/ASIL regions that can't encroach on each other |
| **Dual-core lockstep** | Needs specific hardware | Cortex-R5 dual-core lockstep (DCLS): two cores execute the same instructions and compare their outputs |
| **Full AUTOSAR E2E implementation** | Profile 1's 4-bit counter is enough at teaching scale | Production code can switch to E2E Profile 5: CRC-16, an 8-bit counter (max 0xFF), a 16-bit DataID that participates in the CRC implicitly, and a single-frame data length limit of 4 kB |
| **ASIL decomposition** | Purely conceptual; not covered here | Decompose redundant elements according to the decomposition schemes the standard allows (for example B(D)+B(D)), then argue independence with a dependent failure analysis. Sections 2.14 and 2.15 of this book cover this |
| **Watchdog window mode** | timerfd can't simulate "too fast is also a fault" | A hardware WDT accepts a kick only inside the window between two thresholds |
| **NVRAM fault log** | No persistent storage layer | Detected faults are written to NVRAM for the power-on self-test to read |

Our goal: **convey as much safety design intent as possible with as little code as possible.** When you meet `WdgM_CheckpointReached()` or `E2E_P01Check()` in a real AUTOSAR project, you'll already understand what they do and why they exist.

The essence of a safety monitoring framework is not "prevent faults." It's "detect the fault before it causes harm and enter a safe state." The distinction matters. Many engineers hear "functional safety" and think of redundancy, fault tolerance, voting. Those are means, not ends. The end is that when a fault occurs, the system behaves in a **predictable safe state**.

## Summary

1. safe-lite is a teaching-grade safety monitoring framework. On Linux x86 it uses timerfd to simulate a hardware watchdog and CRC8 to simulate a hardware CRC engine. Its four layers map to the human immune system.
2. The four modules each do one job: the watchdog supervises task liveness, E2E protects message integrity, the safety queue guards the storage structure, and fault injection verifies safety-mechanism coverage.
3. The design principle is "detect the fault before it causes harm and enter a safe state," not "prevent every fault."
4. Hardware watchdog, MPU memory protection, and dual-core lockstep are deliberately omitted so the chapter can focus on conveying the core intent of safety design.
5. The six .c files total 1,173 lines; with the headers and Makefile that's 1,426 lines. Zero external dependencies, zero compiler warnings, and all 11 tests pass.
