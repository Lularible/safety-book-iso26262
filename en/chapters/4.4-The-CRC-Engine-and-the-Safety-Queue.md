# 4.4 The CRC Engine and the Safety Queue: Mathematics Meets Engineering

## Scenario: When a Bit in RAM Is Hit by a Cosmic Ray

This is not science fiction: for every 1000 m of altitude, the neutron flux roughly doubles. On a mountain road at 3000 m, your ECU's SRAM holds steering-angle data coming from the sensor queue, including 12 historical samples. A single neutron hitting one SRAM bit can turn `0x1A3F` into `0x0A3F`, and the drive motor will execute a wrong angle off by 4096 units from the real value.

You already know how E2E protects data **in transit**. But what about data that has already reached the ECU and is parked in RAM? The CRC engine signs the data mathematically, Safety_Queue embeds the signature into the data structure, and the two locks together lock down every byte of the queue's RAM.

## 1. Crc_32.c: From Mathematical Definition to Engineering Code

Open `SafeLib/Crc/src/Crc_32.c`, 232 lines. First impression: a compile switch with three modes:

```c
#ifndef Crc_32_Mode
#define Crc_32_Mode 0
#endif

#if Crc_32_Mode == CRC_32_HARDWARE
#error "Crc_32_Mode is set to CRC_32_HARDWARE which isn't supported"
#endif
```

Arctic Core does not support hardware CRC acceleration (but leaves the interface). Two software modes:
- `CRC_32_RUNTIME`: bit-by-bit, used to verify the table
- `CRC_32_TABLE`: 256-entry precomputed table, a performance optimization

The IEEE-802.3 parameter definitions:

```c
#define Crc_32_StartValue    0xFFFFFFFFU
#define Crc_32_Polynomial    0x04C11DB7U
#define Crc_32_Xor           0xFFFFFFFFU
```

## 2. Runtime CRC: The Art of reflect

IEEE-802.3 CRC32 has a counterintuitive design: the data must first be reflected bit by bit, and the result is reflected too. Look at the implementation:

```c
static INLINE uint32 reflectResult(uint32 data)
{
    uint32 reflection = 0x00000000U;
    uint8 bit;
    uint32 tmpData = data;

    for (bit = 0; bit < 32; bit++) {
        if ((tmpData & 0x01U) != 0) {
            reflection |= (1UL << (31UL - bit));
        }
        tmpData = tmpData >> 1;
    }
    return reflection;
}

static INLINE uint8 reflectInData(uint8 data)
{
    uint8 reflection = 0x00;
    uint8 bit;
    uint32 tmpData = data;

    for (bit = 0; bit < 8; bit++) {
        if ((tmpData & 0x01U) != 0) {
            reflection |= (uint8)(1U << (7U-bit));
        }
        tmpData = (tmpData >> 1U);
    }
    return reflection;
}
```

`reflectResult` reverses a 32-bit input bit by bit: bit0→bit31, bit1→bit30, ... `reflectInData` reverses an 8-bit byte within itself: bit0→bit7, ... This is the preprocessing the LSB-first CRC algorithm requires, the opposite of the intuitive "divide from the high bit first".

The bit-by-bit CRC32:

```c
static uint32 calculateCRC32(const uint8* message,
    uint32 nBytes, uint32 start)
{
    uint32 remainder = reflectResult(start);
    uint8  bit;
    const uint32  topbit = 0x80000000U;

    if (message != NULL_PTR) {
        for (uint32 byte = 0; byte < nBytes; byte++) {
            uint32 reflectedData = reflectInData(*message);
            remainder ^= (reflectedData << 24u);
            message++;

            for (bit = 8; bit > 0; bit--) {
                if ((remainder & topbit) != 0) {
                    remainder = (remainder << 1u)
                        ^ Crc_32_Polynomial;
                }
                else {
                    remainder = (remainder << 1u);
                }
            }
        }
    }
    return reflectResult(remainder);
}
```

Algorithm flow:
1. **Reflect the start value** (`reflectResult(start)`)
2. For each byte: **reflect the input** → **move it to the high bits** → **XOR into the remainder**
3. 8 rounds of bit-by-bit: if the top bit is 1, shift left and XOR the polynomial; otherwise just shift left
4. **Reflect the final remainder** and return

These two modes are selected by a compile switch, and only one implementation is compiled into a given build. The bit-by-bit version runs 8 rounds of shift-and-XOR per byte, O(n×8) complexity, and the source comment states that its purpose is to cross-check the table implementation.

## 3. Table CRC: 256 Magic Numbers

In the configuration header, `CRC_32_TABLE` is annotated as the Default value, but the mode macro names this configuration writes for the two 32-bit options are all uppercase, while the source `#if` tests a mixed-case name. The two sides don't match, so neither the bit-by-bit nor the table branch gets compiled in; for 8-bit and 16-bit the macro names agree on both sides, so the configuration really does land on the table. The listing below follows the table implementation in the source: 256 `uint32` values precomputed (each group of 8 is one row of the table):

```c
uint32 Crc_CalculateCRC32(const uint8* Crc_DataPtr,
    uint32 Crc_Length, uint32 Crc_StartValue32,
    boolean Crc_IsFirstCall)
{
    uint32 crc = 0;
#if Crc_32_Mode == CRC_32_TABLE
    static const uint32 Crc_32_Tab[] = {
        0x00000000U,0x77073096U,0xEE0E612CU,0x990951BAU,
        0x076DC419U,0x706AF48FU,0xE963A535U,0x9E6495A3U,
        0x0EDB8832U,0x79DCB8A4U,0xE0D5E91EU,0x97D2D988U,
        0x09B64C2BU,0x7EB17CBDU,0xE7B82D07U,0x90BF1D91U,
        // ... 256 entries total ...
        0xB40BBE37U,0xC30C8EA1U,0x5A05DF1BU,0x2D02EF8D };
#endif

    if (Crc_DataPtr != NULL_PTR) {
        crc = (TRUE == Crc_IsFirstCall) ?
            Crc_32_StartValue :
            (Crc_StartValue32 ^ Crc_32_Xor);

#if Crc_32_Mode == CRC_32_TABLE
        for(uint32 byte = 0; byte < Crc_Length; byte++) {
            crc = ((crc >> 8) & 0x00FFFFFFU)
                ^ Crc_32_Tab[(crc ^ *Crc_DataPtr) & 0xFFU];
            Crc_DataPtr++;
        }
#endif
        crc = crc ^ Crc_32_Xor;
    }
    return crc;
}
```

A single line does the CRC update for one byte:

```c
crc = ((crc >> 8) & 0x00FFFFFFU) ^ Crc_32_Tab[(crc ^ *Crc_DataPtr) & 0xFFU];
```

This is the classic form of the CRC32 table algorithm: table index = `(crc XOR data_byte) & 0xFF`, new crc = `(crc >> 8) XOR table value`. O(n) complexity, one byte per iteration.

The `Crc_IsFirstCall` parameter is the key to continuous CRC computation: the first call uses the standard StartValue (0xFFFFFFFF), and later calls use the passed `Crc_StartValue32 ^ Crc_32_Xor` to cancel the previous final XOR. That way the CRC of a large data block can be computed across several calls while keeping the intermediate results consistent. Safety_Queue takes another route: it uses the 8-bit version of the library and runs a separate CRC over the data buffer and over the structure metadata, storing the two results in `bufferCrc` and `queueCrc`; neither continues from the other. The metadata call writes the first-segment flag as FALSE and the start value as 0.

## 4. Safety_Queue.c: The Dual CRC Lock

Open `Safety_Queue.c`, and the first thing you notice is the templated API:

```c
Queue_ReturnType Safety_Queue_Init(Safety_Queue_t *queue,
    void *buffer, uint8 max_count, size_t dataSize,
    cmpFunc compare_func)
{
    SYS_CALL_SuspendOSInterrupts();
    // ... validation ...
    queue->bufStart = buffer;
    queue->bufEnd = (char *) buffer + (max_count * dataSize);
    queue->head = queue->bufStart;
    queue->tail = queue->bufStart;
    queue->dataSize = dataSize;
    queue->count = 0u;
    queue->max_count = max_count;
    queue->compare_func = *compare_func;

    queue->bufferCrc = Crc_CalculateCRC8(queue->bufStart,
            queue->dataSize * queue->max_count, 0u, 1u);
    queue->isInit = TRUE;

    size_t without_buffer_size =
        (char*) &(queue->queueCrc) - (char*) queue;
    queue->queueCrc = Crc_CalculateCRC8((void*) queue,
            without_buffer_size, 0u, 0u);

    SYS_CALL_ResumeOSInterrupts();
    return QUEUE_E_OK;
}
```

Note the pointer arithmetic `(char*) &(queue->queueCrc) - (char*) queue`. It computes the number of bytes **from the start of the structure to the queueCrc field**. That way the CRC covers only the fields before queueCrc (queueCrc itself does not participate), avoiding the recursive "CRC covering itself" problem. These are the two CRCs' jurisdictions:
1. **bufferCrc**: covers the entire data buffer (`dataSize * max_count` bytes)
2. **queueCrc**: covers the structure metadata (head, tail, count, bufferCrc... but not queueCrc itself)

## 5. The Add Operation: Verify Before Write

Every `Safety_Queue_Add` disables interrupts, validates pointers and initialization state, and then runs an **integrity check** before writing data:

```c
Queue_ReturnType Safety_Queue_Add(Safety_Queue_t *queue,
    void const *dataPtr)
{
    SYS_CALL_SuspendOSInterrupts();
    // ... NULL/init checks ...

    uint8 currBufferCrc = Crc_CalculateCRC8(queue->bufStart,
            queue->dataSize * queue->max_count, 0u, 1u);

    size_t without_buffer_size =
        (char*) &(queue->queueCrc) - (char*) queue;
    uint8 currQueueCrc = Crc_CalculateCRC8((void*) queue,
            without_buffer_size, 0u, 0u);

    if ((queue->bufferCrc != currBufferCrc)
            || (queue->queueCrc != currQueueCrc)) {
        SYS_CALL_ResumeOSInterrupts();
        return QUEUE_E_CRC_ERR;
    }

    // Queue is full check
    if (queue->count == queue->max_count) {
        queue->bufFullFlag = TRUE;
        queue->queueCrc = Crc_CalculateCRC8((void*) queue,
            without_buffer_size, 0u, 1u);
        SYS_CALL_ResumeOSInterrupts();
        return QUEUE_E_FULL;
    }

    MEMCPY(queue->head, dataPtr, queue->dataSize);
    queue->head = (char *) queue->head + queue->dataSize;

    if (queue->head == queue->bufEnd) {
        queue->head = queue->bufStart;  // Wrap-around
    }
    queue->count++;

    // Update CRC values
    queue->bufferCrc = Crc_CalculateCRC8(queue->bufStart,
            queue->dataSize * queue->max_count, 0u, 1u);
    queue->queueCrc = Crc_CalculateCRC8((void*) queue,
            without_buffer_size, 0u, 1u);

    SYS_CALL_ResumeOSInterrupts();
    return QUEUE_E_OK;
}
```

Operation sequence:
1. **Disable interrupts** (`SYS_CALL_SuspendOSInterrupts`): prevents check-then-act races
2. **CRC integrity check**: corrupted data returns QUEUE_E_CRC_ERR immediately
3. **Full check**: when full, return QUEUE_E_FULL and update queueCrc (bufFullFlag changed)
4. **MEMCPY the data in**
5. **Update head / count / wrap-around**
6. **Recompute and store both CRCs**
7. **Enable interrupts**

Next has the same skeleton with a slightly different check order: it first checks whether the queue is empty, returning `QUEUE_E_NO_DATA` immediately if `count` is 0, and only then computes both CRCs for validation. After the dequeue completes it looks at `bufFullFlag`; if the flag is TRUE the queue was full at some point, so it clears the flag, updates only queueCrc, and returns `QUEUE_E_LOST_DATA` to tell the caller that data may have been lost.

## 6. The Peek Operation: A Side-Effect-Free Read Protected by CRC

Peek offers a data read that **does not modify queue state**:

```c
Queue_ReturnType Safety_Queue_Peek(Safety_Queue_t const *queue,
    void *dataPtr)
{
    SYS_CALL_SuspendOSInterrupts();
    // validation, CRC check...
    if ((queue->bufferCrc != currBufferCrc)
            || (queue->queueCrc != currQueueCrc)) {
        SYS_CALL_ResumeOSInterrupts();
        return QUEUE_E_CRC_ERR;
    }
    if (queue->count == 0u) {
        SYS_CALL_ResumeOSInterrupts();
        return QUEUE_E_NO_DATA;
    }

    MEMCPY((void*) dataPtr, queue->tail, queue->dataSize);

    SYS_CALL_ResumeOSInterrupts();
    return QUEUE_E_OK;
}
```

After Peek the queue's CRC does not need updating because no data was modified. But **a full CRC verification still runs before the read**. That guarantees the returned data is trustworthy even if the read happens silently.

## 7. Error Typology: Return Codes as Safety Signals

The return codes defined by Safety_Queue map a complete safety state space:

| Return code | Meaning | Safety impact |
|--------|------|---------|
| `QUEUE_E_OK` | Operation succeeded | Continue |
| `QUEUE_E_NULL` | Null pointer | Caller code error |
| `QUEUE_E_NO_INIT` | Not initialized | Call-order error |
| `QUEUE_E_CRC_ERR` | **CRC check failed** | **Hardware fault** |
| `QUEUE_E_FULL` | Queue full | Possible data loss |
| `QUEUE_E_NO_DATA` | Queue empty | No data to read |
| `QUEUE_E_LOST_DATA` | Historical frame loss found at dequeue | Gap in the data window |
| `QUEUE_E_ALREADY_INIT` | Repeated initialization | Logic error |
| `QUEUE_E_TRUE` / `QUEUE_E_FALSE` | Contains result | Search answer |

`QUEUE_E_CRC_ERR` is the most critical error; it means the data in RAM has been silently corrupted. When the caller receives this error it should usually:
1. Record a DEM event (evidence of a hardware fault)
2. Reinitialize the queue (clear the corrupted data)
3. If it keeps happening → trigger safety degradation

Safety_Queue's dual-CRC design solves a classic problem: how do you detect silent corruption of RAM data without relying on hardware ECC? The answer is to sign the metadata and the data with separate CRC8s, verify before every operation, and recompute after changing state. A CRC8 has only 256 possible values, so random garbage slips through with probability about 1 in 256 — a detection rate of about 99.6%; a single-bit flip and any burst error of 8 bits or less is always caught. In the table implementation each byte is just one table lookup and XOR, and the loop body contains no data-dependent branch, so for typical queue sizes of tens to hundreds of bytes the cost is on the order of microseconds.

## Summary

1. The CRC32 engine's two modes are selected by a compile switch: `CRC_32_RUNTIME` (bit-by-bit, O(n×8), which the source comment positions as a reference implementation to compare against the table result) and `CRC_32_TABLE` (256-entry precomputed table, O(n), marked as the default in the configuration). Both modes use the `Crc_IsFirstCall` parameter to compute one large data block across several consecutive calls.
2. IEEE-802.3 CRC32 requires the data to be reflected bit by bit before calculation and the result reflected afterwards. The reflect operation reverses each individual bit, which is the core of the LSB-first algorithm and the opposite of the intuitive "divide from the high bit first".
3. Safety_Queue uses a dual-CRC8 strategy: `bufferCrc` covers the whole data buffer, while `queueCrc` covers the structure metadata (head/tail/count and so on, including the stored bufferCrc, with only queueCrc itself excluded). The first detects silent data corruption, the second detects metadata modification, and the two covered memory ranges do not overlap.
4. Add/Next/Peek all run a full CRC verification before acting (Next checks empty first, then verifies). Add and Next recompute and update both CRCs after changing state; Peek does not change state so it skips that step. Interrupts stay disabled throughout to prevent races. A CRC failure returns `QUEUE_E_CRC_ERR`, and the caller should record a DEM event and trigger safety degradation.
5. Safety_Queue's return codes map a complete safety state space (OK/NULL/NO_INIT/CRC_ERR/FULL/NO_DATA/LOST_DATA/ALREADY_INIT). `QUEUE_E_LOST_DATA` uses `bufFullFlag` to detect a historical overflow, closing the blind spot in "full → dequeue → data gap" detection.
