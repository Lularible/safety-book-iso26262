# 4.6 Integration: WdgM_ConfigTypes.h and the Art of Static Configuration

## Scenario: Walking Through the "Genetic Sequence" of Configuration Data

You have now read all the runtime code in the first five sections: WdgM's Init/MainFunction, E2E's Protect/Check, Safety_Queue's dual CRC, RamTst's March X. These code paths share one property: they never make runtime decisions. No `malloc`, no `if (runtime_flag) create_table()`, no dynamically created objects.

Open `WdgM_ConfigTypes.h`. 159 lines. It contains **the static blueprint of the entire WdgM world**, unfolding from the top-level `WdgM_ConfigType` down to every supervised entity, every alive checkpoint, every deadline time window, every logical transition edge. This is not just configuration; it is the "genetic sequence" that fully determines system behavior before compilation.

## 1. From Leaves to Root: Walking the Configuration Tree in Reverse

We start from the lowest-level data structures and build upward layer by layer.

### Level 1: The Supervision Items

The smallest unit in the configuration:

```c
typedef struct
{
    const uint16            TriggerConditionValue;
    const WdgIf_ModeType    WatchdogMode;
    const uint8             WatchdogId;
} WdgM_Trigger;
```

A Trigger defines: which watchdog (`WatchdogId` first serves as an index into `General.Watchdogs[]`, and that entry's `WatchdogDeviceId` then maps to the WdgIf device number), which mode (`WDGIF_FAST_MODE`/`WDGIF_SLOW_MODE`/`WDGIF_OFF_MODE`), and what value to feed. Three struct lines give almost all the parameters of `WdgIf_SetTriggerCondition` in MainFunction; the only exception is that after the global state lands on STOPPED, the trigger value is forced to zero.

```c
typedef struct
{
    const uint16        CheckpointId;
    const uint16        ExpectedAliveIndications;
    const uint8         MinMargin;
    const uint8         MaxMargin;
    const uint16        SupervisionReferenceCycle;
} WdgM_AliveSupervision;
```

An AliveSupervision binds one checkpointId, expects `ExpectedAliveIndications` calls, allows a deviation of `-MinMargin`/`+MaxMargin` (the actual comparison is "count minus expected value" falling between these two bounds), and evaluates once every `SupervisionReferenceCycle` MainFunction cycles. These `uint16`/`uint8`/`boolean` are all AUTOSAR platform types, brought in by `Platform_Types.h` through `Std_Types.h`, and underneath they are the C99 fixed-width integers: 16-bit unsigned for IDs and counts, 8-bit unsigned for tolerances. **No type is imprecise**. This is a data model built for embedded safety.

```c
typedef struct
{
    const uint16            CheckpointIdStart;
    const uint16            CheckpointIdFinish;
    const uint32            DeadlineMin;
    const uint32            DeadlineMax;
} WdgM_DeadlineSupervision;
```

DeadlineMin/Max are uint32, giving second-level precision, because deadline supervision involves multiplication and comparison of OS ticks and needs the width to prevent overflow.

```c
typedef struct
{
    const uint16            CheckpointIdSource;
    const uint16            CheckpointIdDestination;
} WdgM_InternalTransition;
```

The transition edges of logical supervision: an ordered pair of checkpoint IDs that defines which paths in the program execution graph are legal.

### Level 2: The Supervised Entity Definition

```c
typedef struct
{
    const uint16                    Id;
    const uint16                    *CheckpointIds;
    const uint16                    Length_CheckpointIds;
    const WdgM_InternalTransition   *Transitions;
    const uint16                    Length_Transitions;
    const uint16                    *StartCheckpointIds;
    const uint16                    Length_StartCheckpointIds;
    const uint16                    *FinalCheckpointIds;
    const uint16                    Length_FinalCheckpointIds;
    const boolean                   isOsApplicationRefSet;
    const ApplicationType           OsApplicationRef;
} WdgM_SupervisedEntity;
```

`WdgM_SupervisedEntity` describes a **supervised software entity**: it has a unique Id, a set of checkpoints, a transition table, and a set of start and final checkpoints. Note that all arrays are **pointer + length** pairs, with no flexible array members and no runtime length inference. These `Length_xxx` fields serve two roles: the bound for iteration, and the ID limit at the API entry. `WdgM_SetMode` uses `Length_Modes` to bound the mode number; `WdgM_CheckpointReached` first uses `General.Length_SupervisedEntities` to bound the SEID, then uses the entity's own `Length_CheckpointIds` to bound the CheckpointId, and an out-of-range call is rejected on the spot by the parameter check. The checkpoint check only compares magnitudes and does not search a table, so checkpoint numbers must lie in the contiguous range from 0 to `Length_CheckpointIds` minus one.

`isOsApplicationRefSet` is a boolean flag. If set to TRUE, `OsApplicationRef` is valid and WdgM can associate with the OS Application level.

### Level 3: Entity Configuration Within a Mode

```c
typedef struct
{
    const uint16                            SupervisedEntityId;
    const boolean                           CheckInternalLogic;
    const WdgM_AliveSupervision             *AliveSupervisions;
    const uint16                            Length_AliveSupervisions;
    const WdgM_DeadlineSupervision          *DeadlineSupervisions;
    const uint16                            Length_DeadlineSupervisions;
    const uint8                             FailedAliveSupervisionReferenceCycleTol;
    const uint8                             OSCounter;
} WdgM_SupervisedEntityConfiguration;
```

This is the "runtime configuration" of the entity in the context of a mode: which alive/deadline supervisions are active in this mode, whether internal logic supervision is on (`CheckInternalLogic`), how many cycles of failure to tolerate, and which OS Counter to use. Note that there is **no** LogicSupervision array here: the transition table for logical supervision lives in `WdgM_SupervisedEntity`, is a global constant, and does not change when the mode switches.

`FailedAliveSupervisionReferenceCycleTol` is the tolerance for a local state moving from FAILED to EXPIRED: the failure-cycle counter `FailedAliveCyclesCounter` accumulates with each failed alive supervision round, and the entity is escalated to EXPIRED only when it is strictly greater than this tolerance value. If in some round all three substates come back correct, the counter is decremented again, so the entity has a chance to climb back to OK on its own.

### Level 4: The Mode

```c
typedef struct
{
    const uint8                                 Id;
    const uint16                                ExpiredSupervisionCycleTol;
    const uint32                                SupervisionCycle;
    const WdgM_SupervisedEntityConfiguration    *SEConfigurations;
    const uint16                                Length_SEConfigurations;
    const WdgM_Trigger                          *Triggers;
    const uint8                                 Length_Triggers;
} WdgM_Mode;
```

A Mode defines: the global identifier ID, the global EXPIRED→STOPPED tolerance cycle count, which SEs are active in the current mode, and which watchdogs to feed.

`ExpiredSupervisionCycleTol` is the mode-level grace period: as long as any entity's local state is EXPIRED, the global state stays at EXPIRED, and the runtime `ExpiredSupervisionCycleCounter` increments cycle by cycle until it reaches this tolerance value, only then falling to STOPPED. A mode switch is itself a global event, so the tolerance is kept at the mode level for uniformity. `SupervisionCycle` on the same level belongs to the class of fields that are "declared in the configuration but have no reader in this implementation": `WdgM.c` never reads it, and the pace is set entirely by the OS schedule for MainFunction.

### Level 5: General and ConfigSet

```c
typedef struct
{
    const WdgM_SupervisedEntity *SupervisedEntities;
    const uint16                Length_SupervisedEntities;
    const WdgM_Watchdog         *Watchdogs;
    const uint8                 Length_Watchdogs;
} WdgM_General;

typedef struct
{
#if defined(USE_DEM)
    const WdgM_DEMEventIdRefs           DemEventIdRefs;
#endif
    const uint8                         initialModeId;
    const WdgM_Mode                     *Modes;
    const uint8                         Length_Modes;
} WdgM_ConfigSet;
```

General holds two global arrays:
- `SupervisedEntities[]`: the **definitions** of all supervised entities (their transition tables, checkpoint lists)
- `Watchdogs[]`: the **mapping** of all hardware watchdogs (each WatchdogId corresponds to one WdgIf device ID)

ConfigSet holds:
- `DemEventIdRefs`: two DEM event IDs. `Supervision` is the supervision failure event (reported only when the global state lands on STOPPED and the corresponding report switch is on); `SetMode` is the mode-setting failure event (reported only when deactivating or activating the watchdog fails during initialization or a mode switch)
- `initialModeId`: the mode entered after startup
- `Modes[]`: the definitions of all modes

### Top Level: The Wrapper

```c
typedef struct
{
    const WdgM_General      General;
    const WdgM_ConfigSet    ConfigSet;
} WdgM_ConfigType;

extern const WdgM_ConfigType WdgMConfig;
```

At the top level everything becomes one global const symbol, `WdgMConfig`, which the linker places in the .rodata section (or a Flash-mapped address space). `WdgM_Init(&WdgMConfig)` starts the entire monitoring world with one pointer. There is an easily overlooked division of labor here: `WdgMConfig` is only declared extern in this header; the definition lives in the configuration source file generated by the toolchain.

## 2. The Safety Argument for "All const"

Look back at the whole configuration tree: from leaf nodes to the root, every field is `const`. That means:

1. **Physically read-only**: if `.rodata` maps to a read-only Flash region and the MPU configures that region read-only (safety-related projects usually do; the exact permission bits are the chip manual's business), any code that tries to modify the configuration triggers an access exception, and the hardware blocks configuration tampering.

2. **Build-time decisions**: all array lengths are explicit `Length_xxx` fields, and those length values are themselves constants in `.rodata`. From the type alone the compiler still sees only "a pointer plus a length"; once a static analysis tool (such as Polyspace or Astree) substitutes the constants, it can prove there are no out-of-bounds accesses.

3. **No indirect jumps**: there are no function pointers in the configuration tree (note that `WdgM_Trigger` has only value and mode, no callback). Every execution path driven by configuration is fixed at compile time; the RTE branch does have an indirect jump table, but that is generated code and has nothing to do with the fields in `WdgM_ConfigTypes.h`.

4. **Provability**: because the configuration is static constants, you can write a formal configuration validation tool: "Is the CheckpointId of this mode's SE AliveSupervision present in the CheckpointIds array defined by the SE?" The answer is pure logical reasoning, no execution needed.

This is a strong safety argument: structural errors in the configuration surface at compile or link time (a wrong field name or type mismatch is stopped by the compiler; a version macro mismatch makes the two checks at the top of `WdgM.c` stop the build with `#error`), so there is no chance to fail silently at runtime. Once the configuration compiles, links, and passes static analysis, its structural integrity counts as proven. What remains is value consistency, which is left to the generation toolchain and review.

## 3. The EOL (End-of-List) Termination Pattern

You see no explicit EOL marker in the code and no `{0, 0, 0, ...}` sentinel. So how do you know where an array ends?

The answer is the `Length_xxx` field. `WdgM_Mode` iterates up to `Length_SEConfigurations`:

```c
for (i = 0u; i < WdgM_instance.CurrentMode->Length_SEConfigurations; i++)
```

This pattern has two advantages:
- **No sentinel value needed**: a sentinel can collide with valid data (for example, checkpointId=0 may be legal)
- **The bound is O(1)**: no linear scan to find EOL; `Length_xxx` gives it directly

What AUTOSAR specifies is which configuration parameters WdgM must have; how those parameters are laid out in C structs is the implementation's freedom, and "pointer plus explicit length" is Arctic Core's choice. Compared with the common practice on other embedded platforms (terminating arrays with `{NULL, 0, 0, 0}`), WdgM's explicit length is the safer O(1) approach.

## 4. The WdgIf Mapping Chain

The signal chain from WdgM configuration to the hardware watchdog:

```
WdgM_Mode.Triggers[i].WatchdogId
  → WdgM_General.Watchdogs[WatchdogId].WatchdogDeviceId
    → WdgIf_SetMode(DeviceIndex, mode)
    → WdgIf_SetTriggerCondition(DeviceIndex, value)
```

Every link in this mapping chain is an index fixed at compile time: the configuration generation tool (such as Vector DaVinci) ensures WatchdogId never goes out of range. The source code:

```c
uint8 DeviceIndex = WdgM_instance.ConfigPtr->General.Watchdogs[
    Mode->Triggers[i].WatchdogId].WatchdogDeviceId;
(void)DeviceIndex; /* Remove compile warning when using
                      only one watchdog driver */
Std_ReturnType potError = WdgIf_SetMode(
    DeviceIndex, Mode->Triggers[i].WatchdogMode);
```

The `(void)DeviceIndex` idiom is worth pondering; the reason is in the WdgIf header. That header branches on the number of watchdog devices configured: when there is more than one device, `WdgIf_SetMode` is a real function with a `DeviceIndex` parameter; with only one device it degrades into a macro that hard-codes `WdgIfConfig.WdgIf_Device[0u]`, and `DeviceIndex` never appears in the macro body. The same `WdgM.c` under the two builds has this local variable read in one case and untouched from birth to death in the other, and the latter draws an "unused variable" warning; `(void)` swallows it explicitly. This is the usual code-smell handling in statically configured code.

## 5. Optional Compilation of DEM Events

```c
#if defined(USE_DEM)
typedef struct
{
    const Dem_EventIdType       Supervision;
    const Dem_EventIdType       SetMode;
} WdgM_DEMEventIdRefs;
#endif
```

If `USE_DEM` is not defined, `WdgM_DEMEventIdRefs` does not exist in the structure at all. ConfigSet becomes:

```c
typedef struct
{
#if defined(USE_DEM)
    const WdgM_DEMEventIdRefs           DemEventIdRefs;
#endif
    const uint8                         initialModeId;
    const WdgM_Mode                     *Modes;
    const uint8                         Length_Modes;
} WdgM_ConfigSet;
```

`#if` inserts it when DEM is present and removes it when DEM is absent, so the struct's memory layout differs between the two configurations. This is the "compile-time polymorphism" common in AUTOSAR, achieved not through a virtual function table but through the preprocessor. The space saved is a definite 4 bytes: in this platform's types `Dem_EventIdType` is `uint16`, and two event IDs are exactly two cells. Places in the code that call `DEM_EVENT_ID_NULL` are replaced by the macro with `0` (defined at the top of WdgM.c).

## 6. Runtime Data Structures: The Shadow of the Configuration

The configuration is read-only, but WdgM also has a corresponding set of **runtime data structures**, defined in WdgM's private header. You have already seen them in the code:

- `WdgM_runtime_SupervisedEntity`: stores LocalState, SubstateAlive/Deadline/Logical, FailedAliveCyclesCounter, PreviousCheckpointId_internalLogic, IsInternalGraphActive
- `WdgM_runtime_SupervisedEntityConfig`: stores the counter of each AliveSupervision and the LastTickValue of each DeadlineSupervision
- `WdgM_runtime_Mode`, stores ExpiredSupervisionCycleCounter

The runtime structs **mirror the tree relationships of the configuration structs**, but each field type is chosen again for its purpose: the alive accumulation count uses `uint32`, the last timestamp of deadline supervision uses the OS `TickType`, the local state uses `WdgM_LocalStatusType`, the three substates use `WdgM_Substate`, plus a set of `boolean` flags. `WdgM_Substate` is an alias of `uint8`, and the two value macros `WDGM_SUBSTATE_INCORRECT=0`, `WDGM_SUBSTATE_CORRECT=1` are deliberately chosen as 0 and 1, so at runtime `SubstateAlive`, `SubstateDeadline`, and `SubstateLogical` can be added directly and the sum is the number of correct substates this round, with 3 meaning all correct; on failure the tolerance counter decrements as described in the previous section.

Instantiation:

```c
WdgM_debuggable_runtimeData WdgM_instance = {
    .GlobalState = WDGM_GLOBAL_STATUS_DEACTIVATED,
    .isInitiated = (boolean)FALSE
};
```

`WdgM_instance` is a global variable and the entry point for accessing all runtime state in the WdgM module. It does not itself hold that tree; it holds a `runtimeDataPtr`, which in `WdgM_Init` is pointed at `WdgM_runtimeData`, a separate global object provided by the generated configuration. `WdgM.c` separately holds the two static redundant-storage variables `firstExpiredSEID` and `firstExpiredSEIDInverse`, and with RTE enabled it also uses a mode-switch function pointer table provided by generated code. Funneling mutable state through one entry point is still worthwhile: following `WdgM_instance` reaches all runtime data, and state-integrity assertions only need to start from this one root.

## 7. The Last Link of the Version Check

Don't overlook the include chain at the top of `WdgM_ConfigTypes.h`; the real version gate is at the top of `WdgM.c`:

```c
#include "WdgM_Cfg.h"
#include "WdgIf.h"
#if defined(USE_DEM)
#include "Dem.h"
#endif
#include "Os.h"
```

`WdgM_Cfg.h` is the output of the configuration generation tool and supplies module switches such as `WDGM_DEV_ERROR_DETECT`; `USE_DEM`, `USE_RTE` and friends are written in Arctic Core's board-level build configuration and turned into `-D` switches on the compiler command line by the build script. At the top of `WdgM.c` there are also two conditional-compilation blocks, each with an `#error`: one requires the BSW module version to be 3.0.x, the other requires the AUTOSAR version to be 4.3.x, and the build stops if they do not match. These switches decide which structs, which fields, and which code paths get compiled.

## 8. Full-Stack Wiring: How Configuration Drives Behavior

To summarize the whole configuration → runtime mapping:

| Configuration struct | Runtime behavior it drives |
|-----------|-----------------|
| `WdgM_ConfigType` | The only parameter of `WdgM_Init` |
| `WdgM_Mode.Id` | Index for mode switching |
| `WdgM_Mode.Triggers[]` | Parameters for feeding the watchdog in MainFunction |
| `WdgM_Mode.SEConfigurations[]` | List of active SEs; each entry's `CheckInternalLogic` decides whether logical supervision is on |
| `WdgM_Mode.ExpiredSupervisionCycleTol` | Timing of GlobalState EXPIRED→STOPPED |
| `WdgM_SEConfiguration.AliveSupervisions[]` | Alive expectation and tolerance calculation |
| `WdgM_SEConfiguration.DeadlineSupervisions[]` | Deadline start/end and time window (configured in seconds, converted to OS ticks at check time) |
| `WdgM_SupervisedEntity.Transitions[]` | Transition-table verification for Logical supervision; the graph activates when `StartCheckpointIds` matches and closes when `FinalCheckpointIds` matches |
| `WdgM_ConfigSet.DemEventIdRefs` | DEM event reporting |
| `WdgM_ConfigSet.initialModeId` | First mode after startup |

Every runtime decision can be traced field by field from the configuration structs to where it is referenced in the code. That is needed both to read the code and because the standard demands it of configurable software: the configuration data must specify the legal value range of each field, its intent and purpose, its range and units, and the interdependencies between fields. Then it must be verified: that the data conforms to the software architecture and unit design, that every value lies in its declared range, and that the values are compatible with one another. The ASIL of the configuration data must be the highest ASIL of the software it configures.

The real power of "static configuration" is not at compile time; it is in the **Safety Case**. When you say "this system cannot have a configuration error at runtime", your evidence is not how many if-else fallbacks you wrote, but "the configuration is const, lives in read-only memory, and is verified by the toolchain before compilation". Static configuration turns "code that might fail" into "code that cannot compile". You don't need to prove the software can handle every configuration error; you only need to prove that a wrong configuration cannot be compiled and linked.

## Summary

1. The 159 lines of `WdgM_ConfigTypes.h` hold type definitions, two substate macros, and one extern declaration. The complete configuration tree from `WdgM_Trigger` to `WdgM_ConfigType` lives there, every field is `const`, and it lands in `.rodata` after linking; configure that region read-only in the MPU and any runtime tampering attempt becomes an access exception on the spot.
2. The configuration tree is built in reverse, "leaf → root": `WdgM_AliveSupervision` / `WdgM_DeadlineSupervision` / `WdgM_InternalTransition` → `WdgM_SupervisedEntity` → `WdgM_SupervisedEntityConfiguration` → `WdgM_Mode` → `WdgM_ConfigSet` + `WdgM_General` → `WdgM_ConfigType`. The `Length_xxx` at each level is both the array bound for iteration and the limit used at API entries for SEID, CheckpointId, and mode number.
3. The runtime data structures (`WdgM_runtime_*`) mirror the tree of the configuration, with field types chosen per purpose (`uint32` counters, `TickType` timestamps, enum states, `boolean` flags); `WdgM_instance` is the entry to the runtime tree, following the "single global state root" approach to safe coding.
4. DEM event IDs control the struct's memory layout through `#if defined(USE_DEM)`, saving 4 bytes when DEM is absent (`Dem_EventIdType` is `uint16` in this platform's types, and there are two event IDs) — AUTOSAR's "compile-time polymorphism", done purely with the preprocessor rather than a virtual function table.
5. The real value of static configuration is the Safety Case: not a pile of runtime if-else fallbacks, but making a wrong configuration impossible to compile and link — "code that might fail" becomes "code that cannot compile".
