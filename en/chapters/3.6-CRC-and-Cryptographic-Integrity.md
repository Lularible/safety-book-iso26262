# 3.6 CRC and Cryptographic Integrity: A Message's Genetic Fingerprint

You are the powertrain domain master of an electric vehicle, and you face a serious problem: you just sent a 256-byte BMS (battery management system) firmware upgrade block to the battery pack MCU over CAN. The 256 bytes contain a critical change to the overcharge protection threshold (4.25 V→4.20 V). If that value changes in transit, the battery pack may go into thermal runaway on the next fast charge.

The battery pack MCU receives the data and must verify that it is intact. The first thing it can do is compute a checksum. The simplest algorithm: add up all 256 bytes, take the result modulo 256, and append it to the data. The receiver recomputes it, and if the values match, the data is considered intact.

This scheme has a fatal flaw. Consider these two 70-byte data blocks:

```
Data block A: [0x12, 0x34, 0x56, ..., 0x78] → sum of all bytes = 0x5A40 → mod 256 = 0x40
Data block B: [0x34, 0x12, 0x56, ..., 0x78] → sum of all bytes = 0x5A40 → mod 256 = 0x40
```

The first two bytes swapped positions, but the simple checksum cannot detect it, because addition is commutative. Worse: any two bytes that flip at the same time while keeping their sum unchanged (for example 0x12→0x13 and 0x34→0x33) also slip past the checksum.

You turn to the check method recommended by the standard: CRC. CRC does not add bytes; it treats the whole message as one giant binary polynomial, divides it by a carefully chosen "generator polynomial," and takes the remainder as the check value. That remainder is highly sensitive to the data pattern: flip one bit, swap two bytes, add a zero byte—each produces a completely different remainder.

The difference between CRC and an ordinary checksum lies in the algebraic structure of the operation. An ordinary checksum is an additive, commutative linear operation (sum(A+B) = sum(A) + sum(B)); swap two values or add one and subtract another and the sum holds. CRC is also a linear map over GF(2), CRC(A+B) = CRC(A) + CRC(B) (where the plus sign is XOR). The difference is that it gives every bit a positional weight (multiplication by a power of x): move a byte and the weight moves with it, so the remainder changes. Detection power comes from those positional weights and the choice of polynomial.

## Polynomial Arithmetic over GF(2): The Mathematical Basis of CRC

To understand CRC, you need to enter the world of the Galois field GF(2). In GF(2):
- addition is XOR: 1+1=0, 1+0=1, 0+0=0
- multiplication is logical AND: 1×1=1, 1×0=0, 0×0=0
- subtraction equals addition: a-b = a+b (because every element is its own additive inverse)

A binary sequence can be represented as a polynomial over GF(2). For example, `10110011` corresponds to the polynomial:

```
x⁷ + x⁵ + x⁴ + x¹ + x⁰
```

The CRC computation is: shift the message polynomial M(x) left by n bits (n is the CRC width), then divide by the generator polynomial G(x), and take the remainder R(x). That R(x) is the CRC value.

```
M(x) × xⁿ ÷ G(x) → quotient Q(x) + remainder R(x)
CRC = R(x)
```

At the receiver, divide the received message polynomial (M'(x) = M(x) × xⁿ + R(x)) by the same G(x). If transmission was error-free, the remainder should be zero, because M(x) × xⁿ + R(x), in the additive (XOR) sense, equals Q(x) × G(x) + R(x) + R(x) = Q(x) × G(x), exactly divisible by G(x).

If an error E(x) (the error polynomial) occurs in transit, the received polynomial becomes:

```
M'(x) + E(x) = Q(x) × G(x) + R(x) + E(x) + R(x) = Q(x) × G(x) + E(x)
```

The remainder after division by G(x) is E(x) mod G(x). If E(x) happens to be a multiple of G(x), the CRC misses it. That is why the choice of G(x) matters so much.

The essence of CRC is mapping infinitely many error patterns onto finitely many CRC values. CRC-N has only 2ᴺ possible CRC values, but there are infinitely many error patterns. Missed detection is mathematically unavoidable: the design goal of CRC is not "never miss" but to spread the miss probability evenly over all error patterns that can realistically occur, and keep it low enough.

## The Five AUTOSAR CRC Polynomials

AUTOSAR's Crc library exposes five computation entry points, covering four widths (8-bit has two polynomials), each chosen for different hardware constraints and error-detection needs:

### CRC8 — SAE J1850 (0x1D)

Polynomial: `x⁸ + x⁴ + x³ + x² + 1`

An 8-bit CRC, fast to compute (table lookup needs one index into a 256-byte table), suitable for checking bytes or short messages (<16 bytes). The Hamming-distance-4 threshold comes from an example in the standard for another 8-bit polynomial (0x97, length ≤ 119 bits) and cannot be applied directly to 0x1D; within the length range where Hamming distance 4 holds, it detects all 1-bit, 2-bit, and 3-bit errors—switch polynomials and you must recompute for the new one.

Typical uses of CRC8 in AUTOSAR:
- message checking for E2E Profile 1 (Profile 2 uses the 0x2F polynomial below)
- address and data checking for I2C communication
- SPI communication checking for the SBC (system basis chip)

### CRC8H2F (0x2F)

Polynomial: `x⁸ + x⁵ + x³ + x² + x + 1`

Although it is also an 8-bit CRC, it uses a different polynomial, so it does not share the same "holes" as CRC8(0x1D). Assuming their missed-detection events are independent, the product of the miss probabilities on the same message is 1/65536, greatly reducing the chance that both CRCs miss at once. This is useful in a safety architecture when one message is protected by two CRC layers (for example, CAN frame CRC + E2E CRC).

### CRC16 — CCITT (0x1021)

Polynomial: `x¹⁶ + x¹² + x⁵ + 1`

A 16-bit CRC and the most widely used check algorithm in the automotive industry. Hamming distance 4 (for message length ≤ 2048 bits), able to detect:
- all odd numbers of bit errors
- all 1-bit and 2-bit errors
- all burst errors of length ≤ 16 (99.9984% probability of detecting bursts of length ≥ 17)
- 99.9969% of all burst errors of length 17

CRC16 is used in AUTOSAR for E2E Profile 5 and 6, protecting most ASIL B/C control commands.

### CRC32 — IEEE 802.3 (0x04C11DB7)

Polynomial: `x³² + x²⁶ + x²³ + x²² + x¹⁶ + x¹² + x¹¹ + x¹⁰ + x⁸ + x⁷ + x⁵ + x⁴ + x² + x¹ + 1`

This is the standard CRC32 used by Ethernet, gzip, PNG, and other protocols. Hamming distance 4 (for message length ≤ 91,639 bits, almost 11.5 KB). Undetected rate about 1/2³² ≈ 2.3 × 10⁻¹⁰.

### CRC32P4 — AUTOSAR Profile 4 (0xF4ACFB13)

Polynomial: `x³² + x³¹ + x³⁰ + x²⁹ + x²⁸ + x²⁶ + x²³ + x²¹ + x¹⁹ + x¹⁸ + x¹⁵ + x¹⁴ + x¹³ + x¹² + x¹¹ + x⁹ + x⁸ + x⁴ + x¹ + 1`

This is the polynomial AUTOSAR customized for Profile 4, different from the standard CRC32. Why not use the standard 0x04C11DB7? Because standard CRC32 was designed for Ethernet, and Ethernet's error patterns (burst noise, collision fragments) are completely different from CAN's. Typical CAN bus errors are **pulse noise** and **bit-stuffing errors**. According to AUTOSAR's selection notes, this polynomial targets typical CAN bus error patterns; the detailed simulation and comparison process belongs to specification-side material.

CRC32P4 has a Hamming distance of at least 6 (for length ≤ 268 bits), which means it detects any 5-bit error with 100% probability, providing a solid mathematical foundation for ASIL D safety-critical control commands.

Polynomial quality is measured by three indicators: Hamming distance (100% detection of any error up to k bits), burst-error protection length (the maximum length of consecutive error bits that can be detected with 100% probability), and detection rate against the error patterns of a specific communication medium. 0xF4ACFB13 was chosen as the P04 polynomial; according to AUTOSAR's selection notes it targets CAN bus failure modes; what the source code can verify is the polynomial value itself.

## Table Lookup vs Runtime Computation: Speed Against Space

The mathematical definition of CRC is elegant: bit-by-bit polynomial division. But in a real embedded implementation (Cortex-M/R, TriCore, RH850), bit-by-bit computation is too slow.

A 256-byte message with bit-by-bit CRC32 needs 256 × 8 = 2048 iterations, each with a conditional test, two XORs, and one shift. On a 200 MHz Cortex-R5, that takes about 50 µs. For a 10 ms EPS control loop, 50 µs is only 0.5%, which seems acceptable. But an ECU may have dozens of safety messages to protect, and the accumulated cost can reach milliseconds.

**Table lookup** speeds CRC up by nearly an order of magnitude. The idea is to precompute the CRC intermediate result for all 256 byte values (256 × 4 bytes = 1 KB table). On each step, index the table with the high or low byte of the current CRC, and one table lookup plus one XOR processes one byte.

```c
/* Core loop of the CRC32 table-lookup method */
uint32 Crc_CalculateCRC32(const uint8 *data, uint32 length, uint32 startValue, boolean isFirstCall) {
    uint32 crc = (isFirstCall == TRUE) ? 0xFFFFFFFFU : (startValue ^ 0xFFFFFFFFU);
    for (uint32 i = 0; i < length; i++) {
        crc = (crc >> 8) ^ crc32_table[(crc ^ data[i]) & 0xFF];
    }
    crc ^= 0xFFFFFFFF;  /* final XOR, performed after the computation */
    return crc;
}
```

AUTOSAR's Crc module (SWS_Crc) requires at least runtime computation (for all polynomials) and table-lookup acceleration (recommended but not mandatory).

## Hardware CRC Engines: Silicon Immune Cells

Modern automotive MCUs have pushed CRC computation down into hardware. Here are the hardware CRC capabilities of mainstream platforms:

**NXP SPC58x (PowerPC e200z4)**:
- dedicated CRC computation unit (CCU)
- supports CRC8, CRC16, CRC32, CRC32P4
- throughput: 1 byte per clock cycle (80 MB/s at 80 MHz)
- supports DMA-chain triggering, starting CRC computation automatically as data arrives

**Infineon AURIX TC3xx (TriCore)**:
- CRC peripheral (CRC)
- supports multiple polynomial configurations (including custom polynomials)
- deeply integrated with the DMA module
- special mode: memory CRC scan (automatic background verification of Flash integrity)

**Renesas RH850**:
- data CRC calculator (DCC)
- supports 8/16/32-bit CRC
- hardware bit reversal and byte reversal (for different endianness)

With a hardware CRC engine, CRC32 over a 256-byte block drops to 256 clock cycles (about 3 µs total including configuration and startup overhead), roughly 3× faster than software table lookup and 16× faster than the bit-by-bit method.

## Quantifying CRC Detection Capability

CRC is not magic; its detection capability has strict mathematical limits. Take CRC16 (0x1021):

| Error type | Detection rate |
|----------|--------|
| 1-bit error | 100% |
| 2-bit error | 100% |
| odd number of bit errors | 100% |
| burst error ≤16 bits | 100% |
| burst error =17 bits | 99.9969% |
| burst error >17 bits | (1-2⁻¹⁶) ≈ 99.9985% |
| other multi-bit errors | statistical meaning of (1-2⁻¹⁶) |

The proof that "100% detection of all odd numbers of bit errors" is simple: if G(x) contains the factor (x+1), then any odd-term error polynomial is divisible by (x+1). 0x1021 = x¹⁶ + x¹² + x⁵ + 1 contains the factor (x+1) (verification: substitute x=1 into the polynomial; a result of 0 means the factor is present), so CRC16 detects all odd numbers of bit errors.

The proof that "100% detection of all burst errors of length ≤ 16": any burst error of length k≤16 can be written as the polynomial E(x) = xⁱ × (xᵏ⁻¹ + ... + 1), where i is the burst start position. E(x) is divisible by a degree-16 polynomial if and only if xᵏ⁻¹ + ... + 1 is divisible by a degree-16 polynomial. But a degree-16 polynomial cannot divide a polynomial of degree less than 16. Therefore E(x) mod G(x) ≠ 0.

## CRC vs Cryptographic Hash: Why Not SHA-256

You may ask: since SHA-256 provides 2¹²⁸ collision resistance, why not just use SHA-256 instead of CRC32P4?

The answer comes down to three things: **real-time behavior, resources, and determinism**.

In CAN communication (500 kbps), transmitting one 8-byte CAN frame takes about 200 µs. If the receiver needs 50 µs to compute SHA-256 (even with hardware acceleration), the software stack's latency increases by 25%. For 10 ms EPS control, that accumulated overhead can cause control-loop jitter.

More importantly, Flash and RAM are scarce resources in embedded systems. A software SHA-256 implementation needs about 2 KB of code and 256 bytes of working memory. CRC16 needs only about 50 bytes of code (or a 1 KB lookup table, but the table can live in ROM).

The most critical difference is **determinism**. CRC is a deterministic polynomial operation: given the same input and initial value, the output is always the same (consistent across compilers, platforms, and endianness). SHA-256 is deterministic in theory, but implementations on different platforms must carefully handle endianness and padding conventions; otherwise you get the nightmare of "the same data produces different hash values on different platforms."

| Dimension | CRC16 | CRC32P4 | SHA-256 |
|------|-------|---------|---------|
| Output length | 16 bits | 32 bits | 256 bits |
| Miss probability | 1.5×10⁻⁵ | 2.3×10⁻¹⁰ | 8.6×10⁻⁷⁸ |
| Software speed | ~100 MB/s | ~200 MB/s | ~10 MB/s |
| Code size | <100 B | <500 B | ~2 KB |
| Hardware support | widespread | limited | very few MCUs |
| Determinism | perfect | perfect | needs endianness handling |

## The Immune-System Metaphor: A Genetic Fingerprint

Every biological individual has a unique DNA sequence. DNA fingerprinting (PCR amplification + electrophoresis) can precisely identify one individual's DNA among a million samples. Short tandem repeats (STRs) in specific regions of DNA are natural "biological CRCs": any tiny change during replication (the gain or loss of one repeat unit) completely changes the fingerprint pattern.

CRC acts as the message's "genetic fingerprint"—not the message itself, but a highly sensitive, unique short sequence extracted from the message's genes. Once any base pair (bit) in the message's "genes" mutates, the fingerprint pattern changes completely.

AUTOSAR's five CRC polynomials are like five different DNA fingerprint probes: CRC8 gives coarse identification of short sequences, CRC32P4 gives ultra-fine individual identification. In the immune system, the polymorphism of MHC molecules (HLA-A, HLA-B, HLA-C) provides antigen recognition at different granularities, and the diversity of CRC polynomials provides exactly the same layered protection.

CRC is polynomial division over the Galois field GF(2). From CRC8's 1/256 miss rate to CRC32P4's 1-in-4.2-billion miss rate, it provides a complete detection-capability chain from ASIL A to ASIL D. Choosing a CRC is not "the safer the better"; it must match the consequences of failure strictly.

Hardware CRC engines turn CRC computation from a software burden into a hardware feature; CRC32 over a 256-byte block drops to 3 µs.

## Summary

1. CRC is polynomial division over GF(2): divide the message polynomial by a generator polynomial and take the remainder. Unlike an ordinary checksum (where addition is commutative), CRC is highly sensitive to the data pattern.
2. AUTOSAR's Crc library gives five entry points and four widths: CRC8 (0x1D) for E2E P01, CRC8H2F (0x2F) for E2E P02 and also usable as a second check layer to avoid sharing holes with CRC8, CRC16 (0x1021) for P05/P06, CRC32 (0x04C11DB7) as the Ethernet standard, and CRC32P4 (0xF4ACFB13) exclusively for E2E Profile 4.
3. According to AUTOSAR's selection notes, CRC32P4 targets CAN bus failure modes; Hamming distance ≥ 6 (100% detection of any 5-bit error) is a coding-theory result and the mathematical cornerstone of ASIL D steering/braking.
4. A hardware CRC engine can cut CRC32 over 256 bytes to 3 µs, about 3× faster than software table lookup and 16× faster than bit-by-bit, and modern automotive MCUs all integrate one.
5. SHA-256 is unsuitable as a CRC replacement in embedded real-time systems: 2 KB code size, 10 MB/s software speed, and endianness compatibility issues are unacceptable in a 10 ms control loop.
