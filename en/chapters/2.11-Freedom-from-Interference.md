# 2.11 Freedom from Interference: The Engineering Blood-Brain Barrier


## Scenario

Two things are running on your ECU.

The first is a QM-classified infotainment task (quality management, no safety requirements). It renders the navigation map, plays Bluetooth music, and occasionally writes a block of random data to some SRAM address because of a wild pointer. You don't even know the bug exists: infotainment feature tests never cover memory overruns, because as long as it doesn't crash, who cares?

The second is an ASIL D electric power steering control task. It reads the steering wheel torque sensor, computes the assistance curve, and drives a three-phase BLDC motor. If even one byte of this task's result is corrupted — one sign bit in the control command flips — the steering direction can change from "turn left" to "turn right."

They run on the same MCU, share the same SRAM, and are scheduled by the same RTOS.

Then a question drives into your spine like a needle: **can the infotainment task's wild-pointer bug contaminate the steering control task's data?**

If you answer "possibly," then by the standard the entire embedded software must be treated at the highest ASIL, unless the software components satisfy the criteria for coexistence and achieve freedom from interference. If you answer "impossible, I have freedom from interference," then how do you guarantee it?

Part 6 of ISO 26262 gives the answer to this question, and it gives it in a way you cannot negotiate.

## Freedom from interference (FFI): the definition

ISO 26262 defines freedom from interference (FFI) as: **the failure of an element does not lead to a violation of the safety requirements of another element.** The key words are "between elements." It is not about protecting a software module from its own defects. It is about protecting a software module from **other** software modules, especially low-ASIL or no-ASIL modules.

The annex on freedom from interference in ISO 26262-6 groups interference between software elements into three categories:

### Category 1: Timing and Execution

This is interference about "time." A faulty task can destroy the real-time behavior of a safety-critical task in the following ways:

- **Blocking**: a low-priority QM task holds a mutex or spinlock, so a high-priority ASIL task cannot run.
- **Deadlock**: two tasks each wait for a resource the other holds, and the system stalls.
- **Livelock**: two tasks keep changing state without making real progress, for example two tasks repeatedly colliding and retrying while contending for bus access.
- **Incorrect allocation of execution time**: a task with no safety requirements unexpectedly enters an infinite loop or runs abnormally long, exhausts the CPU time budget, and delays or skips a safety task.
- **Incorrect synchronization**: the synchronization signals between two tasks (semaphores, event flags) are triggered wrongly or lost, and the execution flow of the safety task is disrupted.

### Category 2: Memory

This is interference about "space." A task can corrupt another task's memory space through legal memory accesses, or through illegal accesses caused by bugs:

- **Corruption of content**: a QM task writes through a wild pointer or an array overrun and overwrites an ASIL task's stack, global variables, or heap data.
- **Read/write inconsistency**: a QM task is halfway through writing shared data when an ASIL task reads an incomplete value, or the other way around.
- **Stale data**: a QM task stretches the update period of shared data abnormally, and an ASIL task uses an expired value.
- **Stack overflow**: a task's stack usage exceeds its allocated boundary, and the overflow spills into an adjacent memory region. That region may belong to another ASIL task.
- **Unauthorized access**: a QM task bypasses the operating system and accesses another task's memory or peripheral registers directly through absolute addresses.

### Category 3: Exchange of Information

This is interference about "communication." When two tasks exchange data through shared memory, message queues, IPC, or similar mechanisms, the following error types can occur. The annex on freedom from interference in ISO 26262-6 lists ten; here are the eight most common:

1. **Repetition of information**: the same message is sent twice, and the receiver executes the same instruction twice.
2. **Loss of information**: a message is overwritten or dropped in transit, and the ASIL task never receives critical data.
3. **Delay of information**: a message arrives later than designed, beyond what the FTTI allows.
4. **Insertion of information**: a message that should not appear on that channel is inserted.
5. **Masquerade or incorrect addressing of information**: a message is wrongly labeled with another sender's identity, and the receiver trusts an untrustworthy source.
6. **Incorrect sequence of information**: the correct content arrives in the wrong order, for example "open the window, then close it" becomes "close the window, then open it."
7. **Corruption of information**: message content is altered in transit or in storage, and CRC/E2E protection fails to detect it.
8. **Asymmetric information**: two receivers get different data from the same sender, possibly because an intermediate buffer refreshes inconsistently.

Before we go further into implementations, ISO 26262-6 has one "hard" requirement you cannot ignore (the informative annex only supplies examples for it):

> For ASIL D safety requirements, software partitioning must be supported by dedicated hardware features or equivalent means; the standard's example is an MPU (memory protection unit).

In other words, you cannot achieve ASIL D FFI merely by claiming "code reviews ensure that no buggy QM code accesses safety memory." You need **hardware isolation**, or a separate argument for "equivalent means."


## The immune-system metaphor: the blood-brain barrier

Before we get to engineering, let's build the core analogy.

The human body has two kinds of "channels." One is open: blood flows through the whole body, and every organ can draw nutrients and dump waste. The other is guarded with extreme care: around the brain and spinal cord sits the **blood-brain barrier (BBB)**.

The blood-brain barrier is not "a complete wall between brain and blood" — that would be fatal. What it does is: **only molecules that pass strict screening get through.** Oxygen can. Glucose needs a transport protein. Most serum proteins and large-molecule metabolic waste, pathogens, and toxins are turned away at the door.

This is living, selective isolation. It solves three problems at once:

- **Timing**: a spike of adrenaline in the blood does not immediately change neuronal firing. The BBB buffers the rate at which chemical signals are passed on.
- **Memory**: inflammatory factors can flood the bloodstream but cannot enter the brain. The BBB enforces "access control."
- **Communication**: the brain can talk to the body (through neurotransmitters and hormones), but only over a defined set of channels and message types — not "every chemical signal in the blood is broadcast between brain cells."

**This is the biological implementation of freedom from interference.** And the annex on freedom from interference in ISO 26262-6 asks you to build an engineering version of the blood-brain barrier on an MCU.


## Engineering the barrier: MPU and software partitioning

### Partitioning

Partitioning divides different software functions into separate execution environments that do not interfere with each other. In the AUTOSAR architecture, partitioning is implemented as OS-Applications. Each OS-Application is an independent set of schedulable entities with its own tasks, interrupt service routines, and resources.

The first step in partitioning is **ASIL separation**: all ASIL D tasks and ISRs go into one partition, ASIL B goes into another, and all QM tasks are thrown into a third. The interaction channels between them are strictly limited — like a brain that talks to the body only through specific neural pathways.

The software part of ISO 26262 draws one more key conclusion: **the OS itself must be developed to the highest ASIL of all partitions.** In other words, if your system has one ASIL D partition, your OS must be ASIL D even if there is a pile of QM tasks beside it.

That makes sense. The OS is the arbiter of all partitions. It manages context switches, interrupt dispatch, and resource allocation. If the OS itself is defective, every higher-level mechanism for freedom from interference can be bypassed through the OS. It's like a blood-brain barrier with a leak: no matter how healthy the brain cells are, it won't help.

### MPU configuration

The MPU (memory protection unit) is a component inside ARM Cortex-R cores and most Cortex-M cores; the number of regions and the register layout depend on the implementation, and the low-cost Cortex-M0 core doesn't have one at all. It lets you define multiple memory regions and specify access permissions (read/write/execute) and privilege level (privileged/user mode) for each.

In a real project configuration, you define the memory range each OS-Application "legitimately owns":

- ASIL D steering partition: owns the SRAM region 0x2000_0000 to 0x2000_7FFF (32 KB), read/write in privileged mode, read-only in user mode.
- ASIL B diagnostic partition: owns 0x2000_8000 to 0x2000_BFFF (16 KB), same access rules.
- QM infotainment partition: owns 0x2000_C000 to 0x2000_FFFF (16 KB).

**If any code in any partition tries to access a memory address it doesn't own, the MPU raises an exception immediately: a MemManage fault on Cortex-M, a Data Abort on Cortex-R5, with instruction-fetch violations going to Prefetch Abort. The hardware response is measured in nanoseconds: no software detection needed, no watchdog timeout needed.**

This means that even if a runaway pointer from an array overrun is loose in the QM partition's code, it can only destroy the QM partition itself. The MPU blocks every cross-boundary access in hardware.

### Timing protection

In some RTOSes that support temporal protection (such as the AUTOSAR OS), you can configure per task:

- Execution budget: the maximum CPU time for a single run of the task
- Lock budget: the maximum total time the task may hold all its locks
- Arrival rate: the minimum interval between activations of the task

If a QM task tries to exceed its execution budget, the OS timer interrupt fires and sees "this task still hasn't exited," and the timing protection mechanism can suspend or terminate the task outright and hand the CPU back to the scheduler.

That is the mechanism against timing interference: not relying on QM code to behave, but on the OS stepping in with a timer.

### Shared resource management

What if partitions need to communicate? You can't "forbid all communication" — the blood-brain barrier can't forbid glucose from entering the brain either. What you need is a **controlled, verified, protected communication channel**.

AUTOSAR provides the IOC (Inter-OS-Application Communicator) mechanism. Two partitions exchange data through a specially configured shared memory region, and the OS controls access to it: writes and reads are atomic (or protected by interrupt locks), the data format is fixed at compile time, and E2E protection (end-to-end protection: CRC + sequence counter + timeout detection) can be added to cover those eight communication failure modes.

**The key difference: the two tasks do not "see" each other's memory directly. They go through a third party (OS/IOC) as an intermediary.** That intermediary is itself verified (an ASIL D OS), so you can trust it not to pass the wrong data.


## What software partitioning demands of the hardware at ASIL D

ISO 26262-6 is explicit: for ASIL D, software partitioning must be supported by dedicated hardware features or equivalent means, and the hardware feature the standard names is the memory protection unit.

This is a hard threshold. If your MCU has no MPU (some low-cost Cortex-M0 parts, for example), then to run ASIL D tasks and QM tasks together on the same MCU you must produce a separate argument for "equivalent means," and code review plus coding guidelines usually cannot carry it. You either move to an MCU with an MPU, or put the ASIL D function on a separate MCU: physical isolation.

This also explains why, in real production programs, many Tier-1s deploy a dedicated MCU for the ASIL D steering function instead of running it on the same SoC as infotainment — even when the SoC theoretically supports an MPU. Engineering practice contains too much uncertainty. Physical isolation is the most thorough FFI.


## Summary

1. Freedom from interference (FFI) is the basis for coexistence of software at different ASILs (including QM), and the precondition for mixed-criticality software deployment. The independence ASIL decomposition needs must additionally rule out common-cause failures.
2. The annex on freedom from interference in ISO 26262-6 groups interference between software into three categories: timing and execution, memory, and exchange of information.
3. FFI in an ASIL D system depends on a hardware MPU, OS-level partitioning and timing protection, and controlled IOC communication channels.
4. The OS itself must be developed to the highest ASIL of all partitions.
