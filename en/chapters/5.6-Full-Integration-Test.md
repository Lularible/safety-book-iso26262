# 5.6 Full Integration Test: One Complete Safety-Loop Verification

## Scenario: Final Inspection at the Assembly Plant

At the assembly plant, every car coming off the line goes through a "final inspection line." The inspector isn't just looking for scratches in the paint: they're stepping on the brakes, turning the wheel, accelerating and decelerating, switching on the headlights, honking the horn — while watching hundreds of live data streams on the diagnostic screen. They are **activating every safety loop in the car**.

Did the ABS pump start? Are the brake pressure sensor readings right? When the brake lights came on, did the ESP controller's brake status flag flip? Did the CAN brake message carry the correct E2E header? Did the ABS controller's watchdog get fed properly throughout the braking cycle?

A competent final inspection line answers all these questions in 30 seconds.

That's what this chapter does: not unit tests of an isolated module (5.2 through 5.5 already did that), but stringing the four modules into a closed loop, simulating a complete safety monitoring scenario, and then deliberately sticking a knife in while it runs. You'll see your safety framework behave like the human immune system, intercepting the "intruder" the moment it appears.

## Architecture of the Integration Test

We need to simulate a simplified control system with three software components (tasks) and two data flows:

```
┌──────────────┐  E2E Protected   ┌──────────────┐  Safe Queue  ┌──────────────┐
│   Sensor     │ ───────────────→  │  Controller  │ ──────────→ │  Actuator    │
│   Task       │                   │  Task        │              │  Task        │
│              │                   │              │              │              │
│ checkpoint(0)│                   │ checkpoint(1)│              │ checkpoint(2)│
└──────┬───────┘                   └──────┬───────┘              └──────┬───────┘
       │                                 │                             │
       └──────────┬──────────────────────┴─────────────────────────────┘
                  │
           ┌──────┴──────┐
           │  Watchdog   │  ← monitors three checkpoints, each with its own deadline
           └─────────────┘
```

**Deadline configuration for the three tasks** (these numbers are teaching simplifications; in a real system deadlines come from schedulability analysis):

| Task | deadline_ms | tolerance_ms | max_misses | Physical meaning |
|------|-------------|--------------|------------|---------|
| Sensor | 100 | 20 | 3 | Sample sensor data every 100 ms |
| Controller | 80 | 15 | 2 | Run the control algorithm every 80 ms |
| Actuator | 120 | 30 | 3 | Produce one drive output every 120 ms |

**One pair of E2E contexts** (the sender and the receiver each hold one):

```c
safe_e2e_ctx_t sensor_tx = { .data_id = 1, .counter = 0 };  // sensor sender
safe_e2e_ctx_t sensor_rx = { .data_id = 1, .counter = 0 };  // controller receiver
// the two counters stay in sync during normal operation
```

**One safety queue**: the command channel from controller to actuator.

## Walking Through the Complete Test Code

Let's read `test_full_integration()` (in `main.c`) stage by stage:

### Phase 1: Infrastructure Initialization

```c
safe_wdg_t wdg;
safe_wdg_init(&wdg, on_timeout);
safe_wdg_register_slot(&wdg, 0, "sensor",    100, 20, 3);
safe_wdg_register_slot(&wdg, 1, "controller", 80, 15, 2);
safe_wdg_register_slot(&wdg, 2, "actuator",  120, 30, 3);
safe_wdg_start(&wdg);

safe_e2e_ctx_t sensor_tx = { .data_id = 1, .counter = 0 };
safe_e2e_ctx_t sensor_rx = { .data_id = 1, .counter = 0 };

safe_queue_t cmd_queue;
safe_queue_init(&cmd_queue);

printf("  Phase 1: Infrastructure initialized.\n");
```

At this point the watchdog's timerfd starts pulsing every 20 ms, the three slots are in place, and the E2E contexts and queue are ready. Nothing needs to be allocated: no threads created, no heap allocation. This is embedded-style initialization: **everything happens in stack and static memory**.

### Phase 2: 10 Normal Cycles

```c
for (int cycle = 0; cycle < 10; cycle++) {
    /* ── Sensor task ── */
    safe_wdg_checkpoint(&wdg, 0);  /* "I'm still alive" */

    uint8_t reading[8];
    snprintf((char *)reading, sizeof(reading), "S%03d", cycle);
    uint8_t frame[SAFE_E2E_MAX_DATA_LEN + SAFE_E2E_HEADER_SIZE];
    size_t  f_len = safe_e2e_protect(&sensor_tx, reading,
                                     strlen((char *)reading) + 1, frame);

    /* ── Controller task ── */
    safe_wdg_checkpoint(&wdg, 1);

    uint8_t rx_data[SAFE_E2E_MAX_DATA_LEN];
    size_t  rx_len;
    safe_status_t e2e_st = safe_e2e_check(&sensor_rx, frame, f_len,
                                          rx_data, &rx_len);
    if (e2e_st == SAFE_OK) {
        uint8_t cmd[SAFE_QUEUE_DATA_SIZE];
        snprintf((char *)cmd, sizeof(cmd), "CMD_%s", rx_data);
        safe_queue_add(&cmd_queue, cmd, strlen((char *)cmd) + 1);
    }

    /* ── Actuator task ── */
    safe_wdg_checkpoint(&wdg, 2);

    uint8_t exec_cmd[SAFE_QUEUE_DATA_SIZE];
    size_t  cmd_len;
    safe_queue_get(&cmd_queue, exec_cmd, &cmd_len);

    /* ── Simulated work + watchdog service ── */
    usleep(25000);  /* 25 ms of execution time */
    safe_wdg_service(&wdg);
}
```

There's a subtle design decision in this code: the `e2e_st == SAFE_OK` check **does not allow error propagation**. If the E2E check fails, the controller doesn't generate a command; it silently skips this cycle. This models the "silent drop" strategy of safety-critical systems: **better to miss one command than to generate a wrong command from wrong data.**

In a real system, "silent drop" has to be paired with timeout detection. If E2E checks fail for N consecutive cycles, the controller should trigger a fault response (such as entering limp mode). That's beyond safe-lite's teaching scope, but the design intent should be clear.

### Phase 3: Fault Injection and Detection

Phase 3 deliberately injects faults at three different safety layers:

**Fault A — corrupt the E2E frame's header byte (testing CRC detection)**

```c
uint8_t bad_msg[] = { 0xFF, 0xFF, 0xFF, 0xFF };
uint8_t bad_frame[SAFE_E2E_MAX_DATA_LEN + SAFE_E2E_HEADER_SIZE];
safe_e2e_protect(&sensor_tx, bad_msg, sizeof(bad_msg), bad_frame);
fault_bit_flip(bad_frame, sizeof(bad_msg) + SAFE_E2E_HEADER_SIZE, 10);
// flip bit 10 of the whole frame

uint8_t tmp[SAFE_E2E_MAX_DATA_LEN];
size_t  tmp_len;
safe_status_t st_a = safe_e2e_check(&sensor_rx, bad_frame, ...);
// expected: SAFE_CRC_MISMATCH
```

**Where does bit 10 land?** Bit 10 is in the frame's first byte, the header byte. Its high nibble holds Counter and its low nibble holds DataID. Change one of those bits and the DataID the receiver parses changes from 1 to 5. The CRC covers DataID, Counter, and payload, so once the header is touched the recomputed value won't match the stored one either. The frame gets stopped at the CRC gate and never reaches the later DataID comparison. Bit 0 lands in the CRC byte itself; change the stored value and the equation against the recomputed value breaks immediately. Both are detected, just for different reasons.

**Fault B — corrupt a queue entry's CRC (testing storage-layer detection)**

```c
uint8_t qdata[] = "Q_FAULT";
safe_queue_add(&cmd_queue, qdata, strlen((char *)qdata) + 1);
uint32_t last_idx = (cmd_queue.head + safe_queue_count(&cmd_queue) - 1)
                    % SAFE_QUEUE_MAX_ENTRIES;
fault_queue_crc_corrupt(&cmd_queue, last_idx);

safe_status_t st_b = safe_queue_get(&cmd_queue, tmp, &tmp_len);
// expected: SAFE_CRC_MISMATCH
```

The logic for locating `last_idx` deserves an explanation: `(head + count - 1) % MAX_ENTRIES` locates the last entry that was enqueued but not dequeued — the "Q_FAULT" entry just added. Then `fault_queue_crc_corrupt` flips the lowest bit of that entry's entry_crc. The next `get` recomputes the CRC and it necessarily mismatches.

**Fault C — starve a watchdog slot (testing task-layer detection)**

```c
for (int i = 0; i < 10; i++) {
    safe_wdg_checkpoint(&wdg, 0);  /* sensor alive */
    safe_wdg_checkpoint(&wdg, 1);  /* controller alive */
    /* slot 2 (actuator) deliberately gets no checkpoint */
    usleep(35000);  /* 35 ms */
    safe_wdg_service(&wdg);
}
// expected: SAFE_TIMEOUT; the watchdog calls the on_timeout callback
```

Key calculation: the actuator's deadline=120 ms, tolerance=30 ms → limit=150 ms, max_misses=3. Each loop sleeps 35 ms; the actuator's last_seen stays put and elapsed keeps accumulating.

**Trigger sequence**:
- Cycles 0–2: elapsed ≈ 60 / 95 / 130 ms, all below the 150 ms limit, miss_count=0
- Cycle 3: elapsed ≈ 165 ms, first crossing of the limit → miss_count=1
- Cycle 4: elapsed ≈ 200 ms → miss_count=2
- Cycle 5: elapsed ≈ 235 ms → miss_count=3, reaches max_misses → **FIRE**

Meanwhile sensor and controller keep checking in, proving this is an "actuator-specific fault," not a "system-level paralysis."

## The Complete Safety Loop Diagram

Unfolding the whole integration test structure gives us a complete **safety loop**:

```
                ┌─────────── Safety loop start ───────────┐
                │                                         │
                ▼                                         │
                                                          │
    ┌────────────────────────┐                            │
    │Sensor samples normally │                            │
    │      Data: "S003"      │                            │
    └───────────┬────────────┘                            │
                │                                         │
    ┌────────────────────────┐                            │
    │     E2E Protect()      │                            │
    │   → CRC8 + Ctr + DID   │                            │
    │ Frame: [CRC|hdr|data]  │                            │
    └───────────┬────────────┘                            │
                │                                         │
    ┌────────────────────────┐       ┌──────────────┐     │
    │      E2E Check()       │ ← ─   │   Fault A    │     │
    │CRC→DID→Counter all pass│       │   bit-flip   │     │
    └───────────┬────────────┘       └──────────────┘     │
                │                                         │
    ┌────────────────────────┐                            │
    │  Controller generates  │                            │
    │  Command: "CMD_S003"   │                            │
    └───────────┬────────────┘                            │
                │                                         │
    ┌────────────────────────┐       ┌──────────────┐     │
    │    safe_queue_add()    │ ← ─   │   Fault B    │     │
    │     + magic + CRC      │       │ CRC corrupt  │     │
    └───────────┬────────────┘       └──────────────┘     │
                │                                         │
    ┌────────────────────────┐                            │
    │    safe_queue_get()    │                            │
    │  magic + CRC verified  │                            │
    └───────────┬────────────┘                            │
                │                                         │
    ┌────────────────────────┐                            │
    │ Actuator runs command  │                            │
    └───────────┬────────────┘                            │
                │                                         │
    ┌────────────────────────┐                            │
    │ Watchdog checkpoint()  │                            │
    │all three tasks check in│                            │
    └───────────┬────────────┘                            │
                │                                         │
    ┌────────────────────────┐       ┌──────────────┐     │
    │   safe_wdg_service()   │ ← ─   │   Fault C    │     │
    │       → SAFE_OK        │       │  starvation  │     │
    └───────────┬────────────┘       └──────────────┘     │
                │                                         │
                └──────────── return to loop ──────────── ┘
```

When fault injection A takes effect → the loop is intercepted at the "E2E Check" node  
When fault injection B takes effect → the loop is intercepted at the "safe_queue_get" node  
When fault injection C takes effect → the loop is intercepted at the "safe_wdg_service" node  

**No single fault can pass through all three lines of defense to reach the actuator.**

## From safe-lite to Real AUTOSAR

If you started this chapter as a beginner with zero background, typed out all the code step by step, and saw 11 PASSes, you've already crossed from "heard about it" to "practiced it" in functional safety. When you face a real AUTOSAR toolchain, you'll find that this experience transfers directly:

| safe-lite | AUTOSAR | Similarity |
|-----------|---------|--------|
| `safe_wdg_checkpoint()` | `WdgM_CheckpointReached()` | 100% identical concept |
| `safe_e2e_protect()` | `E2E_P01Protect()` | 90% (the real library hands offsets, lengths, and DataID mode to a configuration struct; safe-lite keeps only data_id and counter) |
| `safe_e2e_check()` | `E2E_P01Check()` | 85% (safe-lite also has a state enum; the real library further breaks counter anomalies into duplicate, skipped, and pending-sync cases, and records the number of lost messages) |
| `safe_queue_add()` | Custom CDD or RTE queue | Same design intent |
| `fault_bit_flip()` | Hardware SEU injection | Same fault model, different injection method |

## Summary

1. The integration test strings the watchdog, E2E protection, and safety queue into a Sensor→Controller→Actuator closed loop. The three tasks each have their own deadline configuration and checkpoint slot.
2. Phase 2 shows the normal loop: sensor E2E Protect → controller E2E Check → command into the safety queue → actuator dequeues and consumes it. Every message goes through two layers of protection.
3. Phase 3 injects three kinds of fault at once: an E2E header bit flip (CRC_MISMATCH), an entry_crc flip in a queue entry (CRC_MISMATCH), and actuator watchdog starvation (TIMEOUT). All are intercepted precisely.
4. The "silent drop" strategy is a key design decision: when the E2E check fails, the controller generates no command. Better to miss a message than to make a decision from wrong data.
5. With 1,173 lines of C, zero dynamic allocation, a single thread, and only glibc as a dependency, it completes the full closed-loop verification of the "safety loop." The experience transfers directly to AUTOSAR's WdgM/E2E/SafeLib components.
