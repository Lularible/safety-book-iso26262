# 5.5 Fault Injection: How to Break Your System on Purpose to Verify Its Safety Mechanisms

## Scenario: The Logic of a Vaccine

In 1796, Edward Jenner injected an 8-year-old boy with cowpox pus (a virus that sickens cows but is mild in humans). The boy developed a slight fever and recovered within days. Two months later, Jenner injected him with deadly smallpox virus, and the boy was fine. It was the first recorded vaccination experiment in human history.

The logic of a vaccine is to use a known, controlled injury to test whether the immune system can withstand a genuinely lethal attack.

In functional safety this operation is called **fault injection**. It isn't meant to crash the system; it verifies that the safety mechanisms step in before the system crashes. You have to break the system first to prove it can protect itself.

Today you'll walk through safe-lite's seven fault-injection functions one by one. Five of them actually land on data in the tests, damaging the safety components you built in earlier chapters, so you can watch each line of defense respond. The other two are left for you to add fault models of your own.

## A Theoretical Framework for Fault Injection

Before we start coding, let's sort out the ISO 26262 concepts related to fault injection:

| Concept | Definition | Counterpart in safe-lite |
|------|------|-------------------|
| **Fault model** | An abstract description of a physical fault | bit_flip = SEU, counter_reset = ECU reset, magic_corrupt = RAM damage |
| **Fault injection point** | Where in the data flow the fault is injected | During E2E frame transfer, in queue storage, at a watchdog checkpoint |
| **Fault detection time (FDTI)** | The time from fault occurrence to detection | After a slot's silence passes deadline+tolerance, only a poll that still sees an overrun advances miss_count by one, and only reaching max_misses fires it; measured at about 235 ms in the integration test |
| **Fault coverage** | The proportion of fault types a safety mechanism can detect | CRC covers all single-bit errors + 99.6% of multi-bit errors |

Fault injection has to be statistically meaningful. At the hardware level the standard requires quantitative analysis of random hardware failures, measuring failure rate in FIT (failures in time, failures per 10⁹ hours) and using that to assess failure probability over the life cycle. In safe-lite's teaching environment we don't compute statistical coverage, but you need to build the awareness **at the level of your mind**: whenever you implement a safety mechanism, ask yourself immediately, "which physical phenomena can bypass this mechanism?"

## The Injection Functions in Detail

### 3.1 fault_bit_flip() — Simulating a Single-Event Upset (SEU)

```c
void fault_bit_flip(uint8_t *buf, size_t buf_len, size_t bit_offset)
{
    size_t byte_idx = bit_offset / 8;
    size_t bit_idx  = bit_offset % 8;
    if (byte_idx >= buf_len) return;
    buf[byte_idx] ^= (uint8_t)(1U << bit_idx);
}
```

**The physical phenomenon behind it**: in space and at high altitude, energetic neutrons or α particles strike SRAM cells, and the injected charge can flip the cell's state. In automotive electronics, although ground-level neutron flux is far below space, at advanced process nodes (≤28 nm) the single-event upset (SEU) rate has risen from "negligible" to "must be considered in the safety analysis."

**Expected detection mechanism**: the flip lands in the data area of an E2E frame → the recomputed CRC doesn't match → SAFE_CRC_MISMATCH.

**Test example**:
```c
uint8_t frame[] = { 0xB8, 0x42, 0xAA, 0xBB, 0xCC, 0xDD };
// CRC=0xB8, Header=0x42(Ctr=4,DID=2), payload=AA BB CC DD

fault_bit_flip(frame, 6, 27);
// flip bit 27: frame[3]=0xBB, bit 3 flips → 0xB3
// new frame: B8 42 AA B3 CC DD
// safe_e2e_check() returns SAFE_CRC_MISMATCH
```

Note: if the flip lands in the CRC byte itself (bits 0–7), it's still detected. The receiver recomputes the CRC from DataID, Counter, and payload, then compares it with the byte stored in the frame; the stored value has changed, so the equation naturally fails. If the flip lands in the Header byte (bits 8–15), the CRC also mismatches, because the Header is part of the CRC input.

### 3.2 fault_corrupt_byte() — Simulating EMI / Voltage Droop

```c
void fault_corrupt_byte(uint8_t *buf, size_t buf_len, size_t byte_offset)
{
    if (byte_offset >= buf_len) return;
    buf[byte_offset] = 0xFF;  /* All-ones wedge */
}
```

**The physical phenomenon behind it**: electromagnetic interference (EMI) near high-power switching devices can couple onto signal lines and create a local voltage spike. If the spike lands in a data bus read/write cycle, the whole bus can be "pinned" all-ones (or all-zeros, depending on the pull-up/pull-down configuration), rewriting a byte entirely to 0xFF.

ALL-ONES (0xFF) as the fault value models stuck-at-1 faults: the bits on the data line are all pinned high. Aged flash, and DRAM row hammer landing on susceptible addresses, can both cause this kind of whole-block rewrite. It belongs to a different fault model from a single-bit flip: the former tests the CRC's ability to detect burst errors, the latter its ability to detect discrete soft errors. An 8-bit CRC detects all burst errors up to 8 bits long, so "a whole byte rewritten" falls inside its guaranteed coverage.

### 3.3 fault_counter_reset() — Simulating an Unexpected ECU Reset

```c
void fault_counter_reset(safe_e2e_ctx_t *ctx)
{
    ctx->counter = 0;
}
```

**The physical phenomenon behind it**: an automotive ECU can reset unexpectedly during operation for many reasons — a brownout reset (BOR) from a power transient, a watchdog reset, or a software-triggered external reset. After the reset, the ECU's RAM is reinitialized (or at least some regions are zeroed), and the E2E counter starts from zero.

**The receiver's view**: before the reset the receiver had received counter=8. After the reset, the sender starts again at counter=1. The receiver computes:
```
diff = (1 - 8) & 0x0F = 9  →  9 > 8 (window size) → SAFE_COUNTER_ERROR
```
That's why a Counter error should be reported even when the data received is correct (CRC passes, DataID matches). The error tells the system "the sender went through some abnormal event." Even if the current message's content is correct, the consistency of the historical state has been broken.

### 3.4 fault_queue_magic_corrupt() — Simulating Wild-Pointer Damage

```c
void fault_queue_magic_corrupt(safe_queue_t *q, uint32_t entry_index)
{
    q->entries[entry_index].magic = 0xBAADF00D;
}
```

0xBAADF00D is a famous debugging magic number (leet-speak for "bad food"), widely used in Microsoft's and Apple's development toolchains. It's chosen over 0x00000000 or 0xFFFFFFFF because **it's unlikely to appear by accident**. A zeroed memory region is 0x00000000, not 0xBAADF00D. If magic validation passes on a zeroed entry, your magic value is badly chosen — either it's 0, or you picked a value that collides easily.

### 3.5 fault_queue_crc_corrupt() — Simulating a Bit Flip After the CRC

```c
void fault_queue_crc_corrupt(safe_queue_t *q, uint32_t entry_index)
{
    q->entries[entry_index].entry_crc ^= 0x01;
}
```

This fault model corresponds to a very specific scenario: **write ordering on shared memory in a multi-core system**. Suppose core A writes the data field, then computes and writes entry_crc, but core B's cache writeback flushes data+entry_crc to DDR as a whole. If the cache controller's write combining merges two adjacent cache lines of the entry into one burst write, and the CRC happens to sit on the boundary between the two lines... that's just one of many microarchitectural faults that can cause "CRC and data damaged independently."

### 3.6 fault_queue_metadata_corrupt() — Simulating a Race Condition

```c
void fault_queue_metadata_corrupt(safe_queue_t *q)
{
    q->head = (q->head + 3) % SAFE_QUEUE_MAX_ENTRIES;
}
```

Why +3 rather than +1 or some fixed value? Because if head+1 happens to point at a valid entry (the next entry to consume also happens to be valid), validate() might not detect the problem immediately. The entry it fetches is correct in both CRC and magic, but it's the "wrong entry" for the queue semantically. +3 sends head into an unknown region and raises the detection probability.

This is an important fault-injection principle: **don't inject faults that are guaranteed to be detected; inject the ambiguous faults near the detection boundary.** If a test can only catch the most obvious faults, you can't be confident it's equally reliable under real-world marginal conditions.

### 3.7 fault_wdg_starvation() — Simulating a Task Deadlock

```c
void fault_wdg_starvation(safe_wdg_t *wdg, int slot_id)
{
    (void)wdg;
    (void)slot_id;
    /* deliberately empty: the "fault" is not calling checkpoint */
}
```

This function is a design joke. It does nothing, because "task deadlock" is itself **the absence of behavior**, not damage to some memory location. The only way to detect a watchdog timeout is to **stop calling `safe_wdg_checkpoint()`**, and that's a test-code-level action, not something a fault-injection function can "inject."

In the integration test we see:
```c
for (int i = 0; i < 10; i++) {
    safe_wdg_checkpoint(&wdg, 0);  // slot 0 normal
    safe_wdg_checkpoint(&wdg, 1);  // slot 1 normal
    // slot 2 deliberately gets no checkpoint ← this is the "injection"
    usleep(35000);
    safe_wdg_service(&wdg);
}
// → WATCHDOG TIMEOUT: slot 2 (actuator) unresponsive
```

## The Fault-Injection Integration Test

In `test_full_integration()` in main.c, we build a complete fault-injection scenario:

**Phase 1: Initialize the safety infrastructure**
```
Watchdog:   3 monitored slots (sensor/100 ms, controller/80 ms, actuator/120 ms)
E2E pair:   sensor → controller direction
Safety queue:  empty queue, used to buffer commands
```

**Phase 2: Run 10 normal cycles**
- The sensor samples data → E2E protection → the controller receives it (E2E check passes) → generates a command → enqueues it in the safety queue → the actuator dequeues and consumes it
- All 3 checkpoints execute on every cycle
- At the end the queue is empty (the consumer caught up with the producer)

**Phase 3: Inject and detect three faults**

| Step | Injection | Expected result |
|------|------|---------|
| Fault A | Bit flip in the E2E frame header (bit 10, landing in the DataID nibble) | safe_e2e_check() → CRC_MISMATCH |
| Fault B | Flip the entry_crc of a queue entry | safe_queue_get() → CRC_MISMATCH |
| Fault C | Stop the actuator's checkpoint for 300 ms | safe_wdg_service() → TIMEOUT |

**Output verification**:
```
Integration summary:
  E2E bit-flip detected:  YES
  Queue CRC corrupt detected: YES
  Watchdog timeout detected:  YES
```

All three green lights are on. Your safety monitoring framework correctly detected every injected fault type.

## Advanced Thoughts on Fault Injection

In a real system, fault injection happens at several levels:

| Level | Injection method | Tool | Purpose |
|------|---------|------|------|
| Physical | Heavy-ion beam / laser into SRAM cells | Particle accelerator | Verify SEU sensitivity and EDAC effectiveness |
| Hardware | Lower voltage / raise clock frequency / inject EMI | Environmental chamber | Verify hardware behavior under boundary conditions |
| Firmware | Register bit flips / DMA error injection | Debugger (JTAG/SWD) | Verify driver-layer error handling |
| Software | API-level fault injection (as in this section) | Test framework | Verify application-layer safety-mechanism coverage |
| System | Network faults / data corruption / timing disturbance | CAN jammer / timing fault injector | Verify the end-to-end safety loop |

safe-lite's fault injection sits at the **software level**. It's the easiest to understand and implement, but it's also the furthest from real physical phenomena. When you design a fault-injection plan for a real project, you have to decide: is this test meant to verify logical correctness (software injection is enough), or physical reliability (hardware/physical-layer injection is required)?

The quality of fault injection isn't measured by how many kinds of faults you inject. It's measured by how many faults you inject that the safety mechanisms can't detect. If a safety mechanism claims to protect the system, a good fault-injection engineer asks: "which fault models does your mechanism not cover?" Then they construct those fault models one by one and verify that they really do slip through. **The faults that go undetected are the ones you need to worry about.** They are the holes in your safety argument.

## Summary

1. Fault injection is functional safety's "vaccine mechanism": use known, controlled damage to verify that safety mechanisms step in before the system crashes. A safety mechanism that has never been tested is equivalent to one that doesn't exist.
2. The seven injections cover three kinds of safety component: `fault_bit_flip` and `fault_corrupt_byte` target E2E (simulating SEU/EMI), `fault_queue_magic_corrupt` and the others target the safety queue (simulating wild pointers/races), and `fault_wdg_starvation` targets the watchdog (simulating task deadlock).
3. The fault-injection principle is "inject the ambiguous faults near the detection boundary," not faults that are certain to be detected. Only that exposes the holes in the safety argument.
4. Counter-reset injection shows an important E2E property: even when the current message content is correct, a broken historical consistency should trigger an error. It tells the system "the sender went through something abnormal."
5. safe-lite's fault injection sits at the software level and is suited to verifying logical correctness. Real projects also need physical-layer and hardware-layer injection to verify physical reliability.
