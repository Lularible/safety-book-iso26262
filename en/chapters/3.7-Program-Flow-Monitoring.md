# 3.7 Program-Flow Monitoring: Did the Brain Skip a Step?

Your EPS (electric power steering) control task runs every 5 milliseconds. Its execution sequence is precisely four steps:

**CP1 — ReadSensors**: read raw steering wheel angle and torque sensor data over SPI.
**CP2 — CalculateTorque**: convert raw sensor values into physical quantities, compute the steering torque applied by the driver, and combine it with vehicle speed to compute assist torque.
**CP3 — ApplyLimits**: apply saturation (maximum 80 Nm), rate limiting (maximum 20 Nm/ms), and the temperature derating curve to the assist torque.
**CP4 — OutputCommand**: write the final steering assist command into the motor driver's PWM duty-cycle register.

This is a perfect linear sequence: each step's output is the next step's input, and none can be skipped. Skip CP2 (CalculateTorque), and CP3 receives last cycle's assist torque. Skip CP3 (ApplyLimits), and CP4 sends the raw, unclamped command straight to the motor driver. In theory, a software fault could make the motor deliver 300 Nm, enough to twist the steering wheel from center to full lock in 0.1 seconds.

On a muggy afternoon, the nightmare comes true.

The EPS control task has a local array `float32 tempBuffer[32]`, used for intermediate filtering in the torque calculation. Because a recursive call path is triggered under an extremely rare vehicle-speed sensor failure mode, stack usage exceeds the static-analysis limit. `tempBuffer[31]` overflows the top of the stack and happens to overwrite the return address in the stack frame.

When `CalculateTorque()` finishes, it does not return to its caller (the main task loop); it "returns" to the entry address of `OutputCommand()`. The CPU takes the tampered value from the return-address register and jumps to CP4, cleanly skipping CP3 (ApplyLimits).

The command the motor driver receives is a raw torque value that was never limited and may exceed the physically safe range. Worse, the skip is **silent**: the CPU did not crash, the WatchDog was not triggered, and the task is rescheduled 5 ms later, starting the next cycle at CP1...

And the only thin line of defense that may actually protect you is **program-flow monitoring**.

Traditional Alive Supervision can prove only that "the CPU is still running," not that "the CPU is running on the correct path." A completely crashed task cannot kick the dog, and that is the easiest case to detect. But a task that jumps locally executes every step, just skipping critical safety computation: if the skipped step has no separate alive supervision configured, Alive Supervision, which merely counts reports per cycle, may not catch it. That is why Logical Supervision is needed: it fills in sequence, checking "is the path correct?" while "did it run at all?" remains with alive supervision.

## WdgM's Algebraic Data Model

AUTOSAR's WdgM (Watchdog Manager) defines a complete program-flow monitoring framework. Its core data model has three layers:

**First layer: SupervisedEntity**
- can be a Task, a Runnable, or an interrupt service routine.
- each SupervisedEntity has its own monitoring configuration: local state, allowed checkpoint set, transition table.

**Second layer: Checkpoint**
- special marker points inserted into the code.
- WdgM provides the function `WdgM_CheckpointReached(SupervisedEntityId, CheckpointId)` to mark execution progress in code.
- checkpoints fall into three categories:
  - **StartCheckpoint**: the starting node of the program flow.
  - **FinalCheckpoint**: a terminating node that must be reached (such as the last step of task execution).
  - **intermediate Checkpoint**: marks neither start nor end, only an intermediate state.

**Third layer: Transition**
- defines whether a jump from one checkpoint to another is legal.
- the configuration table `Transitions[]` is really a set of source/destination checkpoint pairs, each with only two fields, `CheckpointIdSource` and `CheckpointIdDestination`; conceptually it can be viewed as a two-dimensional Boolean matrix: `Transitions[source][destination] = TRUE` means a transition from source CP to destination CP is allowed.

### Transition Table Example

Take our EPS task. The configuration table is:

```
Transitions[CP1_ReadSensors]  = {FALSE, TRUE,  FALSE, FALSE}
Transitions[CP2_CalculateTorque] = {FALSE, FALSE, TRUE,  FALSE}
Transitions[CP3_ApplyLimits]  = {FALSE, FALSE, FALSE, TRUE}
Transitions[CP4_OutputCommand] = {FALSE, FALSE, FALSE, FALSE}  // terminal point
```

This table means:
- from CP1 you can go only to CP2 (CP1→CP3 and CP1→CP4 are not allowed)
- from CP2 you can go only to CP3
- from CP3 you can go only to CP4
- CP4 is the terminal point and cannot transition to any other checkpoint

When the stack overflow skips CP3 (ApplyLimits), the program flow becomes `CP2 → CP4`. WdgM checks Transitions[CP2][CP4] = FALSE—**illegal transition**. The system detects the anomaly.

## The Two Pillars of Supervision: Logic and Time

Logic supervision (is the program flow correct?) and time supervision (does the program finish within the specified time?) must work together; neither is optional. They are like two lines of defense in the immune system: antibody recognition of antigens (logic) and the inflammatory response (time pressure) must act together.

### Time Supervision (Deadline Supervision)

Deadline supervision is configured per pair of checkpoints, each with two time thresholds:
- **DeadlineMin (minimum execution time)**: the shortest time from the start checkpoint to the end checkpoint. If it is too fast (say, because a step was skipped), a fault has occurred.
- **DeadlineMax (maximum execution time)**: the longest allowed completion time. A timeout means the task is blocked, deadlocked, or in an unbounded loop.

In our EPS case:
- DeadlineMin = 1200 µs (the shortest time for a normal run of the four steps)
- DeadlineMax = 5000 µs (the 5 ms period)

If a stack overflow jumps to CP4, execution time may be only 800 µs (skipping CP2 and CP3, the heaviest CPU load). 800 < 1200 → below DeadlineMin → fault.

### Logic Supervision (Logical Supervision)

WdgM maintains state variables for each SupervisedEntity:
- **PreviousCheckpointId_internalLogic**: the ID of the last checkpoint reached.
- **IsInternalGraphActive**: whether a program flow graph is currently active (set to TRUE after the StartCheckpoint).

Algorithm pseudocode:

```c
void WdgM_UpdateLocalStatus(SupervisedEntityId seId, CheckpointId cpId) {
    // 1. If this is the start checkpoint
    if (IsStartCheckpoint(seId, cpId)) {
        if (IsInternalGraphActive(seId)) {
            // The graph is already active but another start point arrived = flow restarted without terminating normally
            ReportFault(seId);
        }
        ActivateGraph(seId);
        SetPreviousCheckpoint(seId, cpId);
        return;
    }

    // 2. If this is not the start checkpoint but the graph is not active
    if (!IsInternalGraphActive(seId)) {
        // Did not start from the start point = abnormal program flow
        ReportFault(seId);
        return;
    }

    // 3. Check whether the transition is legal
    CheckpointId prevCp = GetPreviousCheckpoint(seId);
    if (!IsTransitionValid(seId, prevCp, cpId)) {
        // Illegal transition!
        ReportFault(seId);
        return;
    }

    // 4. Update state
    SetPreviousCheckpoint(seId, cpId);

    // 5. If this is the final checkpoint
    if (IsFinalCheckpoint(seId, cpId)) {
        // Reaching the final checkpoint closes the program flow graph
        DeactivateGraph(seId);
    }
}
```

The design of the transition table is essentially compressing infinitely many erroneous execution paths into a finite state space. The number of possible execution flows in a program is astronomical. But by inserting n checkpoints and m legal transitions, we classify all possible paths into "legal paths" (present in the transition table) and "illegal paths" (absent). This is not enumerating every error; it is defining "what is right" and treating every deviation as a fault.

## The External Watchdog: The Immune System's Second Line of Defense

WdgM performs logic supervision and time supervision. But WdgM itself runs on the main MCU. If the main MCU stops completely (clock failure, power dip, total memory corruption), WdgM cannot perform supervision either.

At that point you need an **external watchdog**, a monitor chip independent of the main MCU (such as the Infineon TLF35584 system basis chip or the NXP PF5020 power management chip; the exact part numbers and interfaces come from chip manuals, and this repository has no corresponding driver), communicating with the main MCU through a challenge-response protocol.

### How the Challenge-Response Protocol Works

1. The external watchdog (WD) generates a pseudo-random number and sends it to the main MCU over the SPI/WDI line.
2. The main MCU's SPI driver receives this "challenge" and passes it to the application-layer response computation code.
3. The scheduler calls `WdgM_MainFunction()` periodically; it first evaluates alive supervision, then aggregates the local states of all SupervisedEntities.
4. WdgM aggregates all local states into one global state (OK / FAILED / EXPIRED / STOPPED / DEACTIVATED).
5. The main MCU computes the response value (for example, a CRC over the challenge data + global state) and sends it back to the external watchdog.
6. The external watchdog verifies the response:
   - if the CRC does not match (the global state is inconsistent, meaning a software logic fault) → trigger a reset.
   - if the CRC is correct but the global state is FAILED → trigger a reset.
   - if the CRC is correct and the global state is OK → reset the watchdog timer.
   - if no response arrives before the timeout → trigger a reset.

The clever part of this challenge-response mechanism is that the main MCU must not only be "alive" (able to answer) but also "awake" (answer correctly). It is like antigen-presenting cells (APCs) in the immune system: they must not only exist, they must correctly display the MHC-antigen complex before T cells consider everything normal. If an APC displays the wrong antigen, or displays nothing at all, the immune system treats it as "infected" and clears it.

## Complex Program Flow in a Real Scenario

Real program flow is much more complex than a simple linear sequence. Consider a complex control algorithm with branches and loops:

### Scenario: Brake Force Distribution in a Braking System

```
StartCP = CP1_ReadWheelSpeeds

CP1_ReadWheelSpeeds → CP2_FilterSpeedData
CP2_FilterSpeedData → CP3_CalculateSlipRatio

CP3_CalculateSlipRatio [SlipRatio_OK] → CP5_ApplyBrakePressure
CP3_CalculateSlipRatio [SlipRatio_HIGH → EBD must reduce rear-axle pressure] → CP4_ApplyEBD
CP4_ApplyEBD → CP5_ApplyBrakePressure

CP5_ApplyBrakePressure → CP6_VerifyPressureFeedback (FinalCP)
```

Transition table:
```
Transitions[CP3][CP4] = TRUE  // branch 1: EBD path
Transitions[CP3][CP5] = TRUE  // branch 2: normal path
Transitions[CP3][CP2] = FALSE // backward jumps are not allowed!
```

WdgM supports this kind of directed acyclic graph (DAG), because its transition table allows one source to have multiple legal destinations. As long as every step of the actual execution path is in the transition table, it is legal. WdgM does not care about the program's internal logic; it cares only whether "which road you took" is on the allowed map.

### Handling Loops

What if the program needs to reach the same checkpoint repeatedly in a loop? For example:

```
CP1 → CP2 → CP3 → CP2 → CP3 → CP2 → CP3 → CP4 (FinalCP)
```

WdgM allows self-loops to be defined in the transition table:
```
Transitions[CP2][CP2] = FALSE
Transitions[CP2][CP3] = TRUE
Transitions[CP3][CP2] = TRUE  // allow returning to CP2
```

That makes CP2→CP3→CP2→CP3 legal. WdgM's logic supervision itself does not limit the number of loop iterations; the iteration count is constrained by alive supervision's expected count and its min/max margins.

## Detection Capability and Missed-Detection Cases

Program-flow monitoring is not a silver bullet; it has detection limits too:

**Faults it can detect**:
1. illegal program jumps (jumping to the wrong checkpoint)
2. skipping critical steps (jumping from CP2 to CP4)
3. program flow that does not start at the start point
4. a missing required terminal point
5. execution timeout (Deadline Supervision)
6. execution too fast (below DeadlineMin)
7. external watchdog timeout

**Faults it cannot detect**:
1. Checkpoint markers reached correctly, but the computation logic between checkpoints is wrong (for example, the limit function uses the wrong threshold internally: the program path is correct, the data result is wrong). This needs E2E protection and other data-integrity measures.
2. A jump that happens to land on the address of the start function (skipping no checkpoint). This needs the external watchdog's time verification.

Program-flow monitoring solves the control-flow integrity (CFI) problem. Detection granularity depends on checkpoint insertion density: more checkpoints means finer resolution, but also more overhead. In practice, checkpoints are usually inserted at the entry and exit of each safety-related software partition.

Through the checkpoint-transition model, WdgM constrains the possible execution paths of the monitored program to a predefined legal set. But it can verify only path correctness, not data correctness. CRC and E2E protection handle data integrity; WdgM handles path integrity. They must work together.

## Summary

1. Program-flow monitoring (Logical Supervision) defines legal execution paths through the checkpoint-transition model. An illegal CP2→CP4 jump caused by a stack overflow is caught by the WdgM transition table; if the skipped step also has alive supervision configured, the report count may catch it—what alive supervision truly cannot see is a path whose count is sufficient but whose order is wrong.
2. Deadline Supervision and Logical Supervision work together: DeadlineMin prevents execution that is too fast (skipping computation steps), and DeadlineMax prevents timeout (deadlock or blocking).
3. WdgM maintains each Supervised Entity's PreviousCheckpointId and program-flow graph activation state. Any transition not in the transition table triggers a fault immediately; an illegal start point or a missing terminal point is also detected.
4. Through the challenge-response protocol, the external watchdog verifies not only that the main MCU is "alive" but that it is "awake"—the WdgM global state is encoded into the CRC response, and a software-stack fault produces a wrong response that triggers a hardware reset.
5. Program-flow monitoring's detection granularity depends on checkpoint insertion density; in practice checkpoints are placed at the entry and exit of safety-related software partitions. It governs path correctness; data correctness still needs E2E protection.
