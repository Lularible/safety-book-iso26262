# 5.2 A Minimal Watchdog: Alive Supervision from Scratch

## Scenario: A Late Heartbeat

The elevator in your building has to pass an annual inspection every month. The inspector runs a test that looks pointless: halfway through a ride, he pulls the main controller board's power plug. Guess what happens? Not free fall — the brake clamps the guide rail **within 150 milliseconds** of power loss, the car stops dead, and the passengers feel nothing worse than a slight jolt.

Behind that "150 milliseconds" stands an eternal guardian: the **watchdog timer**.

In the embedded world, the watchdog is the oldest and most basic safety mechanism. Its working principle is simple enough to state in one sentence: "If I don't get a signal from you within X milliseconds telling me you're still alive, I'll assume you're dead and do something about it." But this simple mechanism has kept countless runaway ECUs from turning into disasters.

Today you'll implement a teaching-grade watchdog from scratch on Linux. No hardware timer? No problem: the Linux kernel's `timerfd` mechanism provides a high-resolution monotonic clock in user space. No hardware reset line? No problem either: we replace "reset the system" with "invoke a user-registered callback." All the core logic — checkpoint registration, deadline monitoring, miss counting, the tolerance window — stays intact.

## Design Idea: Not a One-Shot Dog

Many introductory tutorials teach you to use a watchdog like this:

```c
// Wrong: single-timeout mode
void main_loop() {
    wdg_start(500);  // 500 ms timeout
    while (1) {
        do_work();
        wdg_kick();  // kick the dog every iteration
    }
}
```

This pattern has a fatal flaw: **it can only tell whether the whole system is alive. It can't tell which part has stopped breathing.**

Imagine a three-task system: sensor acquisition (100 Hz), control algorithm (200 Hz), CAN communication (50 Hz). If the CAN task deadlocks but the other two keep kicking the dog, a single-timeout watchdog **will never find out that CAN communication is dead**.

The right approach is **independent multi-slot supervision**. Each task registers its own "heartbeat period," and the watchdog tracks them separately:

```c
safe_wdg_register_slot(&wdg, 0, "sensor",    10, 2, 5);   // 10 ms ±2 ms, 5 consecutive misses = timeout
safe_wdg_register_slot(&wdg, 1, "controller", 5, 1, 3);   // 5 ms ±1 ms, 3 consecutive misses = timeout
safe_wdg_register_slot(&wdg, 2, "can_tx",     20, 5, 2);  // 20 ms ±5 ms, 2 consecutive misses = timeout
```

This is like an ICU monitor in a hospital: it doesn't take one heart-rate reading and call it done. It tracks heart rate, blood oxygen, and respiratory rate at the same time, and each parameter has its own alarm threshold and alarm delay. safe-lite's watchdog is that design philosophy expressed in C.

## Data Structures: safe_wdg_slot_t and safe_wdg_t

Open `safe_wdg.h`. First, the definition of a "slot":

```c
typedef struct {
    const char *name;          /* slot name, used in timeout log output */
    uint32_t    deadline_ms;   /* maximum allowed checkpoint interval (ms) */
    uint32_t    tolerance_ms;  /* extra tolerance (ms); deadline + tolerance = actual threshold */
    uint32_t    max_misses;    /* consecutive misses before a timeout is declared */
    uint32_t    miss_count;    /* current consecutive miss count */
    uint64_t    last_seen_us;  /* monotonic timestamp of the last checkpoint (µs) */
} safe_wdg_slot_t;
```

**Key design decision:** Why two parameters, `deadline_ms + tolerance_ms`, instead of one "total timeout"?

Because they **come from different places** during system design:
- **deadline_ms** comes from schedulability analysis: the controller task is designed to run every 5 ms, and that's the deadline.
- **tolerance_ms** comes from the **jitter range of the worst-case execution time (WCET)**. If the controller's WCET fluctuates between 3 ms and 5.5 ms, you need at least 0.5 ms of tolerance on top of the deadline.

Keeping them separate lets the configurator express two dimensions clearly: **scheduling intent** and **execution uncertainty**. Merging them into one parameter is simpler but throws away design information. When intermittent timeout alarms appear after integration, you can't tell whether it's the scheduler's problem (deadline set too tight) or execution jitter (tolerance too small).

The watchdog body:

```c
typedef void (*safe_wdg_timeout_cb_t)(int slot_id, const char *name);

typedef struct {
    int                   timer_fd;        /* Linux timerfd file descriptor */
    safe_wdg_slot_t       slots[SAFE_WDG_MAX_SLOTS];  /* up to 8 monitored slots */
    uint32_t              slot_count;      /* number of registered slots */
    safe_wdg_timeout_cb_t on_timeout;      /* timeout callback pointer */
    bool                  enabled;         /* whether the watchdog has been started */
    bool                  fired;           /* whether a timeout has fired (prevents repeat callbacks) */
} safe_wdg_t;
```

The `fired` field is a safety-critical design decision. Once the watchdog has fired, `safe_wdg_service()` returns `SAFE_TIMEOUT` directly and never calls the callback again. This prevents a second injury while the system is already in an abnormal state — for example, re-triggering a reset sequence that is already in progress.

## Init and Start: Using timerfd

```c
safe_status_t safe_wdg_init(safe_wdg_t *wdg, safe_wdg_timeout_cb_t cb)
{
    memset(wdg, 0, sizeof(*wdg));
    wdg->timer_fd = timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK);
    if (wdg->timer_fd < 0) {
        perror("timerfd_create");
        return SAFE_ERROR;
    }
    wdg->on_timeout = cb;
    return SAFE_OK;
}
```

**Why CLOCK_MONOTONIC?** Because the watchdog's timeout decision must not be affected by system time adjustments. If an administrator changes the wall clock (`CLOCK_REALTIME`), you definitely don't want the watchdog to fire falsely or miss a real timeout. `CLOCK_MONOTONIC` increases monotonically from boot and is unaffected by NTP synchronization or manual time changes. This matches the design intent of driving a hardware watchdog from an independent RC oscillator in production systems.

The `TFD_NONBLOCK` flag ensures the `read()` in `safe_wdg_service()` won't block the main loop. If no timerfd expiration is pending, `read()` returns `EAGAIN` immediately and the main loop continues with other safety checks.

Watchdog start:

```c
safe_status_t safe_wdg_start(safe_wdg_t *wdg)
{
    struct itimerspec its;
    its.it_interval.tv_sec  = 0;
    its.it_interval.tv_nsec = 20 * 1000 * 1000;  /* 20 ms service period */
    its.it_value            = its.it_interval;

    if (timerfd_settime(wdg->timer_fd, 0, &its, NULL) < 0) {
        perror("timerfd_settime");
        return SAFE_ERROR;
    }
    wdg->enabled = true;
    return SAFE_OK;
}
```

**20 ms is a double-edged sword.** A shorter period (say 1 ms) gives finer deadline-monitoring resolution but burns too much CPU. A longer period (say 100 ms) may detect the overrun only tens of milliseconds after the actual deadline. That window is long enough for a runaway actuator to do physical damage. 20 ms is a reasonable compromise between Linux user-space scheduling resolution (on the order of milliseconds, depending on load and kernel configuration) and real-time requirements.

**PRODUCTION comparison:** In a real ECU, the `timerfd_settime()` call is replaced by register writes to the hardware watchdog peripheral: initialize the independent clock source, configure window mode. Some automotive MCUs' watchdog peripherals can raise an interrupt before the timeout actually resets the chip, giving the system one last chance to save itself (for example, write critical logs to NVRAM) before the hardware reset.

## The Checkpoint Mechanism: Who Is Still Alive?

`checkpoint` is the watchdog system's core verb. When a task finishes one of its periods, it "clocks in":

```c
safe_status_t safe_wdg_checkpoint(safe_wdg_t *wdg, int id)
{
    struct timespec now;
    clock_gettime(CLOCK_MONOTONIC, &now);
    wdg->slots[id].last_seen_us = (uint64_t)now.tv_sec * 1000000ULL
                                + (uint64_t)now.tv_nsec / 1000ULL;
    wdg->slots[id].miss_count = 0;  /* reset the consecutive miss count */
    return SAFE_OK;
}
```

This code does two things:
1. **Record the timestamp.** Save the current monotonic clock in microseconds. The `tv_nsec / 1000` is necessary: `timespec` gives nanosecond resolution, but we only need microseconds.
2. **Reset miss_count.** Every successful checkpoint is a "vote of confidence" in the system's health. It zeroes that slot's miss_count and wipes the slate clean. What actually blocks a "resurrection" is the `fired` latch: once set, `safe_wdg_service()` returns `SAFE_TIMEOUT` directly and doesn't even scan the slots.

**Slot registration** is a required step before use:

```c
safe_status_t safe_wdg_register_slot(safe_wdg_t *wdg, int id,
                                     const char *name,
                                     uint32_t deadline_ms,
                                     uint32_t tolerance_ms,
                                     uint32_t max_misses)
{
    safe_wdg_slot_t *s = &wdg->slots[id];
    s->name          = name;
    s->deadline_ms   = deadline_ms;
    s->tolerance_ms  = tolerance_ms;
    s->max_misses    = max_misses;
    s->miss_count    = 0;
    s->last_seen_us  = 0;
    wdg->slot_count++;
    return SAFE_OK;
}
```

Note: `last_seen_us = 0` is a sentinel. In `safe_wdg_service()`, if a slot's `last_seen_us` is still 0, the task has never checked in once, and the supervision logic skips that slot. This avoids the embarrassment of "the watchdog barking right after boot." During startup every task needs time to initialize, and that shouldn't count as a timeout.

## Core Logic: safe_wdg_service()

This is the heart of the whole watchdog module. It must be called periodically (every 20 ms in our design):

```c
safe_status_t safe_wdg_service(safe_wdg_t *wdg)
{
    /* 1. Check preconditions */
    if (wdg == NULL || !wdg->enabled) return SAFE_NOT_INITIALIZED;
    if (wdg->fired) return SAFE_TIMEOUT;  /* already fired; do not check again */

    /* 2. Drain the timerfd event: this is the "clock source" */
    uint64_t expirations;
    ssize_t  n = read(wdg->timer_fd, &expirations, sizeof(expirations));
    if (n < 0 && errno != EAGAIN) {
        perror("read(timer_fd)");
        return SAFE_ERROR;
    }

    /* 3. Get the current time */
    struct timespec now;
    clock_gettime(CLOCK_MONOTONIC, &now);
    uint64_t now_us = (uint64_t)now.tv_sec * 1000000ULL
                    + (uint64_t)now.tv_nsec / 1000ULL;

    /* 4. Walk all registered slots and check for timeouts */
    for (uint32_t i = 0; i < SAFE_WDG_MAX_SLOTS; i++) {
        safe_wdg_slot_t *s = &wdg->slots[i];
        if (s->name == NULL) continue;       /* not registered → skip */
        if (s->last_seen_us == 0) continue;  /* no checkpoint yet → skip the startup phase */

        uint64_t elapsed_ms = (now_us - s->last_seen_us) / 1000ULL;
        uint64_t limit_ms   = (uint64_t)s->deadline_ms + (uint64_t)s->tolerance_ms;

        if (elapsed_ms > limit_ms) {
            s->miss_count++;
            if (s->miss_count >= s->max_misses) {
                wdg->fired = true;
                if (wdg->on_timeout != NULL) {
                    wdg->on_timeout((int)i, s->name);
                }
                return SAFE_TIMEOUT;
            }
        } else {
            s->miss_count = 0;  /* timely checkpoint → clear the counter */
        }
    }
    return SAFE_OK;
}
```

**Line-by-line look at the core decision logic:**

```
elapsed_ms = now - last_seen
limit_ms   = deadline + tolerance

if elapsed_ms > limit_ms:
    miss_count++
    if miss_count >= max_misses:
        FIRE
else:
    miss_count = 0
```

The three parameters form a **three-level defense net**:

| Level | Parameter | Role |
|------|------|------|
| First | deadline_ms | The basic scheduling expectation — the task should complete one period within this time |
| Second | tolerance_ms | Allowed execution jitter — an occasional WCET overrun should not alarm immediately |
| Third | max_misses | False-positive resistance — an occasional scheduling delay should not trigger a safety response |

A concrete example: a controller task with deadline=5 ms, tolerance=1 ms, max_misses=3.
- Case A: the task checks in every 5.5 ms → elapsed=5.5 ms, limit=6 ms → **no miss** (tolerance absorbed it)
- Case B: the task occasionally takes 7 ms → elapsed=7 ms, limit=6 ms → miss_count=1 (but max_misses isn't reached yet)
- Case C: three times in a row over 6 ms → miss_count=3, reaches max_misses → **FIRE**

That's the art of the **tolerance trade-off**: `tolerance_ms` too small and the system raises false alarms constantly; too large and real fault detection is delayed. `max_misses` too small and a single scheduling spike triggers a safety response; too large and a deadlocked task takes a long time to detect.

**In ISO 26262 terms,** the time from fault occurrence to timeout firing must fall inside the safety goal's **fault tolerant time interval (FTTI)**. That time is set jointly by deadline, tolerance, max_misses, and the service period. After a slot goes silent, the first overrun is only judged once deadline + tolerance has fully elapsed; after that, each `safe_wdg_service()` call advances `miss_count` by one. With a 20 ms service period, a slot with deadline=100, tolerance=20, and max_misses=3 first crosses the limit at about 140 ms of silence and fires at about 180 ms. If a safety goal requires reaching a safe state within 200 ms, all four parameters have to fit inside that 200 ms budget.

## Integration Tests: Verifying Watchdog Behavior

`main.c` has two key tests:

**Test 1: baseline — a healthy system must not trigger the watchdog**

```c
safe_wdg_register_slot(&wdg, 0, "main_loop", 200, 50, 2);
safe_wdg_register_slot(&wdg, 1, "comm_task", 500, 100, 3);
safe_wdg_start(&wdg);

for (int i = 0; i < 5; i++) {
    safe_wdg_checkpoint(&wdg, 0);
    safe_wdg_checkpoint(&wdg, 1);
    usleep(30000);  // 30 ms — far below every deadline
    st = safe_wdg_service(&wdg);
}
// expected: st == SAFE_OK
```

**Test 2: timeout detection — deliberately starve one slot**

```c
for (int i = 0; i < 20; i++) {
    safe_wdg_checkpoint(&wdg, 0);   // main_loop is still alive
    // slot 1 deliberately gets no checkpoint → starvation
    usleep(60000);  // 60 ms
    st = safe_wdg_service(&wdg);
    if (st == SAFE_TIMEOUT) break;
}
// expected: st == SAFE_TIMEOUT
// output: *** WATCHDOG TIMEOUT: slot 1 (sensor_task) unresponsive ***
```

Note the loop structure of test 2: the registered slots are `main_loop` (100, 20, 2) and `sensor_task` (150, 30, 2), and only slot 0 checks in each time; slot 1 is deliberately abandoned. Each iteration sleeps 60 ms. After a few periods, slot 1's `elapsed_ms` stays above `limit_ms` (sensor_task's limit = 150+30 = 180 ms), `miss_count` accumulates to `max_misses` (2 here), and the watchdog fires.

The most misunderstood thing about a watchdog: it isn't "performance monitoring." It's "liveness monitoring." Many engineers put the checkpoint after some complex computation and then set a "big enough" deadline. If the computation itself falls into an infinite loop, the checkpoint never gets called.

The right approach: put the checkpoint on the **simplest path**, such as the top of the scheduler's main loop. Proving "the program counter is still in a reasonable address range" is enough. Whether the complex business logic completed is the upper application's job. The watchdog answers one binary question: **is this software component still executing instructions?**

## Summary

1. A multi-slot watchdog implements per-task alive supervision with three independent parameters — deadline, tolerance, and max_misses — avoiding the single-timeout mode's inability to locate the failed component.
2. `deadline_ms` comes from scheduling analysis (the task's expected period); `tolerance_ms` comes from WCET jitter. Configuring them separately preserves design-decision information.
3. `timerfd_create(CLOCK_MONOTONIC)` simulates a hardware watchdog's monotonic-clock behavior in Linux user space, unaffected by system time adjustments.
4. A checkpoint belongs on the task's simplest path (such as the top of the scheduler loop), not after complex computation, so an infinite loop can't prevent it from ever being called.
5. The time from fault occurrence to timeout firing must fall inside the safety goal's FTTI. That time is set jointly by deadline, tolerance, max_misses, and the service period: first wait out the full threshold, then count the remaining misses at the service-period rate.
