# 3.1 Watchdogs: Triple Supervision in the Thermoregulatory Center

11 p.m. The vehicle validation lab is down to the hum of server fans. Your domain controller has been running 72 hours of hot/cold cycling on the bench, and the CANoe trace window glows faintly in the dark. Then the green data stream you've watched for three days freezes all at once, and the EPS (electric power steering) messages disappear. You grab the scope probe and touch the CAN transceiver's TXD pin. Only garbage logic levels: no ACK, no error frames, nothing.

Your heart speeds up, but experience tells you this isn't a hardware fault. You attach the debugger. The PC sits at 0x08004F32, deadlocked. The 10 ms steering control task (OsTask_Steering) is blocked on `GetResource(Mutex_CAN_Tx)`, and that mutex is held by the 100 ms diagnostic task (OsTask_DiagLog). The diagnostic task is waiting for a DMA transfer-complete interrupt... but the DMA finished long ago; a higher-priority task just cleared the interrupt by mistake. Two tasks wait for each other, both frozen. The priority ceiling protocol was misconfigured, and the confusion in the OSEK OS is exposed in this moment.

If you were driving this car, the steering angle command would stick at that last 1.7° left turn. On a highway, that means you hit the guardrail in under two seconds. But the fault log you're reading has no real-world crash caused by a frozen steering command. Why? Because the instant the diagnostic task blocked, an RC oscillator completely independent of the Cortex-R5 was quietly counting. It knows nothing about mutexes and doesn't care about OCDS. It has one job: count 1000 clock cycles, then pull the /RESET pin low. It's at 970 now. Thirty microseconds left, and everything gets pulled back to a safe state.

Your ECU didn't die. It just ran a high fever. And the watchdog is the thermoregulatory center at the very bottom of the whole vehicle.

## The Nature of a Watchdog: A Survival Loop Independent of Consciousness

The human body has a precise temperature regulation mechanism: the hypothalamus continuously monitors blood temperature, and when body temperature exceeds the set point (about 37 °C), it triggers heat-loss responses—dilating skin vessels and starting the sweat glands. This mechanism has several key features: it is completely independent of your consciousness (you cannot change the temperature set point by willpower), it has its own sensors (temperature-sensitive neurons distributed through the hypothalamus), and it runs before every other system in the body.

The watchdog plays almost exactly the same role in an ECU. It uses a hardware timer completely independent of the CPU, usually driven by a dedicated RC oscillator, sharing no logic with the system clock. The timer counts down from some initial value, and each software "kick" (watchdog trigger) resets the counter. If the software fails to kick it in time for any reason—deadlock, infinite loop, interrupt storm, or wrong instruction execution caused by a voltage dip—the counter reaches zero, and the hardware reset circuit pulls the MCU straight back into reset.

Take the Infineon AURIX TC3xx family as a concrete example (the clock, register, and password details below come from the chip manual; this repository contains no watchdog driver we can verify against). Each TC3xx MCU contains an independent SWD (Safety Watchdog) module. Its clock source is an on-chip RC oscillator, nominal 100 kHz, accuracy ±15% (far worse than the ±1% of the system PLL, but a watchdog doesn't need accuracy—only independence). The SWD timeout period is set by a 16-bit reload register. At 100 kHz, the longest window is about 655 ms. That means your software has to kick the dog at least once every 655 ms.

```c
/* Key register operations to trigger the AURIX TC3xx SWD watchdog */
#define SWD_BASE_ADDR   0xF0036000UL
#define SWD_SRR_BYTE    (*(volatile uint32*)(SWD_BASE_ADDR + 0x00UL))

void Wdg_17_Scu_Trigger(void)
{
    /* Write the inverted password sequence to service the watchdog */
    SWD_SRR_BYTE = 0x000000BCUL;  /* Step 1: write access code 1 */
    SWD_SRR_BYTE = 0x00000043UL;  /* Step 2: write access code 2, reload the timer */
}
```

Notice the two values, 0xBC and 0x43. They are inverted bit patterns (0xBC = 10111100, 0x43 = 01000011), the bitwise complement of each other. That's no accident. The SWD hardware requires two consecutive writes whose values are bitwise inverses; otherwise the write is ignored. This design keeps a random bit flip in memory (say, an SRAM jump caused by a single-event effect) from kicking the watchdog by accident. A stray pointer that writes through memory and happens to put 0xBC into some variable is already a coincidence. Writing 0xBC and 0x43 precisely, twice in a row, is far less likely.

This is the first core principle of a watchdog: **hardware isolation**. The only interface between it and the CPU is those few trigger registers. Your motor control algorithm can compute any absurd torque command; your communication stack can send any illegal CAN frame. The watchdog doesn't care. It looks at one thing only: did you trigger it inside the time window?

## WdgM's Three Supervision Dimensions: More Than "Being Alive"

A watchdog is not just a low-level hardware driver (the Wdg Driver). The more important part is the watchdog manager above it (WdgM, Watchdog Manager). WdgM offers three supervision mechanisms on different dimensions. If you only use the most basic Alive Supervision, you're using 10% of what a watchdog can do.

### 2.1 Alive Supervision: Are You Still Alive?

Alive Supervision answers the most basic question: is the supervised software entity (Supervised Entity, SE) still running?

The implementation is simple: place checkpoints in the main loop or periodic processing of the supervised task. WdgM counts how many checkpoints were reported in each supervision cycle. If the count falls inside the closed interval from ExpectedAliveIndications − MinMargin to ExpectedAliveIndications + MaxMargin, the task is healthy.

In Vector's configuration, the ARXML parameters for Alive Supervision look like this:

```xml
<WDGM-ALIVE-SUPERVISION>
  <WDGM-EXPECTED-ALIVE-INDICATIONS>3</WDGM-EXPECTED-ALIVE-INDICATIONS>
  <WDGM-MIN-MARGIN>0</WDGM-MIN-MARGIN>
  <WDGM-MAX-MARGIN>1</WDGM-MAX-MARGIN>
  <WDGM-CHECKPOINT-REFS>
    <WDGM-CHECKPOINT-REF>SE_Steering_CP_Input</WDGM-CHECKPOINT-REF>
    <WDGM-CHECKPOINT-REF>SE_Steering_CP_Compute</WDGM-CHECKPOINT-REF>
    <WDGM-CHECKPOINT-REF>SE_Steering_CP_Output</WDGM-CHECKPOINT-REF>
  </WDGM-CHECKPOINT-REFS>
</WDGM-ALIVE-SUPERVISION>
```

This configuration means: in every supervision cycle, WdgM expects to receive exactly 3 or 4 alive indications. If it receives only 2 (below expected minus the minimum margin) or 5 (above expected plus the maximum margin), that's abnormal. Note what MaxMargin means: if a task somehow runs faster than expected (say, a timer misconfiguration or doubled interrupt frequency), that is detected too. Alive Supervision catches not only "can't run" but also "runs too fast."

But Alive Supervision has two fundamental limits. First, it cannot tell whether the execution flow took the correct path. A task can skip every critical computation, trigger the checkpoints, and spin idle; Alive Supervision won't fail it. Second, it is insensitive to time: it only needs enough checkpoints before the supervision cycle ends. A control algorithm with a 5 ms period can take 4.9 ms for a single run (it should take 1 ms) and still not trip, as long as it completes the required number of runs in the supervision cycle.

That's why you need Deadline Supervision.

### 2.2 Deadline Supervision: Did You Finish on Time?

Deadline Supervision measures the time between two checkpoints and checks whether it falls inside the configured minimum and maximum thresholds.

In the AUTOSAR OS context, time measurement uses the OS Counter—a hardware timer tick counter maintained by the operating system. Each Supervised Entity can define several transitions. Each transition names a Start Checkpoint and an End Checkpoint, plus the time window allowed between them.

```
  Task period = 10 ms
  ┌──────────────────────────────────────────────────┐
  │                                                  │
  ▼                                                  ▼
  CP_Start ────────────────► CP_Finish
   (t=0)      execution time     (t≤5 ms)
              Deadline: 5000 us
```

In the Vector DaVinci configuration, the core parameters for Deadline Supervision are:

```xml
<WDGM-DEADLINE-SUPERVISION>
  <WDGM-TRANSITIONS>
    <WDGM-TRANSITION>
      <WDGM-TRANSITION-ID>1</WDGM-TRANSITION-ID>
      <WDGM-TRANSITION-SOURCE-REF>SE_Steering_CP_Start</WDGM-TRANSITION-SOURCE-REF>
      <WDGM-TRANSITION-DESTINATION-REF>SE_Steering_CP_Finish</WDGM-TRANSITION-DESTINATION-REF>
      <WDGM-DEADLINE-MIN unit="us">100</WDGM-DEADLINE-MIN>
      <WDGM-DEADLINE-MAX unit="us">5000</WDGM-DEADLINE-MAX>
    </WDGM-TRANSITION>
  </WDGM-TRANSITIONS>
</WDGM-DEADLINE-SUPERVISION>
```

This configuration requires the time from CP_Start to CP_Finish to be between 100 µs and 5000 µs. The 100 µs minimum may look odd—why require that execution not be too short? Because when a task gets from CP_Start to CP_Finish in under 100 µs, the execution path was probably disrupted by an interrupt, or some critical computation was skipped. The minimum threshold of Deadline Supervision protects against "the program taking a shortcut."

Inside AUTOSAR, Deadline Supervision relies on the `GetElapsedValue()` interface provided by the OS. WdgM records the current tick when CP_Start fires, then takes the difference with the elapsed-value interface when CP_Finish fires, and compares it with the configured thresholds.

```
Time measurement process (AURIX STM timer as the OS Counter):

  CP_Start:  WdgM reads OsCounter = 0x0004A38F  (311,183 ticks)
  CP_Finish: WdgM reads OsCounter = 0x0004A5C7  (311,751 ticks)
  Difference: 568 ticks
  Assume STM frequency = 100 MHz → 568 * 10 ns = 5680 ns = 5.68 µs
  Verdict: 5.68 µs below the 100 µs lower bound → INCORRECT (executed too fast; the minimum threshold flags a suspicious shortcut)
```

### 2.3 Logical Supervision: Is Your Logic Flow Correct?

Neither Alive nor Deadline answers one question: did the program execute the correct path?

Logical Supervision introduces the idea of a **program flow graph**. A Supervised Entity passes through a series of checkpoints while it runs, and the transitions between those checkpoints form a directed graph. WdgM maintains a Transition Table defining every legal transition. Any transition not in the table immediately triggers a supervision failure.

```
  Program flow graph example: steering control task

          ┌─────────┐
          │Idle     │ ◄──────────────┐
          └────┬─────┘                │
               │                      │
               ▼                      │
          ┌─────────┐                 │
          │CP_Start │ (1)             │
          └────┬─────┘                │
               │                      │
               ▼                      │
          ┌─────────┐   normal path   │
          │CP_InpRd │ (2) ────────────┤
          └────┬─────┘                │
               │                      │
               ▼                      │
          ┌─────────┐   data fault    │
          │CP_Comp  │ (3) ────────────┘
          └────┬─────┘
               │
               ▼
          ┌─────────┐
          │CP_OutWr │ (4)
          └────┬─────┘
               │
               ▼
          ┌─────────┐
          │CP_End   │ (5)
          └─────────┘
```

The corresponding Transition Table:

| Source Checkpoint | Destination Checkpoint | Transition ID |
|---|---|---|
| CP_Start | CP_InpRd | 1 |
| CP_InpRd | CP_Comp | 2 |
| CP_InpRd | CP_Start | 3 (data fault, back off and re-read) |
| CP_Comp | CP_OutWr | 4 |
| CP_OutWr | CP_End | 5 |
| CP_End | CP_Start | 6 (next cycle) |

Any transition not in the table above (for example CP_Start→CP_OutWr, skipping input read and computation) triggers a WdgM Logical Supervision failure. That means even when your task looks "normal" at the Alive and Deadline levels—the CPU is executing code and the time is inside the window—WdgM catches it as soon as the execution path departs from what's expected.

Combining these three dimensions, WdgM builds layered, three-dimensional supervision of the software: Alive confirms the task is still running, Deadline confirms it hasn't timed out, Logical confirms it hasn't taken a wrong path. Together they cover almost every quantifiable health indicator of a software component.

## The Underlying Truth of the Hardware Watchdog

When you call `Wdg_17_Scu_Trigger()` from C, you think you're kicking the dog. What actually happens is much more complicated than you imagine.

The internal structure of the AURIX TC3xx Safety Watchdog (SWD) looks like this:

```
                    ┌──────────────────────────────────────────────────────┐
   100 kHz RC OSC ──► 16-bit down-counter                                  │
                    │                                                      │
   fSYS disable ───► SWD keeps working even if the system clock            │
                    │ disappears                                           │
                    │                                                      │
   Password check ◄──── SWD_SRR register (trigger interface)               │
      │                                                                    │
      │  wrong password sequence → timeout triggers reset                  │
      │                                                                    │
      ▼                                                                    │
   ┌──────────────┐                                                        │
   │ Window       │  window timing check                                   │
   │ comparator   │                                                        │
   │              │                                                        │
   │  kick too early ──► reset                                             │
   │  kick too late  ──► reset                                             │
   │  kick in window ──► reload counter                                    │
   └──────────────┘                                                        │
                    └──────────────────────────────────────────────────────┘
```

A watchdog has several operating modes:

**Timeout Mode**: the simplest mode. You only have to kick the dog before the counter reaches zero. This mode is the most common and the easiest to configure.

**Window Watchdog**: much stricter than timeout mode. The kick must happen inside a specified time window—neither too early nor too late. Picture a task with a 10 ms period that you expect to kick at 8–9 ms. If it kicks at 3 ms (too early, which means execution was abnormally fast and probably skipped some computation), the window watchdog rejects it and triggers a reset. If it kicks at 11 ms (too late, which means the task timed out), it also triggers a reset.

```
  Window watchdog timing diagram:

  service request
  allowed  │  forbidden │        allowed        │ forbidden
           │            │                       │
  ─────────┼────────────┼───────────────────────┼────────► time
  0 ms     2 ms         4 ms                  10 ms     12 ms
           │            │                       │
           too early    │                       too late
            → reset     │                       → reset
                        │
                        valid trigger window
```

Why do we need a window? Because a 10 ms task that finishes all its work in 3 ms has almost certainly skipped something—maybe the sensor read was skipped, maybe the fault-detection branch was bypassed. A window watchdog catches this kind of "the task ran but didn't do it right" fault.

**Fail-Safe Mode**: after the system enters a safe state, the watchdog can stay in a "triggered but not reset" state, letting the system move into the safe state under controlled conditions instead of a crude reset.

These modes match different operating phases of an automotive controller:
- normal driving: window mode, strict supervision
- initialization: timeout mode, allowing a longer startup time
- safe state: fail-safe mode, holding the safe state while waiting for the driver to take over

## WdgM Global Status and Fault Propagation

WdgM maintains a global state machine that aggregates the local states of all supervised entities:

```
  WDGM_GLOBAL_STATUS_OK          — all SEs normal
  WDGM_GLOBAL_STATUS_FAILED      — at least one SE failed
  WDGM_GLOBAL_STATUS_EXPIRED     — watchdog expired, reset pending
  WDGM_GLOBAL_STATUS_STOPPED     — watchdog stopped (e.g. debug mode)
  WDGM_GLOBAL_STATUS_DEACTIVATED — watchdog deactivated (e.g. sleep)
```

Each Supervised Entity also has its own local state (WDGM_LOCAL_STATUS_OK/FAILED/EXPIRED/DEACTIVATED; there is no STOPPED in the local states). These states are reported through the RTE mode machine, and the DEM path handles fault logging and DTC storage.

The key fault propagation path:

```
  SE_Steering → local FAILED
       │
       ▼
  WdgM Global Status → WDGM_GLOBAL_STATUS_FAILED
       │
       ├──► DEM: log DTC_Steering_WdgM_Failure
       │
       ├──► EcuM: request controlled shutdown or reset
       │
       ├──► RTE Mode Switch: switch to degraded mode
       │
       └──► WDGM_IMMEDIATE_RESET: reset immediately if configured
```

WDGM_IMMEDIATE_RESET is a compile-time switch that applies to the whole WdgM module. When it is STD_ON, WdgM calls `Mcu_PerformReset()` in the same tick that the global state reaches STOPPED and resets immediately. When it is STD_OFF, the kick condition is forced to 0, WdgM stops kicking, and the hardware watchdog timeout handles the rest. In an ASIL D system, any code that tries to "shut down gracefully" may itself already be corrupted; a direct reset is often more reliable.

RTE Mode Switch integration is another important feature. When an SE fails, WdgM can trigger the AUTOSAR mode machine to switch to a degraded mode. If the EPS main control SE fails, for example, the Mode Switch can move the steering system to a mechanical direct-link mode (or a hydraulic backup mode) and light a warning lamp in the instrument cluster. This supervision-dependent mode lets the system enter a degraded safe state without resetting the whole vehicle, which matters especially for steering and braking.

A watchdog is essentially a timing-constraint guarantee mechanism. It does not check logical correctness; it checks only whether constraints in the time dimension are met. In an embedded real-time control system, every software logic error eventually shows up as a timing anomaly: a deadlock shows up as missing checkpoints, an infinite loop as a deadline timeout, a wrong code jump as an illegal transition in Logical Supervision. Timing is the final common path of all faults.

But it has a blind spot too: a logic error that doesn't change timing (say, computing the opposite direction). The watchdog cannot see that at all. That needs E2E protection (3.5) and sensor redundancy (3.2).

The core challenge in configuring a watchdog is finding the balance between "triggering too early, which causes false resets" and "triggering too late, which misses detection." That balance point has to be established from WCET analysis, scheduling analysis, and worst-case testing.

## Summary

1. A watchdog is a hardware timer independent of the CPU, using a dedicated RC oscillator and unaffected by the system clock. It is the chip's lowest-level survival loop.
2. WdgM provides three layers of supervision: Alive Supervision (confirms the task is running), Deadline Supervision (confirms execution time is inside the window), and Logical Supervision (confirms the execution path is legal).
3. A window watchdog catches both "kicked too late" and "kicked too early," preventing a task from skipping critical computation and triggering early.
4. The kick password sequence (0xBC/0x43 are bitwise inverses) reduces the chance that a random memory flip kicks the watchdog by accident.
5. The WdgM global state machine propagates faults step by step to DEM (DTC logging), EcuM (reset request), and the RTE Mode Switch (degraded mode). At high safety levels it can reset the hardware directly.

> **Coming up next:**
> A watchdog governs "is the program still running?" but not "is the program computing the right thing?" If the CPU takes a wrong computation path without crashing, the watchdog won't trigger—it only watches the kick time, not the results. Lockstep cores close that blind spot: two identical Cortex-R5 cores solve the same problem and compare every clock cycle's output, beat by beat. If one CPU's ALU produces 0x0000A43F and the other produces 0x0000A42F, the CCU comparator catches that one flipped bit within 5 ns.
