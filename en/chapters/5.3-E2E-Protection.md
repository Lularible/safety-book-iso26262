# 5.3 E2E Protection: A Message Engine with CRC8, Counter, and DataID

## Scenario: A Tampered Brake Command

A certain car brand's electric power steering system showed a strange symptom in testing: the CAN message from the steering angle sensor occasionally carried a value offset by 2.3 degrees. The offset was tiny — almost imperceptible at low speed — but in a highway lane change, an accumulated 2.3-degree error is enough to push the vehicle off its intended path.

It took the accident investigation team three months to find the root cause: the steering motor driver's PWM trace ran just 1.2 cm from the sensor sampling circuit. When the motor ran at a particular speed, the electromagnetic field from the PWM current's di/dt coupled into the sampling chain and flipped data at **specific bit positions** in the sensor reading. Worse, standard CAN's 15-bit CRC was powerless. CAN's CRC is computed by the sender and sent with the frame; the receiver recomputes and compares, so a bit flipped on the cable is caught on the spot and retransmission requested. Here the flip happened before the data reached the CAN controller — link-layer checking never saw it.

**This reveals a key fact:** the checks in the underlying communication protocol (CAN CRC, UART parity, SPI checksum) protect the link layer, not end-to-end **application-layer data integrity**. If data is corrupted before it reaches the sender's CAN controller, or a safety-related signal is "silently modified" after several transformations between SWCs inside the ECU, the link-layer error correction knows nothing about it.

That's the background for AUTOSAR E2E (end-to-end communication protection). Today you'll implement a teaching-grade simplified version.

## The "Three Elements" of E2E Protection

Reduced to its leanest form, E2E protection does three things:

1. **Content check (CRC):** were the data bits changed unexpectedly? → CRC8
2. **Identity check (DataID):** is this the message I think it is? → 4-bit message ID
3. **Freshness check (Counter):** is this an old message being replayed? → 4-bit incrementing counter

These three elements map to the three basic threat models of communication safety:

| Threat | Attacker/fault type | E2E countermeasure |
|------|----------------|------------|
| Data corruption | EMI / SEU / voltage droop | CRC8 |
| Message masquerade | SWC misconfiguration / routing error | DataID |
| Replay attack | Network man-in-the-middle / task stall then recovery | Counter |

In a teaching setting we don't separate "security attack" from "random fault." For a functional safety engineer the consequence is the same: the safety goal is violated. E2E protection has to withstand both.

## Wire Format: How Are the Two Header Bytes Encoded?

The wire format safe-lite nails down is a minimal two-byte header:

```
Byte 0: CRC (8 bits)
Byte 1: [Counter(4 bits) | DataID(4 bits)]
```

Industrial-grade Profile 1 makes the positions of the CRC and counter configurable; by default DataID stays only in the sender's and receiver's configuration and never goes on the bus, and only one mode writes the 4-bit nibble into the message on its own. For teaching, safe-lite fixes all the offsets and squeezes DataID into 4 bits, sharing one byte with the counter:

```c
/* safe_e2e.h */
typedef struct {
    uint8_t data_id;   /* 0..15, identifies the message source */
    uint8_t counter;   /* 0..15, +1 per message, wraps automatically */
} safe_e2e_ctx_t;
```

**Why a 4-bit counter?** Real E2E Profile 1 uses 4 bits, but reserves 0xF as an error value, so in practice it cycles only from 0 to 14; Profile 5 uses 8 bits and Profile 4 uses 16. safe-lite lets the counter use all 16 values from 0 to 15. For a teaching setting:
- 4 bits is enough to show counter wrap logic (modulo 16)
- A 4-bit counter takes half a byte and shares one byte with DataID. That's typical of bandwidth-sensitive embedded protocols
- For a production system, 4 bits is clearly not enough: at a 100 Hz CAN message rate, a 4-bit counter wraps every 160 ms, and the receiver must get the message within that 160 ms to distinguish a "legal wrap" from a "replay"

The header encode/decode is straightforward:

```c
/* Pack: Counter in the high nibble, DataID in the low nibble */
uint8_t safe_e2e_build_header_byte(uint8_t counter, uint8_t data_id)
{
    return (uint8_t)(((counter & 0x0FU) << 4) | (data_id & 0x0FU));
}

/* Unpack */
void safe_e2e_parse_header_byte(uint8_t byte, uint8_t *counter, uint8_t *data_id)
{
    *counter = (byte >> 4) & 0x0FU;
    *data_id = byte & 0x0FU;
}
```

Why is Counter in the high bits? No particular reason; it's a design convention. In a real system the choice of endianness depends on the network byte-order convention. High-first here is purely personal preference. You're free to swap the two nibbles as long as both sides agree.

## Protect(): Building the Protected Message

`safe_e2e_protect()` is the sender's core function. It takes raw data and produces a complete frame with the E2E header:

```c
size_t safe_e2e_protect(safe_e2e_ctx_t *ctx,
                        const uint8_t  *data,
                        size_t          len,
                        uint8_t        *out)
{
    /* 1. Increment the counter, wrapping modulo 16 */
    ctx->counter = (ctx->counter + 1) & SAFE_E2E_MAX_COUNTER;  /* & 0x0F */

    /* 2. Build the CRC input buffer: [DataID | Counter | payload] */
    uint8_t crc_buf[SAFE_E2E_MAX_DATA_LEN + 2];
    crc_buf[0] = ctx->data_id;
    crc_buf[1] = ctx->counter;
    memcpy(&crc_buf[2], data, len);

    /* 3. Compute CRC8 */
    uint8_t crc = safe_crc8_compute(crc_buf, len + 2);

    /* 4. Assemble the output frame */
    out[0] = crc;
    out[1] = safe_e2e_build_header_byte(ctx->counter, ctx->data_id);
    memcpy(&out[2], data, len);

    return SAFE_E2E_HEADER_SIZE + len;
}
```

**The most important design decision:** the CRC covers `[DataID | Counter | payload]`, not the payload alone.

Why?

Imagine an E2E implementation that doesn't include DataID in the CRC:
1. Sender A (DataID=3) sends a message into the queue
2. A single metadata corruption in the queue changes the DataID field from 3 to 7
3. The CRC still matches (because it covers only the payload; DataID damage doesn't affect it)
4. Receiver B (DataID=7) gets the message, the payload is perfectly correct, and it accepts
5. **Disaster:** receiver B thinks this is data from source 7 (say, brake pedal position), but it actually came from source 3 (accelerator pedal position)

So: **the CRC must cover all the metadata that determines a message's "meaning."** That's the fundamental difference between end-to-end protection and link-layer protection.

## Check(): The Receiver's Validation Logic

The receiver's code is longer because it runs multiple checks:

```c
safe_status_t safe_e2e_check(safe_e2e_ctx_t *ctx,
                             const uint8_t  *buf,
                             size_t          total_len,
                             uint8_t        *data_out,
                             size_t         *data_len)
{
    /* 1. Validate the parameters */
    if (total_len < SAFE_E2E_HEADER_SIZE) return SAFE_ERROR;

    /* 2. Unpack the header */
    uint8_t rx_crc     = buf[0];
    uint8_t rx_counter = 0, rx_dataid = 0;
    safe_e2e_parse_header_byte(buf[1], &rx_counter, &rx_dataid);

    size_t payload_len = total_len - SAFE_E2E_HEADER_SIZE;

    /* 3. Recompute the CRC */
    uint8_t crc_buf[SAFE_E2E_MAX_DATA_LEN + 2];
    crc_buf[0] = rx_dataid;
    crc_buf[1] = rx_counter;
    memcpy(&crc_buf[2], &buf[2], payload_len);
    uint8_t computed_crc = safe_crc8_compute(crc_buf, payload_len + 2);

    if (computed_crc != rx_crc) {
        return SAFE_CRC_MISMATCH;  /* bit error or EMI */
    }

    /* 4. Validate DataID */
    if (rx_dataid != ctx->data_id) {
        return SAFE_DATAID_MISMATCH;  /* configuration or routing error */
    }

    /* 5. Validate counter freshness */
    uint8_t diff = (rx_counter - ctx->counter) & SAFE_E2E_MAX_COUNTER;
    if (diff == 0 || diff > 8) {
        return SAFE_COUNTER_ERROR;  /* duplicate or replay */
    }

    /* 6. Accept the message */
    ctx->counter = rx_counter;
    memcpy(data_out, &buf[2], payload_len);
    *data_len = payload_len;
    return SAFE_OK;
}
```

**Note the check order:** CRC → DataID → Counter. The order isn't arbitrary. It follows "lightest check first." CRC goes first because if the CRC is wrong, the later checks are meaningless — the data itself is damaged. Counter goes last because updating the counter changes the receiver's state; if the message is rejected for CRC or DataID reasons, the counter must stay unchanged.

## Counter Window Validation: Looking Forward on the Modulo-16 Ring

This is the most elegant part of the whole E2E implementation:

```c
uint8_t diff = (rx_counter - ctx->counter) & SAFE_E2E_MAX_COUNTER;
if (diff == 0 || diff > 8) {
    return SAFE_COUNTER_ERROR;
}
```

Understanding this statement takes a number-theoretic view. Consider the 4-bit counter's range, 0–15, arranged on the cyclic group modulo 16:

```
... → 13 → 14 → 15 → 0 → 1 → 2 → 3 → ...
```

What does a window of 8 (half the range) mean? Concrete numbers:

**Case 1: normal increment**
- Last counter=5, this time counter=7
- diff = (7-5) & 0x0F = 2 → 1 ≤ 2 ≤ 8 → **legal**

**Case 2: counter wrap**
- Last counter=14, this time counter=2
- On the sender: 14→15→0→1→2, a wrap (some messages were lost in between)
- diff = (2-14) & 0x0F = (2+2) & 0x0F = 4 → 1 ≤ 4 ≤ 8 → **legal**

**Case 3: duplicate message (replay)**
- Last counter=8, this time counter=8
- diff = (8-8) & 0x0F = 0 → diff == 0 → **reject**

**Case 4: severe regression (suspected replay)**
- Last counter=10, this time counter=3
- diff = (3-10) & 0x0F = 9 → 9 > 8 → **reject**

Why choose 8 (half range) rather than 14 or 2?

It comes from an assumption about **the maximum tolerable number of consecutive lost messages**. With a window of 8, you allow up to 7 messages to be lost (8 sent, only 1 received — reasonable on a fast bus). With a window of 14, you allow almost any wrap; 15 lost messages are still accepted, which means the system received nothing valid for nearly two full counter cycles. That's usually a disconnected network, not normal packet loss. With a window of 2, any slight burst of loss causes a counter error.

**In a production system this window size is configurable and determined by FMEA.** If you're designing an ASIL D system, you have to answer: within the FTTI window, how many messages can be lost in the worst case? If network load and retransmission guarantee no more than N losses, the window must be at least N+1.

## The CRC8 Polynomial: Behind 0x1D

safe-lite uses the polynomial 0x1D (x^8 + x^4 + x^3 + x^2 + 1). The source comment labels it CRC-8/AUTOSAR; industrial CRC libraries usually call the same polynomial SAE J1850, while AUTOSAR's 8-bit H2F version is a different value, 0x2F. The choice isn't arbitrary: it has a proven balance between Hamming distance and computational complexity.

0x1D's error-detection capability varies with data length; longer data means lower Hamming distance:
- The standard gives a graded example for an 8-bit CRC: with a different polynomial value, data up to 119 bits has a Hamming distance of 4 and detects all 1-to-3-bit errors. That 119-bit threshold belongs only to the polynomial in the example and can't be carried over to 0x1D
- safe-lite feeds at most 66 bytes into the CRC (64-byte payload plus 2 bytes of metadata), which is 528 bits — well past the example's threshold; the same polynomial on longer data only has a lower Hamming distance

The CRC is computed with a 256-entry lookup table:

```c
const uint8_t safe_crc8_table[256] = {
    0x00, 0x1D, 0x3A, 0x27, 0x74, 0x69, 0x4E, 0x53,
    /* ... 256 entries in total ... */
    0x97, 0x8A, 0xAD, 0xB0, 0xE3, 0xFE, 0xD9, 0xC4,
};

uint8_t safe_crc8_compute(const uint8_t *data, size_t len)
{
    uint8_t crc = 0x00;
    for (size_t i = 0; i < len; i++) {
        crc = safe_crc8_table[crc ^ data[i]];
    }
    return crc;
}
```

The lookup-table method is standard in embedded systems: 256 bytes of ROM buys one table lookup plus one XOR per byte. How many times faster that is than bit-by-bit computation, or how many CPU cycles per byte, is an external engineering estimate; the only thing the repository can verify is the implementation itself — one index, one XOR, one loop.

## Test Verification: The Complete State Space

safe-lite's E2E tests cover one normal scenario (A) and three fault scenarios (B, C, D):

**Test A: normal send and receive**
```
TX counter: 1 → sends "Hello Safety!"
RX counter: 1 → receives "Hello Safety!"  ✓
```

**Test B: CRC corruption detection**
```
Original frame: B8 42 AA BB CC DD
Flip bit 3 of byte 3 in the frame (BB→B3):
Corrupted frame: B8 42 AA B3 CC DD
Result: CRC_MISMATCH ✓
```

**Test C: counter error**
```
After normal send/receive: TX=8, RX=8
Inject fault: reset TX counter → TX=0
Send a new message: counter=1
RX check: diff=(1-8)&0x0F=9 > 8 → COUNTER_ERROR ✓
```

**Test D: DataID mismatch**
```
TX DataID=4, RX expects DataID=9
→ DATAID_MISMATCH ✓
```

Each fault scenario validates one independent safety property. The separation is deliberate: if any one test fails, you can immediately tell which validation rule broke.

E2E protection reveals a deeper design principle: communication safety depends on the integrity of three dimensions — "when, from whom, and what you think you received." Many home-grown protocols do only the first step (CRC-check the data) and skip the other two (verify the source and the freshness). That may be acceptable in a single-ECU system, but in a distributed safety-critical system made of dozens of ECUs, a wrong DataID means your ABS controller is making braking decisions from seat position data.

## Summary

1. E2E protection has three elements — CRC8 (content integrity), DataID (message identity), and Counter (freshness) — matching three basic threat models: data corruption, message masquerade, and replay attack.
2. The CRC must cover all three of DataID, Counter, and payload, not just the payload. Otherwise a tampered DataID still matches the CRC, and the receiver may treat data from the wrong source as valid.
3. Counter window validation computes the difference on the modulo-16 ring with `(rx_counter - last_counter) & 0x0F`. A window of 8 (half range) balances packet-loss tolerance against replay protection.
4. `Protect()` increments the counter before computing the CRC; `Check()` follows lightest-first order: CRC → DataID → Counter. The counter update comes last to keep the receiver's state consistent.
5. The safety CRC8 (polynomial 0x1D, usually called SAE J1850 in industrial libraries and labeled CRC-8/AUTOSAR in safe-lite's comments) is implemented with a 256-entry lookup table. Error-detection power falls as data grows; the exact Hamming distance has to be recomputed for this polynomial and the actual length.
