# 1.5 The Dice of Physics: Alpha Particles and SRAM Bit Flips

### Not a Bug, Physics

You spent two weeks writing a CAN communication task. Code review passed, static analysis passed, unit tests passed. The integration test runs to its 3,000th cycle, and the ECU suddenly resets on a watchdog timeout. You search the logs and find no infinite loop, no null pointer, no stack overflow. Every logic path is correct.

You narrow the problem down to SRAM: one bit of one global variable flipped from 0 to 1 by itself at some unpredictable moment. You rule out every possible software write. The variable has exactly one write point, and that point was not executed during those 500 microseconds.

This is not a software bug. It is **a physical flip in a six-transistor memory cell**.

Your code is not wrong, the compiler is not wrong, the logic is not wrong. What is wrong is that the physical world is rolling dice for the logical world. An alpha particle from a trace uranium isotope in the packaging resin decays, crosses the silicon lattice at about 5 MeV, and ionizes hundreds of thousands of silicon atoms along its path, creating a brief chain of electron-hole pairs.

And that chain happens to pass through the storage node of the SRAM cell holding a "1." The extra charge that floods in at that instant changes the state of the cross-coupled inverters. 1 becomes 0. The highest bit of your global variable flips from 1 to 0, so the timer compare value jumps from a reasonable number to a tiny one, and the watchdog times out on the next cycle.

### The SRAM 6T Cell: Logic Surrounded by Physics

One SRAM bit is built from six transistors. Four of them form two cross-coupled inverters, a positive-feedback latch that holds the 0 or 1 state. The other two are access transistors, connecting the bit lines to the inverters for reads and writes. This structure is the 6T cell.

At the 28 nm or 40 nm node, the 6T cell is about 0.1 to 0.3 µm². Inside it, the storage node that holds the "1" state contains roughly two or three hundred dopant ions. That number matters.

If a charged particle passes through this node, it ionizes the silicon lattice and releases electron-hole pairs. If the released charge exceeds the storage node's "critical charge," the stored 1 flips to 0. This is a **single-event upset (SEU)**. It is not permanent damage; the next write restores normal operation. But at the instant of the flip, all your logical reasoning is invalid. The execution of a correct program has had its data rewritten by an external physical event it knows nothing about.

How serious is this problem for cars on the ground? Very serious. Alpha particles do not come only from cosmic rays in outer space; the packaging material itself contains trace radioactive isotopes. Uranium-238 and thorium-232 in the resin filler release alpha particles through natural decay. Lead-210 in solder. **The package is a radiation source. No solar storm needed. The chip's own package shell releases several alpha particles per second**, which is why automotive-grade MCUs require low-alpha molding compound.

### ECC: Not Correcting Your Mistakes, but Physics'

SRAM ECC (error-correcting code) in its simplest form is an exercise in arithmetic interpolation. Take the most common scheme, SECDED (single-error correction, double-error detection): 7 ECC check bits are added to every 32 bits of data. On every write, the ECC engine computes the 7 check bits from the data and writes them into SRAM alongside it. On every read, the engine recomputes the check bits from the data read out and compares them with the 7 stored bits.

If one bit has flipped, the XOR of the check bits points at the flipped bit. The engine flips it back. Correction complete. If two bits have flipped, the XOR of the check bits points at a position that "does not correspond to a valid error-correction vector." This is interpreted as an "uncorrectable error," and the engine does not return the data; it raises an alarm.

**You spend 7 bits of overhead and get instant correction on every word read.** If the probability of an alpha-particle strike is once per thousand hours, ECC lets your system go decades without a reset caused by an SEU.

ECC is not fighting the code you wrote. It is fighting the random decay of uranium nuclei in the packaging material. This is not software engineering; it is radiation physics. Half the time spent on a functional safety argument is not about logic. It is about arguing that physical faults are adequately controlled.

### Lockstep: Standing on Two Legs at Once

If ECC protects memory, lockstep protects the processor. Two identical CPU cores execute exactly the same code. Every clock cycle, a hardware comparator compares the results on the two internal buses. If they match, execution continues. If they differ, the comparator raises an alarm immediately. This redundancy is not "one computes, the other checks." It is **both compute, and both results must agree every cycle.**

Lockstep's extra cost is not small: two cores consume double the power and double the die area. But the benefit is that no software has to participate. Not one line of code needs to change. The C code you wrote for a single core, once compiled and run on the lockstep pair, is compared automatically by the hardware comparator within the bus cycle.

When the comparator detects a mismatch, it does not know which core is right. It only knows there is **a mismatch**. So lockstep does not "correct." It can only shut down, raise an alarm, and enter the safe state. In that sense, lockstep is not an "error correction" mechanism but an "error detection" mechanism. Its downstream stage, usually the SMU (safety management unit) or a watchdog, carries out the actual fault response.

### Redundancy and Common-Cause Failure: Two Kidneys Are Not Enough

Lockstep is much stronger than a single core, but it has a soft spot: **common-cause failure**. The two cores sit on the same die, sharing the same clock source, the same power domain, and the same package. If a supply droop is large enough, both cores are disturbed **at the same time**, and the lockstep comparator cannot see a problem, because the wrong results from both cores also agree.

That is why ASIL D systems, such as braking and steering, sometimes need **heterogeneous redundancy**: the main processor is an Infineon AURIX TriCore TC3xx, and the independent safety monitor MCU is a Cortex-R5 or RL78 from another vendor. Different dies, different design teams, different clocks. A single physical event cannot take out both at once.

The level of redundancy is not just "is there a backup." It is "what does the backup share with the primary." Shared power domain? A power interruption kills both at once. Shared clock? A clock glitch disturbs the timing of both at once. Shared die? The same alpha particle can flip adjacent bits in both. Shared design team? The same bug exists in both chips. Common-cause failure analysis is the hunt for "what both sides depend on." Only when every shared dependency is removed is the redundancy truly independent.

### PMHF: The Measurement Basis of Functional Safety

"Random hardware faults are unavoidable." You and ISO 26262 agree on that. The question is: **unavoidable to what degree is still acceptable?**

ISO 26262-5 sets quantitative targets for the upper limit of random hardware fault tolerance at each ASIL, and the key metric is PMHF (probabilistic metric for random hardware failures): the average probability per hour of violating a safety goal because of a random hardware fault. The ASIL D target is < 10 FIT (failures in time). 10 FIT means fewer than 10 violations of a safety goal caused by random hardware faults in 10⁹ hours of continuous operation — about 114,000 years.

You cannot run an ECU for 114,000 years to verify it. PMHF is not a measured value. It is **a probabilistic target derived from FMEDA and reliability statistics**. You model the failure rate and failure-mode distribution of every hardware component (MCU, power chip, CAN transceiver, sensor). Then you calculate whether the total probability of residual failure, with all safety mechanisms accounted for, is below the FIT limit required by the ASIL.

The philosophical meaning of this number, 10 FIT, has already been laid out in the preceding sections: **absolute safety is impossible. There is a nonzero probability, extremely small, that a random hardware fault will penetrate every safety mechanism. The standard does not ask you to eliminate that probability. It asks you to push it into a range that "society considers acceptable."**

### The Fault-Error-Failure Propagation Chain

Earlier you saw the physical chain: alpha particle → bit flip → watchdog timeout → ECU reset. In ISO 26262's vocabulary, every step in that chain has a precise name. Without these names you cannot read the FMEDA reports in a safety manual.

These four names form a strict propagation hierarchy:

**Fault**: an unexpected abnormal state inside the system. ISO 26262-1 defines a fault as "an abnormal condition that can cause an element or an item to fail." At the instant the alpha particle hits the SRAM cell, extra charge appears on the storage node. That is the fault. The essence of a fault is "the bomb has been buried," but it may never be read. If the flipped bit is in a char array used for a debug log, and your production release turns debug off, the fault has no effect on the function. For now it is harmless; it just has not "produced an error" yet.

**Error**: at the moment the fault is read, it turns from an "abnormal state" into a "deviating value." ISO 26262-1 defines an error as "a discrepancy between a computed, observed or measured value or condition and the true, specified or theoretically correct value or condition." When your program next reads the flipped bit, the value it reads is wrong. That is the error. A fault is "the bomb is buried"; an error is "the bomb has gone off — no one is hurt yet, but the fragments are flying."

**Failure**: the error has propagated to the output through which the system provides its service. ISO 26262-1 says a failure is "the termination of the ability of an element or an item to perform a function as required, due to the manifestation of a fault." The flipped timer compare value causes the PWM to output a wrong duty cycle, the steering motor receives a wrong current command, and the steering assist function deviates. That is the failure. The failure is "fragments have hit the system's output port"; you can no longer deliver the service you promised by design.

**Hazard**: a potential source of physical harm caused by the erroneous behavior of the item. A failure is not necessarily a hazard. The same erroneous extra 100 N·m of steering torque, when the car is parked at the roadside, is just a jolt that startles you; not a hazard. The same failure, at 120 km/h through a curve on the highway, can push the car out of its lane and cause a collision. A hazard combined with a specific operating scenario becomes a hazardous event.

The propagation chain of these four steps (fault → error → failure → hazard) is not instantaneous. Between each step there is a time and logic window in which detection and interception can be inserted. **The essence of every safety mechanism on the ECU — ECC, watchdog, lockstep, E2E — is an "interception point" placed along this chain.** ECC intercepts at fault → error: the instant the bit flip is read and produces an error, ECC corrects it on the spot, and the error does not propagate. The watchdog intercepts at error → failure: the program runs away because of the bad data, and the watchdog resets the whole system before it produces a wrong output signal. E2E intercepts at failure → hazard: even if the bad data has already been packed into a CAN message and sent, the E2E check at the receiver finds a CRC anomaly, discards the frame, and does not let the bad data drive a physical actuator.

Take a concrete steering ECU example. T = 0 ms: an alpha particle hits SRAM. The fault occurs. The calibration offset for steering angle flips from +2.3° to +227.3°. T = 0.2 ms: the steering control task reads the value. The error occurs. T = 0.5 ms: the task computes a target torque from the wrong value, 40 N·m instead of the normal 2 N·m. T = 0.8 ms: a CAN message packs this torque value, but the E2E library computes a new CRC over the bad data. That CRC is self-consistent with the bad data, so E2E does not flag an error. T = 1.2 ms: the steering actuator ECU receives the frame. The E2E check passes (the CRC is self-consistent), it decodes a torque of 40 N·m, the motor outputs 40 N·m, and the steering assist surges. If the car is traveling at high speed at this moment, a hazard occurs.

What do you see in this example? **A fault can be detected only at certain links in the propagation chain. Where you place your safety mechanisms directly determines how many faults you can intercept.** If you have only lockstep and a watchdog but no ECC, the bit flipped by the alpha particle may already have started propagating an error by the time you read it. If you have only E2E and no watchdog, the task runs away because of the flipped data, jumps to a wrong address, and E2E never gets a chance to pack the data. Each safety mechanism covers only one segment of the propagation chain. That is why FMEDA must analyze the complete fault propagation path. It is not just "how many faults are there" but "can a fault reach a hazard." If it can, a safety mechanism must be able to intercept it. If it cannot, you may argue in the safety case that "this fault does not violate the safety goal."

### Diagnostic Coverage: Not Every Fault Can Be Caught

You now know the ECU has many safety mechanisms. But your safety argument cannot stop at a vague statement like "we have ECC." Each mechanism has its own hit rate, and ISO 26262 quantifies that hit rate as **diagnostic coverage (DC)**.

Diagnostic coverage = the failure rate detected by the safety mechanism ÷ the total failure rate of all possible faults. The standard divides coverage into three levels, not precise values from calculus but empirical ranges derived from large amounts of data in engineering practice:

**Low coverage, about 60%.** Typical means: software functional testing, watchdog-based program-flow monitoring. A watchdog can only detect "the task did not execute." If the task executed but computed a wrong result, the watchdog cannot see it. It covers the "stopped" failure mode, not the "wrong" failure mode. Program-flow monitoring is a little better: it checks whether the task executed the expected checkpoint sequence. But if the task's path is unchanged and only some intermediate value was computed wrongly, program-flow monitoring cannot see that either. So low coverage mainly targets the "not executed at all" class of faults.

**Medium coverage, about 90%.** Typical means: periodic RAM/NVM self-test, OS scheduling supervision. Your MCU might run a RAM March-C test at the end of each task loop: write a specific pattern into a region, read it back, and compare. This detects most SRAM hard faults, such as a bit stuck at 0 or 1 (stuck-at fault). But it does not cover transient SEUs: after an SEU flips a bit, the error has already propagated during the tens of milliseconds before the next March-C cycle arrives. So medium coverage suits latent-fault detection (sweep periodically so a fault does not stay latent for long) but not immediate interception of transient faults.

**High coverage, about 99%.** Typical means: hardware ECC (SECDED), lockstep comparators, hardware CRC checked online. ECC checks on every read, not periodically — in real time, every read is a check. Lockstep compares every clock cycle, not by sampling — full comparison. Hardware CRC verifies every CAN frame online at transmission and reception. The coverage of these hardware mechanisms is high because their detection window overlaps almost completely with the window in which the fault occurs. The moment the fault appears, detection is already in place. Hardware detection does not depend on software execution and is not affected by task scheduling.

These three coverage levels map directly onto the core hardware architectural metrics of ISO 26262-5:

**SPFM (single-point fault metric)**: measures how well the hardware architecture protects against single-point and residual faults. ASIL D requires SPFM ≥ 99%. That means, of the failure rate of safety-related hardware — whether the fault is in SRAM, Flash, the ALU, or the CAN controller — single-point and residual faults together may account for at most 1%. The other 99% is either covered by a safety mechanism or is itself a safe fault. In your FMEDA you must work out every hardware component, every failure mode, and the corresponding safety-mechanism coverage, then add them up and prove SPFM ≥ 99%.

**LFM (latent fault metric)**: measures how well the hardware architecture protects against failures that require "two faults in combination" to break through. Some faults do not directly cause a failure, but they disable a safety mechanism. For example, the watchdog's own clock source drifts, and the watchdog timeout threshold moves from 40 ms to 400 ms. The watchdog is still "alive" but can no longer protect the system effectively. This is a latent fault. If a second fault then occurs (the program really does run away), the watchdog can no longer reset in time. ASIL D requires LFM ≥ 90%, meaning at least 90% of latent faults are detected within a reasonable "diagnostic test interval," leaving no exploitable latent window for a second fault.

In the safety argument you cannot just say "we have ECC." You must produce the FMEDA data from the MCU supplier: for the SRAM array, the diagnostic coverage for permanent (stuck-at) faults is 99.X%, and the diagnostic coverage for transient SEUs is 99.Y%. These percentage figures are the "units of credibility" in your safety argument. They are not a vague "it should be safe enough" but numbers that can be calculated, traced, and independently checked by a reviewer.

### Why Two Identical Cores Are Still Not Enough: A Deeper Look at Common-Cause Failure

Earlier we mentioned lockstep's fatal weakness: common-cause failure (CCF). The two cores are on the same die, in the same power domain, under the same clock tree, so a single physical event may take out both at once. This is not as simple as "if the power fails, both fail."

ISO 26262-9, on ASIL decomposition and common-cause analysis, gives a systematic classification of common-cause failure: the **coupling factor**, which breaks "what the two cores share" into seven dimensions. Your common-cause analysis must argue, item by item, the dependency and residual risk of each dimension:

**Hardware coupling: shared die and package.** The two lockstep cores are on the same silicon wafer, in the same resin package. A wafer-level defect (such as a microcrack in a metal layer) may affect the same functional unit in both cores. Moisture ingress into the package, solder-joint fatigue — one mechanical stress acts on the whole package. When your FMEDA says "the failures of the two cores are independent," you must argue whether the physical isolation at the die level is sufficient (for example, whether the two cores sit on different voltage islands on the die, and whether inter-layer physical isolation is used).

**Supply coupling: shared voltage regulator.** Both cores are powered by the same LDO on the same PMIC (power management IC). Voltage droops, overvoltage, ripple — both cores see the same distorted supply waveform. The lockstep comparator then cannot distinguish "both cores computed wrong because the voltage was wrong" from "both cores computed right," because the two results still agree. Your argument needs independent voltage monitoring (for example, an independent overvoltage/undervoltage detection circuit that does not go through the PMIC feedback loop) to break the supply coupling.

**Clock coupling: shared PLL/oscillator.** Both cores are driven by the same PLL through the same clock tree. Clock jitter, frequency offset, duty-cycle distortion all affect the setup/hold time of both cores at once. If a setup-time violation puts a flip-flop into metastability, both cores may sample the same wrong value at the same flip-flop. Breaking clock coupling requires independent clock sources: the main core and the monitor core are driven by different crystals or RC oscillators.

**Environmental coupling: shared temperature field and EMI environment.** The whole chip runs at the same junction temperature, and timing shifts from temperature gradients are global. The same electromagnetic interference, such as high-current PWM harmonics from a motor drive, acts on both cores' I/O and internal logic at once. An alpha particle inside the package can cross adjacent logic cells of both cores; at 28 nm this is already a real failure mode.

**Development coupling: shared RTL design team and verification flow.** The RTL of both cores was designed by the same team, synthesized with the same constraint files, and verified by the same verification team with the same testbench. If the RTL has a design defect (for example, the pipeline produces a wrong bypass result under a particular instruction sequence), both cores make the same mistake. What the lockstep comparator sees still agrees — agrees on being wrong.

These five coupling factors (hardware, supply, clock, environment, development) are the five most critical of the seven. They explain why ASIL D systems need heterogeneous redundancy: **homogeneous redundancy (lockstep) handles random hardware transient faults, while heterogeneous redundancy handles system-level and development-level common causes.** The main processor is an Infineon AURIX TriCore; the independent safety monitor MCU is a Renesas RH850 or TI Hercules — different RTL design teams, different dies, different clock architectures, different power rails. Only when every critical coupling factor is broken can you argue that "the failures of the two channels are probabilistically independent," independent enough to use the multiplication rule directly: probability of main-channel failure × probability of monitor-channel failure = probability of both failing at once.

What you need to do in the common-cause analysis report is not write one sentence: "we used heterogeneous redundancy." You must argue, item by item and category by category, the independence and acceptable residual of every one of the seven coupling factors. If any item cannot be fully independent, you must calculate a conservative probability for the residual coupling and prove that it does not affect the overall PMHF calculation. This is not bureaucratic box-filling. It is the deep foundation of system-level safety: **you can push system-level residual failure risk below 10 FIT because you can credibly say the two safety channels are not "two sides of the same coin." They are "two different coins," struck by different mints, with different dies, at different times.**

### Summary

1. An SRAM bit flip is not a software bug: an alpha particle emitted from the packaging material crosses a 6T cell and leaves an ionization track that flips the logic at the physical level.
2. ECC and lockstep are not fighting software; they are fighting physics. ECC corrects storage flips, and lockstep detects inconsistent processor computation.
3. Common-cause failure is the natural enemy of redundancy: two cores sharing the same power domain or clock source can both be taken out by one physical event. ASIL D uses heterogeneous redundancy to break the common cause.
4. PMHF is functional safety's last ruler: it does not demand zero faults but requires that "the residual fault probability is below a time scale society accepts."
