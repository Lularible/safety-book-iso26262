# 3.5 E2E Protection: The Antigen-Marking Message Engine

You're sitting in an L3 autonomous driving test car on the high-speed ring at Bosch's Boxberg proving ground, doing 120 km/h.

The steering wheel angle sensor sends the current angle over SPI to the main MCU: "3.2°." That number means your car is making a very slight correction to the right to stay centered in the lane. The MCU's EPS (electric power steering) algorithm receives the value, computes the corresponding steering motor torque command, packs it into a CAN frame, and sends it to the motor controller.

Everything is normal. Except for one detail.

Between the MCU's CAN controller and the motor controller's CAN transceiver runs a 12 cm PCB trace. That trace happens to pass above the DC-DC power module. The module's switching frequency is 2.1 MHz, and its 17th harmonic falls right in the spectrum of the CAN bus signal. At one particular switching phase, an EMI pulse on the line flips one bit: bit 11 of the CAN frame data goes from 0 to 1.

The binary representation of 3.2° (assuming a 12-bit signed integer, 1 LSB = 0.1°, positive = right, negative = left) is `000000100000` = 32. Bit 11 is the sign bit. Flipped to 1, the bitstream becomes `100000100000`—in 12-bit two's complement that means -2016, or -201.6°. The sensor reading went from +3.2° to -201.6°; the direction reversed.

The motor controller receives the command: "steering angle = -201.6°." It faithfully executes. The EPS motor delivers 330 A peak current and slams the steering rack to the left. The steering wheel spins in your hands at 800° per second. If you don't let go, your wrists break within 0.4 seconds.

This is the problem ISO 26262 really solves—not "what if the hardware breaks?" but "the data is already on its way, it spoiled in transit, and the receiver has no idea."

What if every safety-critical message carried an identity marker of its own, like an antigen? Then the immune system could recognize at the target cell (the receiver) that "this is not one of my own proteins" and clear it.

That is the essence of E2E protection (End-to-End Protection).

## Core Concept: A Message's "Antigen Markers"

In the human immune system, every cell surface expresses MHC-I molecules. MHC-I displays fragments of the proteins being produced inside that cell. When a cell is infected by a virus, its surface MHC-I displays viral protein fragments, and cytotoxic T cells scan for the "foreign antigen" and clear the cell immediately.

The core idea of E2E protection is exactly the same: every safety-critical message travels from the sender's application layer (message generation) to the receiver's application layer (message consumption), passing through the operating system, the communication stack, the driver layer, and the physical bus. Any layer can introduce data corruption. E2E attaches three markers to the message body:

1. **CRC (cyclic redundancy check)**: the "protein fingerprint" of the message content. If any bit changes in transit, the fingerprint no longer matches.
2. **Counter**: the message's "timestamp." Every message has an increasing sequence number. If the receiver gets an unexpected sequence number, the message was replayed (replay attack), or messages were lost in between.
3. **DataID (data identifier)**: the message's "identity tag." Every message—steering angle, brake pressure, vehicle speed—has a unique DataID. If the DataID of a "steering angle" message is mistakenly written as "brake pressure" (say, memory aliasing from a stack overrun), the receiver immediately notices that "this antigen is in the wrong place."

Together, these three form an unforgeable, non-replayable, content-verifiable "message antigen complex."

## The Five E2E Profiles: Subtypes of Immunoglobulin

Human immunoglobulins come in five subtypes—IgG, IgM, IgA, IgD, IgE—each with a different structure, distribution, and function. E2E protection likewise defines five profiles (P01, P02, P04, P05, P06) for different communication scenarios and ASIL requirements.

### P01: The Lightweight Patrol

Profile 1 uses the CRC8 polynomial (0x1D, the SAE J1850 standard) with a 4-bit counter. The structure is extremely compact: the protection field (serialized CRC + Counter) takes only 12 bits.

The 4-bit counter actually uses only 0 through 14, 15 sequence numbers, with 0xF reserved as an error value. The counter wraps naturally on overflow, which is entirely sufficient for its target: periodic low-speed messages (say, a temperature sensor reading every 100 ms, ASIL A/B).

P01 protection field layout:
```
[CRC8(8bits)] [Counter(4bits)] → 12 bits total
```

### P02: The Global Antigen Library Strategy

Profile 2's core innovation is how it handles DataID. P01 feeds the 16-bit DataID from the configuration directly into the CRC. P02 uses a **DataIDList**: the configuration holds a 16-entry list, and both sender and receiver use the low 4 bits of the current counter as an index to fetch an 8-bit DataID, then append it to the user data before computing the CRC.

P02 maintains a 16-entry DataID list. The DataID itself does not go on the wire; the receiver indexes out the locally expected value with the low 4 bits of the counter and recomputes the CRC with the user data. If it doesn't match, the message is illegal.

This design makes P02 especially suitable for an ECU that receives many different message types. It is like an immune cell that has to recognize many different antigens.

```
[CRC8H2F(8bits)] [Counter(4bits)] → DataID comes from DataIDList[Counter], not sent on the wire
```

### P04: The Elite Special Forces

Profile 4 is the "heavy armor" designed specifically for extremely harsh electromagnetic environments. It uses:
- **CRC32P4**: the 32-bit polynomial `0xF4ACFB13` that AUTOSAR customized for Profile 4. It targets the typical error patterns of a CAN bus (pulse noise, burst bit flips).
- **16-bit counter**: maximum 0xFFFF, wraps to 0 at the top, providing 65,536 sequence numbers.

P04 suits ASIL C/D steering and braking systems. Its header is 12 bytes, 96 bits: Length 16 bits, Counter 16 bits, DataID 32 bits, CRC32P4 32 bits. That is a lot of overhead. But considering that one wrong EPS motor command can destroy a car and kill its occupants, the header overhead is entirely worth it.

```
[Length(16bits)] [Counter(16bits)] [DataID(32bits)] [CRC32P4(32bits)] → 96 bits total
```

### P05: The Balanced Choice

Profile 5 uses CRC16 (0x1021, the CCITT standard) with an 8-bit counter, giving a 24-bit protection field. CRC16 has a Hamming distance of 4 (for messages shorter than 2048 bits), which means it detects any 3-bit flip with 100% probability.

P05 is currently the most widely used E2E Profile in the automotive industry, covering most ASIL B/C applications.

```
[CRC16(16bits)] [Counter(8bits)] → 24 bits total
```

### P06: The Variable-Length Message Specialist

Profile 6 also uses CRC16, but it supports variable-length messages, with payloads from a few bytes to several hundred bytes. P06 puts the Length field on the wire and includes it as an input to the CRC computation, preventing an attack that truncates a long message into a short one.

```
[CRC16(16bits)] [Length(16bits)] [Counter(8bits)] → 40 bits total
```

### Profile Selection Decision Table

| Profile | CRC | Counter | DataID | ASIL | Typical scenario |
|---------|-----|---------|--------|------|---------|
| P01 | CRC8 | 4-bit | 16-bit (multiple modes) | A/B | Temperature/pressure sensors |
| P02 | CRC8H2F | 4-bit | DataIDList[16] (8-bit) | A/B | Nodes receiving multiple messages |
| P04 | CRC32P4 | 16-bit | explicit 32-bit | C/D | Steering/brake actuators |
| P05 | CRC16 | 8-bit | implicit 16-bit | B/C | Most control commands |
| P06 | CRC16 | 8-bit | implicit 16-bit | B/C | Variable-length diagnostic messages |

Choosing an E2E Profile is fundamentally a probability-versus-cost trade-off. CRC8's miss rate is about 1/256, acceptable for an ASIL A temperature display. CRC32P4's miss rate is about 1/4,294,967,296, necessary for ASIL D steering control. There is no "safest" Profile, only the Profile that best matches the ASIL level and the consequences of failure.

## Protect() and Check(): Marking and Recognizing Antigens

The E2E protection API is surprisingly simple: just two core functions:

```c
Std_ReturnType E2E_P04Protect(
    const E2E_P04ConfigType *Config,
    E2E_P04ProtectStateType *State,
    uint8 *Data,
    uint16 Length
);
```

And the corresponding:

```c
Std_ReturnType E2E_P04Check(
    const E2E_P04ConfigType *Config,
    E2E_P04CheckStateType *State,
    const uint8 *Data,
    uint16 Length
);
```

**Protect() responsibilities** (sender, called when the message is generated):
1. Read the current Counter value from the State structure
2. Serialize Counter, DataID, and message data into a byte sequence
3. Compute CRC32P4
4. Write Length, Counter, DataID, and CRC into the header at the positions specified by the Profile
5. Counter++, update State
6. Return E2E_E_OK

**Check() responsibilities** (receiver, called before the message is consumed):
1. Extract the CRC and Counter from the message
2. Skip the CRC field in the message (P04's CRC computation does not cover the CRC itself)
3. Re-serialize Counter, DataID, and message data
4. Recompute CRC32P4
5. Compare the computed result with the extracted CRC: equal means the content is intact; different means corruption
6. Check whether the Counter is within the tolerance range: inside means fresh; outside means too old or a replay
7. Return E2E_E_OK (the call is valid); the quality of the message itself is read from Status in State, and then MapStatusToSM turns it into a message-level status

The Counter tolerance mechanism in Check() is the part most worth understanding. If you simply check "current Counter > previous Counter," then after one message is lost (Counter jumps from 5 to 7), every subsequent legal message will be wrongly rejected as "Counter not continuous." Parameters like MaxDeltaCounter allow non-consecutive Counters within the configured range, solving the recoverability problem after communication desynchronization.

## The E2E State Machine: The Immune System's "Alert Levels"

The E2E specification defines a unified state machine (E2E_SM, E2E State Machine) to manage the receiver's operating state:

```
State transition diagram (simplified):
DEINIT → NODATA → INIT → VALID/INVALID
```

**DEINIT**: the state before initialization. E2E protection is not active yet. `E2E_SMCheck()` does not update state in this state and returns `E2E_E_WRONGSTATE` directly. The communication stack must call `E2E_SMCheckInit()` to enter NODATA.

**NODATA**: waiting for the first message. The receiver has not received any message yet and cannot judge whether communication is normal. As long as the current ProfileStatus is neither ERROR nor NONEWDATA, the state moves to INIT; messages with imperfect counts also make it leave NODATA. Timeout judgment is not the E2E state machine's configuration responsibility; it belongs elsewhere in the communication stack.

**INIT**: initialization verification phase. The receiver has received its first message, but it still looks at the accumulated results in the window: at least MinOkStateInit OK results among the last WindowSize checks, and ErrorCount no greater than MaxErrorStateInit, before moving to VALID. This design prevents mistaking communication as established just because one random piece of data happened to have a correct CRC.

**VALID**: normal operation. Messages keep arriving correctly, the Counter is within tolerance, the CRC matches, and the DataID is correct. This is the "green light" state.

**INVALID**: fault state. Any one of the following:
- CRC, DataID, or Length mismatch, accumulated beyond MaxErrorStateValid
- OK count inside the window falls below MinOkStateValid
- repeated or jumping Counter lowers the OK count, and accumulated to the threshold it also lands here

The transition from VALID to INVALID depends on the error count in the window exceeding MaxErrorStateValid, or the OK count falling below MinOkStateValid. This is another "tolerance design": an occasional error (say, one EMI hit) should not push the system into a fault state immediately, just as the immune system does not trigger anaphylactic shock because you inhaled one pollen grain.

**Key function: MapStatusToSM()**

Each Profile has its own detection logic (the window strategies of P01, P04, and P05 differ), but MapStatusToSM() maps Profile-specific detection results into a unified message-level status (E2E_P_OK/E2E_P_ERROR/E2E_P_NONEWDATA, and so on). The channel-level state machine E2E_SMStateType is a separate five-state enumeration (VALID/DEINIT/NODATA/INIT/INVALID), and E2E_SMCheck() decides it by accumulating the window. The upper layer looks at the message-level status first, then uses the channel state to decide whether to use or discard the message.

## The Sliding Window: The Immune System's "Tolerance Threshold"

The sliding window is one of the most elegant designs in E2E protection. It has three core parameters:

- **WindowSize**: the length of the state machine's statistics window; it counts the most recent check results and does not directly constrain the Counter value.
- **MinOkStateInit / MinOkStateValid / MinOkStateInvalid**: thresholds for each state, all meaning the minimum number of times ProfileStatus was E2E_P_OK inside the window; they do not need to be consecutive.
- **MaxErrorStateInit / MaxErrorStateValid / MaxErrorStateInvalid**: the corresponding upper limits on error count, counting how many times ProfileStatus was E2E_P_ERROR inside the window.

Why do we need a sliding window? Let's return to a real communication scenario. The EPS module sends a steering angle message every 10 ms (10 ms period). At some point:
- t=0 ms: Counter=100, received normally
- t=10 ms: Counter=101, EMI interference, CRC error, discarded
- t=20 ms: Counter=102, received normally
- t=30 ms: Counter=103, received normally

Without a sliding window, when Counter=102 arrives at t=20 ms, the system notices that "the last correct one was 100, now 102 arrives, 101 is missing" and declares a fault. But in reality, a 10 ms gap in steering control can easily be filled by interpolation at the upper layer; discarding one cycle causes no safety harm.

With MaxDeltaCounter=16, delta=2 falls inside the tolerance range, Status gives E2E_P04STATUS_OKSOMELOST, and MapStatusToSM maps it to the message-level E2E_P_OK. The data remains usable. The system's immunity was not triggered by one accidental error.

But what if the tolerance is configured too loosely? MaxDeltaCounter is a uint8, maximum 255; set it to 255 for an 8-bit counter and any jump is accepted, making replay protection meaningless. WindowSize on the state machine side is likewise a uint8; it constrains the statistics window length and is unrelated to the counter value space. So all these parameter configurations are a balance between **safety** and **availability**.

## Deep Correspondence in the Immune-System Metaphor

Put E2E protection and the immune system side by side, and you find a striking structural homology:

| Function layer | Immune system | E2E protection |
|--------|---------|---------|
| **Identity marker** | MHC-I displays antigen peptides | DataID identifies message type |
| **Integrity verification** | TCR recognizes the antigen-MHC complex | CRC verifies message content integrity |
| **Temporal freshness** | memory T cell survival time window | Counter sliding-window mechanism |
| **First contact** | immune priming | INIT→VALID state transition |
| **Tolerance threshold** | immune tolerance (does not attack self) | MaxErrorState tolerates intermittent errors |
| **Memory effect** | memory B cells (fast secondary response) | window recovery (after power loss, recover from the last known Counter) |

E2E protection's core idea: the sender attaches unforgeable tags to the message (CRC + Counter + DataID), and the receiver verifies their authenticity. Any data corruption in between is exposed.

P04 suits ASIL D steering/braking; P01 suits ASIL A sensors. Choose the wrong Profile and you either pay too much or miss too much.

### The Blind Spot of E2E: When an Attacker Swaps the Antigen

E2E protection assumes faults come from the physical world: an alpha particle flips one bit in SRAM, an EMI pulse changes one level on the CAN bus, solder-joint aging causes an intermittent open circuit. These faults share a feature: **randomness and lack of intent**—they do not actively disguise themselves.

But what if the source of the fault is not physical randomness but a deliberate attack? An attacker with access to the CAN bus can:

- listen to the bus and collect a set of legal CAN frames (with correct CRC and Counter values)
- extract the message's DataID, Counter sequence, and CRC value
- replace the payload with their own data, recompute the CRC, and increment the Counter
- send this "legal" message, and the receiver's E2E_Check passes completely

E2E protection fails completely in this scenario. Not because E2E is not good enough—E2E was never designed to defend against deliberate attacks: CRC is not a MAC (message authentication code); it does not depend on a key, and anyone who can read the bus can recompute it. E2E protects against "data being corrupted by noise during communication," not "whether the data came from a trusted source."

This is exactly the intersection of ISO 26262 (functional safety) and ISO 21434 (cybersecurity). Functional safety assumes faults are random, probabilistic, and modelable as FIT values. Cybersecurity assumes attacks are deliberate, adaptive, and not modelable as probability distributions. Their intersection lies in:

- **Does the system stay in a safe state after a safety mechanism is bypassed by an attacker?** For example, an attacker injects a forged brake pressure message, the E2E check passes, and EPS applies the wrong brake. In a functional safety model this scenario may be marked "covered by a safety mechanism," but in a cybersecurity assessment the coverage of that safety mechanism may be zero.
- **Diagnostic coverage of a safety mechanism is designed for random hardware faults and does not apply to deliberate attacks.** A 99% SPFM means "99% of random hardware faults are detected," not "99% of attacks are detected."
- **E2E can be upgraded to SecOC (Secure On-Board Communication).** AUTOSAR SecOC adds a MAC (message authentication code) on top of E2E, signing the message with a symmetric key; the receiver verifies the signature instead of the CRC. MAC computation depends on the key, so an attacker who can listen to the bus still cannot forge a valid message. The cost is extra computation and key-management infrastructure.

When designing a safety architecture, a practical approach is: **first use functional safety analysis to determine the ASIL level and E2E Profile of each message, then use cybersecurity analysis (TARA) to assess which messages an attacker might exploit, and layer SecOC or HSM protection onto high-risk messages.** The two analysis chains must cross-validate during system design.

## Summary

1. E2E protection attaches three markers to every safety message: CRC verifies content integrity, Counter prevents replay attacks, DataID confirms message identity. The receiver's Check() rejects the message if any marker fails.
2. AUTOSAR's E2E library implements five Profiles (P01, P02, P04, P05, P06), from CRC8 + 4-bit Counter to CRC32P4 + 16-bit Counter, matching the different protection needs from ASIL A to ASIL D.
3. Check()'s counter tolerance lets the receiver accept non-consecutive Counters within the configured range, avoiding false faults when communication occasionally drops a frame; the state machine's WindowSize counts the most recent check results and is unrelated to the Counter value.
4. The E2E state machine (DEINIT→NODATA→INIT→VALID/INVALID) uses the MinOkState and MaxErrorState thresholds in the window to implement an immune-tolerance strategy of "tolerate intermittent errors, reject persistent faults"; the counts do not need to be consecutive.
5. E2E protects against random physical faults (EMI, α particles) and does not defend against deliberate attacks (CRC can be recomputed at will). Cybersecurity scenarios need SecOC's MAC key signature on top.
