# 3.2 Lockstep Cores and Redundancy: Engineering with Two Kidneys

In the EMC lab, your steering ECU is undergoing the BCI (bulk current injection) test specified by ISO 11452-4. The test engineer clamps a current probe around the CAN harness and injects 200 mA of 150 MHz RF interference. Harmonics on the spectrum analyzer pulse like a heartbeat. You stare at the Vector CANoe trace window. Everything is normal.

Then the engineer says, "Here it comes."

He presses a button in the test script. It releases a 1 MeV α-particle beam from a Van de Graaff generator through a micron-scale aluminum foil window, aimed precisely at the exposed Cortex-R5 package on the PCB. The range of an α particle in aluminum is itself only microns; a few millimeters of aluminum would absorb it completely. You know what happens next: the α particle strikes some storage node or combinational logic path inside the chip, and the deposited energy is enough to flip a logic level.

At the instant the scope triggers, you see two things happen almost together:
- The SMU (Safety Management Unit) fault output pin goes from high to low; the interval from rising edge to falling edge is 7.3 ns.
- A 3E fault frame appears on the CAN bus. From fault to frame on the bus, the whole path takes less than 50 µs.

You take a deep breath and pull the SMU's internal log. Alarm source ID: 0x0B ("Lockstep Comparator Mismatch"). Core 0 says the result register is 0x0000A43F. Core 1 says 0x0000A42F. BIT[4] flipped. The α particle hit bit 4 of core 1's ALU adder. But the vehicle has no functional degradation, because the SMU triggered the fault response within two clock cycles of detecting the lockstep mismatch.

You take a sip of coffee. A potentially fatal random hardware fault lived in your system for less than 50 µs.

## From Linus Pauling to Dual-Core Lockstep: The Mathematical Roots of Redundancy

In 1949, Linus Pauling published a paper in *Science* that changed medical history: "Sickle Cell Anemia, a Molecular Disease." His core finding was that sickle-cell anemia patients have an amino acid substitution in the hemoglobin molecule: glutamic acid becomes valine. That substitution makes hemoglobin polymerize under low oxygen, deforming the red blood cells. But the most interesting part is that the disease appears only in **homozygotes** (both alleles mutated). **Heterozygotes** (one normal gene, one mutated gene) are almost completely normal, and they even gain partial resistance to malaria.

Why? Because normal hemoglobin produced by one healthy β-globin gene is enough to functionally compensate for the defective mutated gene. One breaks, the other takes over. That is the mathematical essence of biological redundancy: duplicate a critical component, and a single-point fault becomes a tolerable degraded state.

In electronics, redundancy is the standard way to reach ASIL D (single-point fault metric SPFM ≥ 99%, latent fault metric LFM ≥ 90%). No single chip can meet the ASIL D random hardware failure metric targets without redundancy. This is not just an engineering practice; it comes from the standard's quantitative targets for hardware architecture metrics. Take a typical MCU failure rate of λ = 100 FIT (100 failures per billion hours). Without redundancy, the single-point fault metric would fall well below the 90% required for ASIL B, let alone the 99% for ASIL D.

But redundancy has two fundamentally different implementation paths: computational redundancy and functional redundancy. Lockstep cores implement the former: two identical CPUs do the same computation, and hardware compares every result. Dual sensors implement the latter: one independent sensor component verifies another's measurement. They complement each other but cannot replace each other.

## Cortex-R5 Lockstep: The Art of Beat-by-Beat Comparison

The ARM Cortex-R5 is one of the most widely deployed lockstep architectures in automotive, especially in the TI TMS570LC43x and the RPU (Realtime Processing Unit) of the Xilinx Zynq UltraScale+ MPSoC. Cortex-R5 lockstep mode is not just a CPU plus a "checker"; it replicates the entire processor microarchitecture.

In lockstep mode, Cortex-R5 contains two identical processor cores inside: instruction fetch, instruction decode, register file, ALU, multiplier, divider, Load/Store unit, all the way to the AXI bus interface—everything is duplicated. The two copies are called the "Main Core" and the "Checker Core." The main core executes all operations normally and drives the bus and external interfaces. The checker core receives exactly the same inputs as the main core (clock, reset, interrupts, AXI read data), but it drives no external bus. Its outputs go only to a hardware unit called the CCU (Compare and Checker Unit).

The CCU does something extremely simple and extremely demanding: in **every clock cycle**, it XOR-compares all checker-core output signals with the corresponding main-core signals. Any inconsistent level is immediately latched as an error flag.

```
  Simplified Cortex-R5 lockstep block diagram:

  clock ──────┬────────────────────────────┐
              │                            │
              ▼                            ▼
      ┌───────────────┐          ┌───────────────┐
      │  Main Core    │          │ Checker Core  │
      │               │          │               │
      │ Fetch ▸ Decode│          │ Fetch ▸ Decode│
      │ RegFile ▸ ALU │          │ RegFile ▸ ALU │
      │ LSU ▸ AXI IF  │          │ LSU ▸ AXI IF  │
      └───────┬───────┘          └───────┬───────┘
              │      output signals      │    internal signals
              │   ┌──────────────────────┐   │
              │   │   CCU comparator     │   │
              │   │                      │   │
              │   │  Main[i] XOR         │   │
              │   │  Checker[i]          │   │
              │   │       │              │   │
              │   │  Any ≠ 0 → error     │   │
              │   │            latch     │   │
              │   └────────┬─────────────┘   │
              │            │                 │
              │            ▼                 │
              │     SMU alarm input          │
              │            │                 │
              ▼            ▼                 ▼
            AXI bus   interrupt ctrl        TCM
           (driven by main core only)
```

Which signals the CCU compares is decided by the chip implementation, and runtime software cannot turn lockstep off. Typically these signals are compared:
- all AXI write address channel signals
- all AXI write data channel signals
- all AXI read address channel signals
- internal register-file write enables and write data
- all TCM interface write data signals

Note one key design choice: the CCU **does not compare** AXI read data, interrupt inputs, or reset signals, because the checker core and main core share those inputs and they are identical by construction. The CCU compares only signals generated by the core itself that ought to be identical. If both cores receive the same interrupt and the same data but produce different computation results, that's a problem inside the core.

Cortex-R5 lockstep mode is fixed at chip design time; software cannot enable or disable it at runtime. What software can configure is the lockstep error response behavior; which register and which bit depends on the implementation. The configuration code usually runs in Boot ROM, before jumping to the user application:

```c
/* Cortex-R5 lockstep error response configuration (in Boot ROM) */
void Enable_Lockstep(void)
{
    uint32 actlr_val;

    /* Lockstep mode is fixed by the hardware configuration at chip design time (tied off
     * during synthesis). Software cannot disable lockstep at runtime. But software can
     * configure the error response behavior through ACTLR: */
    asm volatile("MRC p15, 0, %0, c1, c0, 1" : "=r"(actlr_val));
    actlr_val |= (1UL << 3U);  /* Enable the lockstep error response; the bit definition depends on the implementation, check the chip manual */
    asm volatile("MCR p15, 0, %0, c1, c0, 1" :: "r"(actlr_val));

    /* Execute synchronization instructions to make the configuration take effect */
    asm volatile("ISB");
    asm volatile("DSB");
}
```

This code must run in the Boot ROM stage, because lockstep is already active in hardware; the assembly instructions themselves execute in parallel on both cores. If you write this configuration code in user code, it goes through the checker comparison as the same two write sequences. Configuration must be complete before executing any asymmetric code (for example, reading a chip serial number or calibration parameters—things the two cores would not get identically).

## What Lockstep Can Do, and What It Can't

The most beautiful property of a lockstep core is **near-zero detection latency**. From hardware fault to detection, latency can be as low as **two clock cycles**. On a 400 MHz Cortex-R5, one cycle is 2.5 ns, so two cycles is 5 ns. Compared with any software mechanism (a watchdog needs milliseconds, E2E protection needs communication cycles), this detection latency is six orders of magnitude shorter.

But lockstep can only **detect** errors, not **correct** them. When the CCU sees a mismatch, it doesn't know which core is right; it only knows the results differ. The only correct response is to enter a safe state, triggering a reset or degradation.

This detect-only property distinguishes lockstep from a more powerful redundancy scheme: **triple modular redundancy (TMR)**. TMR uses three cores doing the same computation, and a majority voter decides the final result. If one core goes wrong, the other two can outvote it, so TMR can detect and correct a single-core fault. But TMR is almost never used in automotive, because of cost and power: relative to a single core, lockstep needs 100% extra silicon area (two cores) and TMR needs 200% (three cores). Automotive ECUs have far tighter area and power constraints than spacecraft.

```
  Redundancy comparison:

  Lockstep (two cores):       TMR (three cores):
  ┌───┐  ┌───┐            ┌───┐ ┌───┐ ┌───┐
  │ A │  │ B │            │ A │ │ B │ │ C │
  └─┬─┘  └─┬─┘            └─┬─┘ └─┬─┘ └─┬─┘
    │       │               │     │     │
    └──┬────┘               └──┬──┴──┬──┘
       │                       │     │
       ▼                       ▼     ▼
   comparator =?          ┌─────────────┐
       │                  │  majority   │
    ┌──┴──┐               │  voter      │
    │     │               │             │
  A=B   A≠B               │ A=B ✓ → A   │
    │     │               │ A=C ✓ → A   │
    ▼     ▼               │ B=C ✓ → B   │
 continue  alarm          └──────┬──────┘
                                 │
                                 ▼
                          output (corrected)

  Detection: ✓      Detection: ✓     Correction: ✓
  Correction: ✗     Correction: ✗
  Area cost: 100%   Area cost: 200%
```

Lockstep has a deeper blind spot: **common-cause failure (CCF)**. The two cores share the same clock source, the same power rail, and the same physical layout. If the VDD core voltage dips and both cores compute wrong, the CCU sees no mismatch, because both produced the same wrong result under the same wrong conditions. Likewise, if the RTL design itself has a defect (say, the multiplier produces a wrong result for a particular operand combination), both cores produce the same wrong output.

ISO 26262-9:2018 discusses common-cause failure analysis in its clause on dependent failure analysis. Countermeasures against common-cause failure must be implemented outside lockstep, including but not limited to:
- a watchdog with an independent clock source (see 3.1)
- end-to-end communication protection (E2E)
- diverse redundancy, using processors with different architectures for the same logical decision

## Sensor Redundancy: The Other Half of the Kidney

Lockstep protects the computation logic. But automotive safety needs another kind of redundancy: sensor redundancy. If both lockstep cores compute the same wrong sensor signal, their results agree completely. And both are wrong.

Take EPS (electric power steering). A real HARA usually rates steering safety goals as ASIL D. That means the steering angle sensor must also reach ASIL D, or reach an equivalent safety integrity through redundancy. In practice, a dual-chip steering angle sensor is the most common solution:

```
  EPS dual-sensor redundancy architecture:

  ┌───────────────────┐     ┌───────────────────┐
  │ TAS Sensor IC 1   │     │ TAS Sensor IC 2   │
  │ (primary sensor)  │     │ (redundant sensor)│
  │                   │     │                   │
  │ magnetic encoder  │     │ magnetic encoder  │
  │ channel A         │     │ channel B         │
  │ AMR/GMR/Hall      │     │ AMR/GMR/Hall      │
  │ SPI output        │     │ SENT output       │
  └────────┬──────────┘     └────────┬──────────┘
           │                         │
           ▼                         ▼
     ┌───────────────────────────────────────┐
     │   MCU A (ASIL D domain)               │
     │   processes sensor 1 data             │
     │   compares it with sensor 2 data      │
     │   |angle1 - angle2| < 3° ?            │  ← plausibility check
     │   if exceeded → safe state            │
     └───────────────────────────────────────┘
```

The accelerator pedal position (APP) sensor uses a similar redundant scheme, usually two independent Hall sensors in the same package, outputting two analog voltages or SENT protocol signals. Different physical principles (some inductive, some Hall) reduce common-cause failure.

But there is an easily overlooked detail: the sensor "plausibility check" must be implemented in software. If the plausibility check code itself fails, two different sensor values can be wrongly judged "consistent," and the redundancy is useless. Who guards the guard? In ASIL D systems, sensor plausibility check code usually runs on the lockstep core and is itself monitored by WdgM Logical Supervision.

## Homogeneous vs Heterogeneous Redundancy: The Value of Diversity

Everything discussed so far is homogeneous redundancy: backing up with components of the same design (even the same physical batch). Homogeneous redundancy has excellent coverage of random hardware faults (like α-particle bit flips). But it can do nothing about system design defects (code bugs, RTL bugs).

Heterogeneous redundancy implements the same function with a completely different design. The classic automotive example is the hydraulic backup in a braking system: the primary brake is an electronically controlled EHB (electro-hydraulic brake), but regulations require a fully mechanical/hydraulic backup brake circuit. Even with the vehicle's power off, the driver pressing hard on the pedal can push the master cylinder through a physical linkage.

At the electronics level, ASIL D systems sometimes use a smaller independent monitor MCU (an 8-bit or 16-bit chip, say) running a stripped-down monitoring algorithm and cross-checking the main MCU's output. This monitor MCU uses a different chip architecture, a different compiler, and even a different team, to minimize shared bugs.

```
  MCU-level heterogeneous redundancy (monitor MCU architecture):

  ┌──────────────────────────┐      ┌──────────────────────┐
  │ Main MCU (Cortex-R5     │      │ Monitor MCU (S08      │
  │ lockstep)                │      │ 8-bit)               │
  │                          │      │                      │
  │ FOC motor control        │      │ simplified monitor   │
  │ algorithm                │      │ algorithm            │
  │ torque command = 123.4 Nm│      │ expected torque      │
  │                          │      │ ∈ [100,150]          │
  │ output → drive bridge    │      │ receives main MCU    │
  │                          │      │ output over SPI      │
  └──────────────────────────┘      └──────────┬───────────┘
                                               │
                                               ▼
                                    ┌─────────────────────┐
                                    │ monitor MCU decides │
                                    │ independently:      │
                                    │ within the safe     │
                                    │ range?              │
                                    │ no → pull enable    │
                                    │      pin low        │
                                    │      → shut down    │
                                    │        drive bridge │
                                    └─────────────────────┘
```

The lockstep architecture in the AURIX TC3xx family follows exactly this principle: the main TriCore core and the Checker Core run **the exact same instruction sequence**, and a hardware comparator compares the two cores' outputs every cycle. The Checker Core does not trim logic; it executes the same compiled binary. The advantage is that no software change is needed: single-core code compiles and runs directly on the lockstep pair, and hardware handles all comparison automatically. Once the comparator sees a mismatch, it triggers a safety response through the SMU.

The price of heterogeneous redundancy is higher development and maintenance cost (two codebases), but it is the strongest weapon against system design defects.

Lockstep cores are extremely good at detecting random hardware faults: α-particle strikes, clock jitter, timing violations from transistor aging—faults that affect one of the two cores in a physically independent way. But lockstep is completely blind to common-cause failure: if both cores share the same design defect, the same power, and the same clock, they fail the same way under the same conditions. ISO 26262 calls this blind spot **common-cause failure**. You cannot fight common-cause failure with "more lockstep"; you can only use diversity—different processor architectures, sensors based on different principles, code written by different teams.

Homogeneous redundancy gives you random-fault coverage; heterogeneous redundancy gives you systematic-fault coverage. You need both. That's why an ASIL D system cannot rely on lockstep alone; it must also pair it with an independent watchdog, E2E protection, and diverse algorithms in a monitor MCU.

From an engineering standpoint, the value of lockstep is that it is completely transparent to software; application code needs no special logic. But that is also the trap: because it is transparent, designers easily forget its limits.

## Summary

1. A lockstep core compares the outputs of two identical CPU cores beat by beat. The CCU comparator detects any mismatch within 5 ns, but it can only detect, not correct.
2. Common-cause failure (CCF) is lockstep's fundamental blind spot: two cores sharing a clock, power supply, and design can fail the same way at the same time. Diversity—heterogeneous architectures, independent watchdogs—must fill the gap.
3. Sensor redundancy compares measurements through dual chips or dual physical principles (Hall plus inductive), but the plausibility check code itself must be protected by lockstep and WdgM.
4. Homogeneous redundancy covers random hardware faults (α particles, transistor aging); heterogeneous redundancy covers system design defects (code bugs). An ASIL D system needs both.
